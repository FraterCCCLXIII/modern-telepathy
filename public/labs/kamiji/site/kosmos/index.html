Reality Kosmos Engine

Build a reality,
not a scene.

An experimental 3D engine written in Rust on wgpu. Prototype games, a film player, character labs and an editor run on it, and agents can drive it over a headless protocol.

What it is

Experimental. Started on 15 October 2026.

Kosmos Engine is a 3D engine in Rust. Its README calls it a third backend beside PlayCanvas on the web and Godot in the Yakopop repository. The plan of record asks for a fixed-tick, seeded, replayable simulation, everything stored as text, and a headless mode, so that people and AI agents can build and test with the same commands.

It is a private repository today. The games below are prototypes, not products.

Features

What the engine does today and what is only planned, from the crates, the plans and the reports. A badge says how far each one is. Nothing here is a shipped product.

In detail: The UI, Workshops, Physics, Airships, Previs and games, Animation, Character Studio, Effects.

  • Replayable simulation tested

    Fixed tick of 1/64 s, seeded random numbers, a state hash, snapshot, restore and replay. CI compares the hash of native builds with the wasm32 build under wasmtime, and on macOS.

    Source: kosmos-core, kosmos-sim, .github/workflows/engine.yml, engine-matrix.yml.

  • wgpu renderer prototype

    Flat, toon and PBR looks, shadows, sky and clouds, grass, water, motion blur and an HDR tone map, with 54 JSON schemas for the data around it. Shaders are WGSL files in the repo.

    Source: crates/kosmos-render/src, schemas/, looks/.

  • Headless protocol prototype

    Typed JSON messages over stdio or WebSocket, a typed TypeScript client, and an MCP server over the same protocol. The step request is the only thing that advances the sim.

    Source: kosmos-protocol, apps/kosmos-cli, packages/kosmos-protocol-sdk.

  • Editor prototype

    An egui editor inside the native app: scene tree, inspector, gizmos, undo, and a list of labs. See The UI below.

    Source: apps/kosmos-app/src/editor, kosmos-cmd.

  • HUD in TypeScript prototype

    Solid components run on Hermes and drive a retained HUD tree that the app paints natively. See Architecture.

    Source: crates/kosmos-host, kosmos-ui, games/kosmica-real.

  • Characters and faces prototype

    Animation graph, 45 face channels, a face plate for heads without morph targets, wardrobe arithmetic, a mochi importer and glTF morph targets.

    Source: kosmos-anim, -face, -faceplate, -wardrobe, -model.

  • Film, subtitles, audio prototype

    Compiled film timelines with camera, actors, subtitles and cues. Cue-driven audio over kira, and a client for a local text-to-speech server.

    Source: kosmos-film, kosmos-audio.

  • Assets prototype

    A content-hashed cache with hot reload, and importers for glTF, FBX, OBJ and mochi. Mesh writers for STL, PLY, OBJ and 3MF, and a KTX2 writer.

    Source: kosmos-assets, kosmos-model, kosmos-meshops, kosmos-texops.

  • Physics prototype

    Rapier colliders, queries and a character controller. A rigid-body world exists but no app uses it. See Physics below.

    Source: crates/kosmos-physics.

  • Airships prototype

    Flight, decks, docking, sway and a planet to land on, checked against numbers from the web code. See Airships below.

    Source: crates/kosmos-airship.

  • Browser runner unverified

    A wasm and WebGPU runner builds a single canvas of the default scene. No public build was found and no browser frame time is measured.

    Source: apps/kosmos-web.

  • Networking, game scripting in wasm planned

    Named in the plan (kosmos-net, wasm components). No such crate exists. The plugin crate is data-only.

    Source: docs/plans/rust-engine.md, crates/kosmos-plugin.

  • Mobile and consoles not found

    Nothing in the repository targets iOS, Android or a console. The consoles idea belongs to the Godot work in Yakopop.

    Source: searched Cargo.toml and CI files.

The UI prototype

The editor lives inside kosmos-app and is built with egui. It has a left rail of views, a scene tree, an inspector, gizmos, a bottom output panel and a list of labs, each lab a small playable page. Commands go through typed edit commands with undo and redo.

The editor has three themes: Dark, Kosmica and a Godot HUD theme taken from Yakopop's tokens. Headless UI tests drive the widgets through their accessibility labels. An older Solid and Vite dev UI is parked. A separate Watch view is described in a plan and was not checked.

Source: apps/kosmos-app/src/editor, docs/themes/godot-hud.md, apps/dev-ui/README.md, reports/labs-ball.png.

Workshops prototype

The word covers two things. On this site the Workshops are three studios for building a character: a Kamiji hand, a Kamikin mochi and an emoji face. They run on three.js in the browser, not on the Kosmos renderer.

In the engine, labs are the working equivalent: more than 40 lab files in the editor, such as broom, hoverboard, mecha, dragon, wardrobe and airship. A draft plan of 17 Oct 2026 proposes one workshop space per area on the editor rail. It says nothing in it is built, so treat that part as planned.

Physics engine prototype

The physics crate wraps Rapier 0.36.1 with its enhanced-determinism option and no threads or SIMD, so results depend only on the scene. It has static colliders, ray and shape queries, and a kinematic character controller. A stepped rigid-body world exists, but no sim or app code uses it. Its gate is a hash case that must match between native and wasm.

The broom, mecha, capture and ball labs and the HUD world queries use the static part. Vehicles are a separate arcade handling model ported from the web code, not Rapier. No buoyancy or water physics and no ragdoll were found. The flesh crate does cosmetic soft chains only. The one measured number is crowd steering: 300 people took 1.25 ms per tick, against 9.2 ms for the TypeScript version on V8. The capture shows a lab that uses the ground queries, not colliders drawn.

Source: crates/kosmos-physics/src/lib.rs, kosmos-vehicle, kosmos-flesh, reports/parity-frametime.md, reports/labs-broom-rider.png.

Airship support prototype

The airship crate ports the web game's flight model, deck geometry and walking on a moving deck, sway and rope, docking and landing, the globe maths and part of the Terra planet. Each part is checked against numbers from the TypeScript, and the hashes match between native and wasm. A loader reads 41 of 42 baked ship designs, and an Airship lab in the editor flies them.

Not done, per the plan of 18 Oct 2026: rigging and livery, sails in the lab, the race lab, and Terra roads and rivers. The sail rigging study lives in a Yakopop worktree. The port does not use a physics engine. Flight is a formula, not a simulation of air.

Source: crates/kosmos-airship, docs/plans/airship-port.md, yakopop-sails docs/plans/sail-rigging.md, reports/labs-airship-ships.png.

Previs and game development prototype

Previs, short for previsualization, is the planning stage before final production: you block out shots, cameras, staging and timing, then cut them into a rough timed version (an animatic) to judge the sequence before anything is polished. Dedicated tools exist for that job. Kosmos is not one of them. It has several parts a previs workflow needs, in an engine where the same data can also become a game.

A film in the engine is a compiled timeline: a list of scenes, each with tracks of timed events for camera shots, actors, dialogue and subtitles, cards, fades and sound cues. Every channel is a pure function of time, so the film can be scrubbed, skipped and played frame by frame with the same result. The editor shows those tracks on its Timeline tab.

Source: crates/kosmos-film/src/lib.rs, schemas/film.schema.json, apps/kosmos-app/src/editor/timeline.rs, reports/timeline-film.png.

Previs: what is there

  • Shots and cameras prototype

    The film player outputs a camera as position, look-at, field of view and roll, with shot cuts, transitions and accents. The demo film in the capture cuts through eight shots, from fixed and medium to over-the-shoulder and close.

  • Staging and actors prototype

    Each actor has an acts track that sets animation parameters on the engine's own characters, plus hands and face from the film data. Staging uses the same models and rigs as the games.

  • Timing, subtitles and cues prototype

    Time runs on the sim's 64 Hz tick. A frame carries the subtitle line, a card, a fade, light and screen effects, and the cues that fire in that tick: a line begins, a sound, a cut.

  • Agents can drive it prototype

    The headless protocol steps the sim, applies typed scene edits and takes screenshots on a build with rendering, over stdio, WebSocket or MCP. That film playback is exposed through the protocol was not checked.

  • Animatic export, shot lists not found

    No video, image-sequence or shot-list export, and no previs mode, was found. Films are compiled from sources written outside this repository, so the editor reads them rather than authoring them.

Game development: what is there

  • Scenes and assets prototype

    Scenes are JSON that can be parsed, written, diffed and resolved from prefabs. Models come in through glTF, FBX, OBJ and mochi importers, with a content-hashed cache and hot reload.

  • Character controller and physics prototype

    A kinematic character controller and ray and shape queries on Rapier, plus a walker for round planets. See Physics above.

  • HUD and input prototype

    A retained HUD tree painted natively, driven by TypeScript on Hermes. An action map handles rebinding and input recording.

  • Replay and tests tested

    The fixed tick, state hash, snapshot and replay let a game run the same way twice. CI checks the hash on native and wasm.

  • Games prototype

    Kamikin and Kosmica run on the engine as prototypes. No public game build and no player-facing packaging step was found.

Sources: kosmos-film, kosmos-scene, kosmos-model, kosmos-assets, kosmos-physics, kosmos-ui, kosmos-input, kosmos-protocol, docs/plans/kamikin-port.md, .github/workflows. Searched for ffmpeg, mp4, animatic and previs in crates, apps, docs and tools: no match.

Animation and rigging prototype

Skeletons, clips, faces and hands. The graph and importers are in the crates. The Faces section below covers the face channels in more detail.

  • Animation graph prototype

    A data file (*.anim.json) holds a state machine, one-dimensional blend trees, crossfades and masked layers over the skinned clips of a character. Fed the fixed tick, a pose is a pure function of its inputs. The crate also has two-bone and FABRIK reach, spring follow-through and crowd walking.

  • Rigged characters prototype

    Skinned models with a skeleton, named clips and clips retargeted by bone name from a donor model. The editor has a Rig lab, which plays a quadruped rig through moves and attacks with effects, and a rig registry that marks some rigs as partial.

  • Face channels and morph targets prototype

    45 face channels, morph targets carried through glTF, and a face plate for heads without them.

  • The Kamiji hand rig prototype

    The Kamiji hand model is among the engine's assets, and the editor builds finger grids from a skeleton's finger chains with curl and spread controls, so a hand with six fingers gets six columns. The hand library on this site is a separate three.js and React build.

  • Mochi importer prototype

    Turns an exported mochi (skinned body, face shell, baked motions, six face states) into the same model type as glTF import. The Kamikin cast loads this way.

  • glTF import and export prototype

    Meshes, skins, clips and morph targets in and out, with golden files under tests/golden.

  • FBX unverified

    Binary FBX import reads meshes, normals and UVs. Its source says node transforms, materials, skins and animation are not read yet. A writer exists too, and its coverage was not read. OBJ, Collada, USD, STL, PLY and 3MF readers are in the model crate.

  • Motion capture, ragdoll not found

    No capture or BVH importer was found. The physics crate names ragdoll only as not built.

Sources: crates/kosmos-anim/src/lib.rs, ik.rs, crates/kosmos-model/src (fbx_import.rs, gltf_import.rs, mochi_import.rs, anim.rs), apps/kosmos-app/src/editor/rig_hands.rs, lab_rig.rs, assets/models/kamiji. Read 25 Oct 2026.

Character Studio prototype

The character builders exist in two places. In the engine, the Character studio lab is one page for a character: a body, head shape, hair plates, clothing and a pose. Garments are shells cut from the body's own skin, so they follow the same bones. Hair guides sway with the head, and the ears of the animal-eared characters flop with its movement. The lab's own file marks its status as work in progress.

On this site the Workshops are the character builders you can open now, and the demo further down this page lets you pick a Kamikin, a face and a clip. They run on three.js, not on the Kosmos renderer.

Particles, liquid and fabric

What exists for effects and soft things, taken from the crates, the plans and the reports. Particles are built and drawn. Water is a flat rendered sheet. A liquid simulation and simulated cloth are plans with no code.

  • GPU particles prototype

    A compute runtime in kosmos-fx reads the web effects library: all 58 effects and 1628 emitters parse, 20 sprite shapes draw, and the GPU motion matches the CPU reference. One million simple particles stepped in 0.197 ms of GPU time on an M3 Max. They are drawn in the editor's lab viewport over the scene, without depth testing. The plan lists joining them to the main render pass as open, and no particle pass was found in the renderer's frame graph.

    Source: crates/kosmos-fx, apps/kosmos-app/src/editor/lab_fx.rs, docs/plans/fluid-vfx.md (F0, F1).

  • Particle lighting and collision prototype

    Billboards are lit by the sun and the lamps. Particles can stop or bounce on static triangles, and a CPU test marches light through a uniform density slab. All of it is visual only and never enters the state hash.

    Source: kosmos-fx light.rs, ballistic.rs, volume.rs, kosmos-render particle_light.rs.

  • Water surface prototype

    The renderer has a water sheet: a grid whose height moves with time, drawn only when a look asks for it. It is not a simulation, and the Kamikin port does not use animated water yet.

    Source: crates/kosmos-render/src/water.rs, water.wgsl, docs/plans/kamikin-port.md.

  • Liquid simulation planned

    Pouring, splashes, rivers and waterfalls are steps F3, F6 and F7 in the fluid plan. No fluid solver exists in the crates: the fx crate holds particles and a density march only. Buoyancy and water physics were not found either.

    Source: docs/plans/fluid-vfx.md, crates/kosmos-fx, kosmos-physics.

  • Rope, cape and tail solver prototype

    A cosmetic XPBD solver for ropes, capes and tails sits in kosmos-flesh with a golden file and two tests. No app code calls it yet. The character studio uses the same crate's springs for ear and tail jiggle.

    Source: crates/kosmos-flesh/src/xpbd.rs, jiggle.rs, tests/golden/rigs/xpbd.json.

  • Cloth, garments in motion, soft bodies planned

    Garments are static shells on the skin. Airship sails move by formula and are not cloth. A cloth decision record and jelly-like soft objects are planned and unbuilt.

    Source: docs/plans/flesh-dynamics.md (FLS.6, PHY.D7), crates/kosmos-wardrobe, kosmos-airship.

  • Fire and smoke grids planned

    Step F8 in the fluid plan. No grid solver was found.

    Source: docs/plans/fluid-vfx.md, crates/kosmos-fx.

  • Breaking things prototype

    Voxel fracture matches the web code's numbers in tests. A separate crate cuts closed meshes into convex pieces, marked a spike. The strike tools, shapes and burn rules are not ported.

    Source: crates/kosmos-voxel, kosmos-break, reports/fx-f4b-voxel.md.

Sources: kosmos-engine docs/plans/fluid-vfx.md, flesh-dynamics.md, crates/kosmos-fx, kosmos-flesh, kosmos-render, reports/labs-rig-fx.png. No code for liquid simulation or cloth was found. Searched 25 Oct 2026.

Architecture

The layers as the code has them, top to bottom. Read each box as a group of crates or files, and each line as the way it talks to the layer below. The list under the diagram says the same in words.

How a frame and a HUD update flow

  1. The window loop sends the game thread a tick (milliseconds since the last one) and any input lines.
  2. Hermes cannot move between threads, so the runtime is created inside its own thread and only messages cross.
  3. The JS bundle runs. Solid's effects call four host operations: create, set property, insert, remove.
  4. Each batch comes back as a delta of UI ops, camera, lights, objects and logs. If many batches pile up, only the newest heading is run and the ticks are summed.
  5. The app applies the ops to the retained HUD tree, then paints it natively over the wgpu frame.
  6. The sim steps on its own fixed 1/64 s tick. A headless agent calls the same step through the protocol.

Sources: crates/kosmos-host/src/inproc.rs, hermes.rs, crates/kosmos-ui/src/op.rs, kosmos-core. Step 6 and the painter come from module docs and were not traced in a run.

How the JavaScript is built

  • Game and HUD source is TypeScript and TSX. Babel with babel-preset-solid compiles the JSX in universal mode against the engine's own renderer module, then esbuild bundles it to one ES2018 script.
  • Hermes is built from a pinned facebook/hermes revision with the JIT compiled out and linked as a static library through a small C++ shim. If that library is missing, the crate still builds and the fixture runner is used.
  • Rust and JS talk through a fixed list of host functions (set_pose, raycast, ground_at, emit and more) described once in engine/wit, from which the TypeScript types are generated.
  • HUD screens come from Yakopop's Solid sources, copied unchanged. The web dev UI is parked.
  • Agents use the headless protocol (JSON lines or WebSocket) with a typed TypeScript client, and an MCP server over the same messages.

Sources: games/kosmica-real/build.mjs and PROVENANCE.md, tools/hermes, crates/kosmos-host/build.rs, engine/wit, packages/kosmos-protocol-sdk.

Compatibility

Kosmos is a third backend beside Godot and PlayCanvas in the Yakopop project. Compatibility means shared data, shared code and a way to compare pictures. It does not mean Kosmos opens Godot or PlayCanvas projects.

Godot partial

Shared. The same exported Kamikin data (planet, height cube, grass, the mochi cast) from Yakopop's Godot folder, copied by one script. The toon shader's header says it follows toon_shade in Godot and celShade in the web code. The Hermes build and the HUD Solid sources are copied from Yakopop's Godot binding.

Measured. Six poses scored against Godot 4.7.2 on Metal. Best is pond at MAE 20.7 and SSIM 0.752. Most error is missing content. No pass or fail threshold is approved. See Numbers.

Not done. No loader for Godot scenes or GDScript. Yakopop's pack files (kamikin.json, kamikin-village.json) feed Godot, and no reader for them was found in the engine. The native extensions in the Godot checkout were dead links, so the references have no Hermes HUD or audio. Embedding Godot as a renderer is a proposal only.

Sources: tools/kamikin-export/sync-data.sh, tests/parity/ref/kamikin/godot/provenance.json, reports/parity-kamikin.md, docs/plans/godot-embed-multi-renderer.md, yakopop apps/godot.

PlayCanvas partial

Shared. Yakopop's web client runs on PlayCanvas 2.23.0, and many engine ports start from its pure TypeScript logic, checked against goldens. A recording stand-in for the playcanvas module lets Yakopop's model builders run inside a Hermes bundle with no rendering.

Measured. PlayCanvas frame times on three web scenes in Chrome (a dense town at 24.1 ms CPU median). The PlayCanvas column of the Kamikin parity table is unmeasured because Kamikin has no web build. Kosmos cells for those three scenes are also unmeasured.

Not done. No PlayCanvas adapter in the engine. A script that captures a PlayCanvas reference exists for the Sakura Town scene. Streaming one scene to several renderers is a proposal.

Faces and voices prototype

Try the Face and Clip menus in the hero. They show the Kamikin face states in this page, not the Rust face crate.

  • Face channels

    The face crate holds 45 numeric channels for eyes, brows, mouth, gaze and more. It was ported from the web code in Yakopop and is checked against golden data from that code.

  • Face plate

    For characters whose head has no morph targets, the faceplate crate paints eyes, brows, mouth, blush and marks onto a texture for the head. Morph targets are also carried through glTF import and export.

  • Visemes and phonemes

    Mouth shapes come from a viseme table with phonemes and coarticulation. A draft proposal asks for a way to author them by hand, and nothing in that proposal is built.

  • Voices

    The audio crate has a client for a local text-to-speech server. The server returns audio plus timed mouth shapes in a header. The server lives in the Yakopop repository. Which voices ship is not settled in the files.

  • Mochi importer

    The model crate turns exported mochi characters (skinned body, face shell, baked motions, six face states) into the same model type that glTF import gives. The Kamikin characters in the hero are those mochi, as GLB files.

Sources: kosmos-engine crates/kosmos-face, kosmos-faceplate, kosmos-audio/src/tts.rs, kosmos-model/src/mochi_import.rs, docs/plans/rig-authoring.md (proposal, 23 Oct 2026), tests/golden/face.
