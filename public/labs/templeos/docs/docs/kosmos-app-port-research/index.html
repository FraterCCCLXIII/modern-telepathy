Porting kosmos-app into the TempleOS desktop: feasibility report

Edited 2026-10-27docs/kosmos-app-port-research.md

Date 2026-10-27. Read-only research; nothing built, run or launched. Paths are relative to the repo root. "Unverified" marks anything not read from code or measured here.

0. Verdict#

A source port of kosmos-app to HolyC is not feasible (it is a 27.5k-line Rust, egui and wgpu program plus roughly 45 crates). Running it inside the guest is impossible (no network, no GPU, no Rust). It can be made to appear inside a TempleOS window by running it on the Mac and bridging two things: its widget tree (as data, drawn by HolyC in the desktop's own style) and its 3D viewport (as a small pixel stream). Input flows back through the existing editor.event grammar. The cheapest honest demo is a read-only mirror of editor.tree plus one viewport crop, which takes about 3 to 5 days, not weeks.

Naming caveat. "Kosmos" at kosmos.computer is a different public product (Arco, a generative-UI OS). kamiji/docs/kosmos-context.md lines 7 to 8 say the engine is not in that org. This report concerns apps/kosmos-app, the engine's editor.

1. What kosmos-app is#

  • Rust, edition 2024. apps/kosmos-app/Cargo.toml lines 1 to 12 and 31 to 90. Binary kosmos-app, 27,535 lines in src/*.rs (wc -l), plus about 130 files in src/editor/. A winit window with an egui editor drawn over a wgpu scene (egui, egui-wgpu, egui-winit, winit, tiny-skia, ab_glyph; Cargo.toml lines 79 to 86). About 45 workspace crates are linked (kosmos-render, -sim, -physics, -anim, -body and more).
  • The editor is immediate-mode egui, not the kosmos-ui tree. crates/kosmos-ui is "Retained HUD tree for the Solid host" that "does not layout, paint, or talk to Hermes" (crates/kosmos-ui/src/lib.rs lines 1 to 7). No Cargo.toml in crates/ or apps/ depends on it (grep, only its own manifest matches). NodeKind has 28 variants (crates/kosmos-ui/src/kind.rs lines 14 to 44). It describes game HUD screens, not the editor.
  • The HUD (game UI) has its own live path. apps/kosmos-app/src/hud.rs (3,036 lines) replays a hud.json op log (create, set, insert, remove) and paints on the CPU with tiny-skia. Hud::paint(width, height, ui_scale) -> Vec<u8> returns RGBA (hud.rs line 457). hud-element/1 is only a proposal: "Not built: nothing in this document exists as code yet" (docs/plans/hud-native-format.md line 3). The schema is schemas/hud-element.schema.json. The HUD painter belongs to the HUD session, and "Do not rewrite the painter" (docs/plans/rust-engine.md line 1305).
  • How the editor is exposed. The editor's widgets are egui's AccessKit tree, flattened to JSON (apps/kosmos-app/src/editor/introspect.rs lines 1 to 10, struct Widget lines 91 to 113).
  • Fields per widget: id, parent, role, label, value, rect [x0,y0,x1,y1] in points, disabled, toggled, src, src_guess.
  • Nodes with no label, value or action are folded away (lines 5 to 6). Roles are not typed beyond a string. interesting() keeps Button, TextInput, CheckBox, Slider, TreeItem and Window (lines 114 to 130).
  • There are no colours, fonts, icons, z-order, clipping or styles in the tree. That detail exists only in pixels.
  • Protocol. editor.tree, editor.at, editor.event {steps}, editor.view {tab,bottom,theme,select}, editor.shot (crates/kosmos-protocol/src/message.rs lines 311 to 345).
  • editor.shot writes a PNG to an engine-owned directory and replies {path,w,h,bytes,hash}. There is no inline or raw-RGBA editor frame request (lines 340 onward).
  • The step grammar is click:Label, hover:, click@x,y, drag@x1,y1>x2,y2[>x,y...], key:cmd+z, type:text, wait:n (apps/kosmos-app/src/editor/script.rs lines 1 to 20 and 141).
  • Two hosts answer it. The open window serves it with --serve-port N (apps/kosmos-app/src/main.rs line 908, window_link.rs). A headless EditorServer serves it with --serve-editor (apps/kosmos-app/src/editor_host.rs lines 1 to 80). The headless one keeps one renderer, scene and egui editor alive per connection and draws a fresh frame per request.
  • kosmos-mcp --connect 5878 is the MCP bridge to all of the above (.mcp.json lines 1 to 8). apps/kosmos-cli/src/mcp.rs lines 274 and 522 define the editor tool.
  • .claude/skills/drive-window/SKILL.md documents a 5 s reply limit. The first event after launch can return window_busy although it landed.
  • Rendering path. The 3D scene goes through kosmos-render (wgpu, Metal on this Mac), then egui-wgpu draws the panels over it. The headless editor shot size defaults to 1600x1000 (main.rs lines 138 to 139). The committed reports/editor-shot.png is 253,567 bytes (ls -la).
  • Split of UI shell versus engine and viewport.
Part Where Notes
UI shell src/editor.rs (3,289 lines), src/editor/* (menus, docks, inspector, timeline, labs, cast, chat) Described by the AccessKit tree; looks need pixels
Viewport and engine main.rs (4,041), kosmos-render, kosmos-sim, kosmos-physics, kosmos-anim and others Real GPU work. Only pixels can cross to the guest
Control plane editor.* and command, undo, redo, list_commands Already text, already agent-driven

2. Transport facts about the guest#

  • Today the host-to-guest path is COM1 over -serial tcp:127.0.0.1:4555 (scripts/boot-vm.sh line 17). The guest receiver Rx busy-polls InU8(0x3FD)&1 and reads InU8(0x3F8) (scripts/send-to-vm.sh line 27). It answers one dot per 8 bytes, and serial-send.py lines 14 to 17 waits for each dot.
  • The measured 1.4 KB/s is therefore the lockstep design (a TCP round trip per 8 bytes, plus the slow cocoa-window guest). It is not a hardware or baud limit. QEMU's 16550 model has no baud throttle on receive (unverified).
  • A streamed, un-acked protocol with the FIFO enabled and a bounded per-frame drain loop is untested. Rough guess, unverified: 1 to 3 us per byte for two port reads under TCG, so about 100k to 500k B/s when draining flat out and about 40 to 130 KB/s with a 4 ms per frame budget. This is the first thing to measure.
  • The guest already has a linear framebuffer address and a full-frame copy. ks_fb comes from PCI BAR0 (KsDesk2.HC line 919). The frame loop does MemCpy(ks_fb,bb,SW*SH*4) (lines 951 to 952), and README says that costs about 7 ms for 5.2 MB. A 640x400x4 blit would be about 1.5 ms.
  • The Viewport window in the desktop is a stub: AppViewport draws a rounded rectangle and two cubes (KsDesk2.HC lines 609 to 617). That is the natural place to blit host pixels.
  • The guest can already scan PCI (PCIClassFind, PCIReadU32, line 917 to 919). It does raw port I/O with no driver (COM1).
  • Input in the guest comes from ms.pos and key reads in Input() (line 853 onward). The mouse is read as relative deltas.

3. Candidate architectures#

(a) Host-driven pixel mirror#

Run kosmos-app (or --serve-editor) on the Mac, take editor.shot, convert, push to the guest, blit into a window.

Bytes per frame, for a 640x400 window (256,000 px).

Format Bytes At 1.4 KB/s At 40 KB/s (guess)
RGBA 1,024,000 12 min 26 s
RGB332 256,000 3 min 6.4 s
4 bpp palette 128,000 91 s 3.2 s
  • Tile deltas (for example 16x16 tiles, hash per tile) help a mostly static editor chrome a lot, but not a spinning viewport. They need a host differ, a protocol and a guest decoder. A typical 3D viewport redraw touches most of its tiles.
  • Serial alone gives a still image or about one frame every few seconds. A smooth 10 fps needs about 128 KB x 10 = 1.3 MB/s even at 4 bpp, so a shared-memory channel is mandatory for live pixels.
  • Host-to-guest channels, ranked: 1. ivshmem-plain. -object memory-backend-file,share=on,mem-path=/tmp/ks.shm,size=16M,id=hm -device ivshmem-plain,memdev=hm. The host mmaps the file and writes at memory speed. The guest finds it with the same PCI scan it already uses (vendor 1af4, device 1110) and reads BAR2 with MemCpy. Unverified: that SeaBIOS places the BAR below TempleOS's identity-mapped range, that TempleOS maps it writable or readable, and that TCG respects the shared mapping coherently. Cost: about 1 day to prove. Latency below 5 ms plus the guest blit. 2. gdbstub memory writes (-gdb tcp::1234, packet M addr,len:hex). Needs the VM stopped per write in system mode, hex doubles the bytes, and the guest buffer address must be sent back on serial. Works as a fallback; jittery (unverified). 3. Raw second drive or ISO. Needs a mounted second block device in TempleOS. The earlier ISO9660 route failed with an ISOInit exception (README.md "Things learned the hard way"), and the guest's cache behaviour is unknown. Lowest priority. 4. Serial tuned (streaming, FIFO on, no acks). Good enough for the tree (below) and stills. 5. Writing into the VBE framebuffer from outside QEMU. Not possible: VGA RAM is an internal RAMBlock with no shared mapping (unverified in detail, but nothing in scripts/ exposes it). The QEMU monitor can read memory (pmemsave) but I know of no stock command that writes it.
  • Look: the app appears as its own pixels (egui theme), not in the OS style. That is the weakest fit with apps/os-styles, which is the point of the Desk2 work.
  • Cost: bridge about 2 days (Rust or Python on the host), guest decoder about 2 days, shared-memory spike about 1 day. Risk: medium, mostly ivshmem.

(b) UI-tree-driven (recommended core)#

Send only the widget tree and events; draw it in HolyC with the toolkit that exists (Rect, RRFill, RRRing, Txt, Icon, Shadow in KsDesk2.HC lines 85 to 352).

  • Size: unverified, because I did not run the app. A 300-widget tree at about 40 bytes binary (id, parent, role, rect, flags, label) is about 12 KB, which is 9 s at 1.4 KB/s once and sub-second as deltas (changed widgets only). That fits the serial link as it stands.
  • Cleanly mapped AccessKit roles and what to draw:
Role or field HolyC drawing
Window Frame()-style window, title from label
Button RRFill plus centred TxtC, disabled greys it
CheckBox / toggled box plus tick, or a switch
Slider (value, numeric) rail plus knob; drag@ back
TextInput well plus caret; type: back
TreeItem indented row; click:Label back
Label / value Txt
  • What is lost: colours, icons (src/editor/lucide.rs), the viewport, timeline lanes, node graphs, gizmos (the skill says handles are "painted, not widgets"), custom egui painting in Cast, face boards and the labs. These are drawn by egui directly and appear in the tree as nothing or as one big rect. Expect the panels, menus, buttons, tree and inspector to look right and every custom canvas to be an empty box, which is where (a) fills in.
  • Free benefit: it picks up the five desktop styles (Longformer light and dark, macOS, Windows 11, Kosmica glass) with no extra work.
  • Cost: bridge 1 day, guest tree renderer 2 to 3 days (layout is given by rect, so no layout engine). Risk: low to medium. Rect clipping, scroll regions, popups and z-order need a rule (draw in tree order, clip children to parent).

(b2) NodeKind (hud-element/1) tree#

  • The kosmos-ui tree and hud-element/1 are the game HUD, not the editor. They map cleanly only for HUD screens.
  • Cleanly mapped kinds: Panel, Label, Bar, Divider, Swatch, Dots, Button, Switch, Slider, TextField (rect, rounded rect, text, caret). Needs host-side resolution before sending: Row, Column, Stack, At, Pad, Center, Spacer, Scroll, Overlay (layout kinds; the painter in hud.rs resolves them, kosmos-ui does not). Needs a bitmap or vector sprite: Icon, Image, Drawing, Wedge, FadeMask, Glyph, Slot.
  • A clean design would tap the painter's resolved layout as a display list of rect, text and image commands. That means a change in apps/kosmos-app/src/hud*.rs, which is owned by the HUD session (rust-engine.md line 1305). Do not start there. Mirror the HUD as pixels instead, because Hud::paint already returns RGBA at any size (hud.rs line 457).
  • Use (b2) only if the user later wants the game HUD in the guest.

(c) HolyC reimplementation of a subset#

  • Reasonable for a few panels only after (b) exists, and only for panels that are pure data (for example the Scene tree, Inspector fields, command list). Every panel reimplemented duplicates egui code and the command semantics (model.*, scene.*, undo steps). Not recommended as a first move; (b) with editor.event gets the same behaviour for free.

(d) Something better#

  • Hybrid (b) plus a thin (a): the chrome from the tree, the viewport as a low-rate pixel stream into a window rect. This is the recommended end state.
  • Do not use: running a second QEMU display or placing the Mac window beside it. That shows the app but is not "inside" the desktop.
  • Possible later: a request editor.frame returning raw RGBA of a region (a new protocol message and an EditorHost change in crates/kosmos-protocol, apps/kosmos-app/src/editor_host.rs). The demo avoids it by reading the PNG file the existing editor.shot writes. Do not add it without the user's go.

4. Input flow back#

Reuse the existing plumbing end to end; no new engine API is needed.

  1. Guest Input() (KsDesk2.HC line 853) already knows the mouse position in screen pixels, the buttons and the keys. Convert to window-local points by subtracting the window origin and dividing by the mirror scale.
  2. Guest writes event lines on COM1 (OutU8(0x3F8, ...); the same port the loader reads, so the link is already duplex): for example M x y b, K name, T text, one line each. A ring in ivshmem is the faster option later.
  3. A host bridge (small Python or Rust process holding both the QEMU socket 4555 and a websocket or TCP to kosmos-app --serve-port 5878) maps events to steps and sends {"t":"editor.event","steps":"..."}. - A press and release without movement maps to click@x,y, or to click:Label when the tree gives a unique hit (more robust). - Press, moves and release map to drag@x1,y1>x2,y2>.... Drags are batched at release, so there is no live orbit while holding the button. A true live drag needs a down/move/up step type (unverified whether script.rs has one; the grammar seen has only atomic drag@). - Keys map to key:cmd+z and type:text; hover maps to hover@x,y.
  4. The reply {ran, log} then triggers editor.tree to refresh. Alternatively kosmos-mcp can be driven by an agent in parallel on the same socket (one editor client at a time; unverified for multiple concurrent clients on --serve-port). - Latency estimate, unverified: serial event to bridge below 10 ms; editor.event plus a fresh frame in the live window is the unknown, and the skill notes a 5 s reply window and a slow first event.

5. Smallest demo (recommended)#

Goal: the editor's real widget tree, drawn in a TempleOS window in the Desk2 style, with click-through to the real editor, plus one still viewport image.

Steps and effort:

  1. Host: start KOSMOS_EDITOR=1 KOSMOS_SPLASH=0 KOSMOS_TITLE=0 kosmos-app --serve-port 5878 (from .claude/skills/drive-window/SKILL.md), or --serve-editor for headless. 0.25 day.
  2. Bridge tools/templeos-bridge (or a script under apps/templeos-holyc/scripts, Python 3): call editor.tree, scale rects into a 640x400 box, pack a compact binary or line text format (role code, rect as 16-bit ints, flags, label), diff against the previous tree and write deltas to the QEMU serial socket. 1 day.
  3. Spike the serial: write a streaming guest drain (no acks, FIFO on, bounded loop) in spike/ and measure bytes per second with the desktop running. 0.5 day. Gate: at least 20 KB/s, else send the tree once on demand.
  4. Guest: new AppKosmos window (replacing or beside AppViewport, KsDesk2.HC line 609) that holds the parsed widgets in arrays and draws them with existing primitives by role. 2 days.
  5. Viewport: bridge reads the PNG at the editor.shot path, crops the viewport rect, quantises to 4 bpp, sends one still over serial (128 KB, about 90 s at today's rate, faster after step 3) or through ivshmem if that spike passes. 1 day plus 1 day for the ivshmem spike (optional).
  6. Input: guest sends click and key lines; the bridge turns them into editor.event and re-sends the tree. 1 day.
  7. Capture screenshots into apps/templeos-holyc/shots/. 0.25 day.

Total about 5 to 6 days for a first-pass demo, about 3 days if the viewport still and ivshmem are dropped. A smaller first proof of 1 day: read-only, one editor.tree snapshot as a text file sent with the existing loader, drawn as labelled boxes.

6. Blockers, unknowns, constraints#

  • Licence. The workspace is MIT OR Apache-2.0 (Cargo.toml line 109). TempleOS is public domain (not verified here). The Inter font in the guest is SIL OFL (README.md). apps/os-styles/kamiji-ui is "local prototyping only: do not publish it" (PROVENANCE.md). None block this work.
  • Plan constraints. Do not start phase work before the go gate (rust-engine.md §1.5, lines 86 to 97). The gate is already ticked go on 2026-10-15 (line 1475), so the engine track is open, but the protocol and apps/kosmos-app changes are engine work. The bridge and guest code live in this repo's apps/templeos-holyc and are not on a phase card.
  • §8.6 questions the user must answer (line 1278): none are triggered by a read-only bridge in apps/templeos-holyc. They would be triggered by adding a runtime dependency with a non-allowed licence, a required CI check, deploying, or a pre-release crate (rust-engine.md §8.7 line 1285 lists winit 0.31 beta and wasmtime rc as not to use). Using Python or QEMU on the host adds no workspace crate.
  • Protected paths (docs/agents/recipes.md lines 55 to 57, docs/agents/verifier.md line 16): .github/, deny.toml, Cargo.lock, rust-toolchain.toml. The demo needs none. The HUD files (apps/kosmos-app/src/hud*.rs, assets/hud/) are owned by the HUD session (rust-engine.md line 1305). A new editor.frame request would be a protocol change; ask first.
  • Base branch and repo rules: branch from local proto, not main; Yakopop must not receive kosmos-* crates (CLAUDE.md). Current branch is task/templeos-shell.
  • Unverified (not measured or read):
  • guest serial drain rate without acks;
  • ivshmem BAR placement and TempleOS mapping;
  • real editor.tree size and widget count for the editor;
  • latency of editor.event and editor.shot on the live window;
  • whether the step grammar has separate mouse-down and mouse-up for a live drag;
  • whether --serve-port accepts a second concurrent client;
  • TempleOS paging identity mapping above 4 GB;
  • gdbstub write behaviour on a running VM.
  • Product risks. The tree is a lossy view of the editor (custom-painted canvases vanish), the guest is TCG-slow (30 to 40 ms frames at 1440x900, README.md), and the wasm or kosmos-web route (docs/plans/os-frame.md "Later") remains the cleaner way to run the engine itself in a browser desktop. The guest can never be the engine host.

7. Recommendation#

Build the hybrid. Draw the editor chrome natively in HolyC from editor.tree, driven over the existing serial link with deltas, and feed editor.event from guest input through a small host bridge. Add a viewport pixel stream through ivshmem only after a one-day spike proves it. Start with the read-only tree mirror demo in section 5, because it needs no change to kosmos-app, kosmos-protocol or the HUD code, and it proves the hardest question (does the tree look right in the desktop's styles) first.
