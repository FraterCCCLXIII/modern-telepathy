Kosmos OS foundation: apps that run normally, no capture

Edited 2026-10-27docs/os-foundation-plan.md

Written 2026-10-27 after the Electron and Tauri research. Facts marked (verify) are from memory or docs and have not been tried here.

The principle#

Electron and Tauri apps do not need pixels forwarded; they need an operating system that provides the contracts they were built for: a Linux kernel interface, a C library, a Wayland display server, D-Bus, an audio server, XDG portals, and a package and sandbox format. So the foundation is a real OS that provides those contracts, with our shell as its desktop environment. We implement the platform instead of imitating an app's output. TempleOS cannot provide these contracts (no libc, threads, network stack, GPU or audio), so it stops being the base. Everything we have built for look and feel carries over.

Options considered#

Base Runs Electron and Tauri natively Cost of the contracts Verdict
TempleOS plus our own drivers no years: TCP, TLS, USB, virtio, libc, threads, a browser engine rejected
Redox OS (Rust) no, Chromium is not ported (verify) high rejected
Android or Fuchsia not Electron or Tauri high, and a different app model rejected
A shell app on macOS (Electron or Tauri itself) yes, but it is not an OS low a useful stepping stone for UI work, not the foundation
Linux with our own Wayland compositor and shell yes, unmodified apps low: the contracts already exist chosen

Build on an existing distribution (Debian, Fedora, Arch or NixOS on arm64 and x86-64) and replace only the desktop layer. Do not build a distribution from scratch: security updates and hardware support are a full-time job.

Layers#

The shell#

Recommended: a compositor on Smithay (Rust, MIT (verify)), which matches the Rust stack in this repo. Alternatives: wlroots (C, MIT), forking COSMIC (Rust, GPL-3.0, so a licence decision (verify)), or a GNOME Shell or KDE plugin (least control). Rendering must work without a GPU, because VMs on this Mac have no usable GL (see below): use Smithay's software and GLES renderers over llvmpipe (verify), and keep the shell UI cheap. Our UI layer options: the engine's wgpu renderer, a Rust toolkit (iced or Slint), or HTML through a system web view. Pick by a small spike (the shell needs a menubar, dock, launcher, settings and notifications, not a general toolkit).

Protocols the compositor must implement for apps to behave normally: xdg-shell (windows), xdg-decoration (our server-side titlebars), layer-shell (menubar and dock), wl-seat with pointer, keyboard, touch, relative-pointer and pointer-constraints, fractional-scale and viewporter (retina), linux-dmabuf and wp-presentation-time, data-device and primary-selection (clipboard, drag and drop), text-input-v3 and input-method (IME), xdg-activation, idle-inhibit, screencopy or image-capture for screenshots, XWayland for legacy apps.

The app platform#

  • Flatpak plus portals. One sandboxed packaging format gives access to Flathub's Electron and Tauri apps (VS Code, Obsidian, Slack, Discord, Signal, Element and more are published there (verify each)), with permissions that match our approval model.
  • Electron runs on Wayland through Ozone (verify the flags and version). Tauri uses WebKitGTK on Linux (verify Tauri 2 packages).
  • First-party apps are Tauri apps built with the Kamiji (Longformer) components and tokens, so system apps and the shell share one design language. Settings, Files, Notes, Terminal and the store are the first ones.
  • Security: every app is sandboxed by default; credentials live in a system keyring; outward actions (sending mail or messages, purchases) always need an explicit user prompt.

What carries over from the HolyC desktop#

Design tokens and the five styles, the Inter and Lucide assets, the window chrome kinds (traffic lights, caption buttons, glass), the dock and menubar behaviour, the Settings structure, the core-apps list, and the animation timings. The HolyC desktop stays as the "Temple" skin reference and as a TempleOS app (TempleOS runs in a QEMU window as one app, with HolyC available as a feature), not as the foundation.

This Mac as the development host#

Checked on 2026-10-27: Apple Silicon (arm64, macOS 27), Homebrew qemu-system-aarch64 with HVF acceleration (guest runs at native speed), Lima and Docker present, 41 GB free. This QEMU build lists virtio-gpu-pci but no GL variant, so a Linux guest would render in software (llvmpipe), which is fine for a shell and for Electron and Tauri apps at normal speed (verify the frame rates in M0). Apple's Virtualization.framework through Lima is the quickest start; a QEMU HVF image is the more controllable one. The real target hardware (an Apple Silicon Mac with Asahi, a PC, a Pi, a VM product) is a decision for the user and affects GPU and driver work.

Milestones, each with a pass or fail gate#

M What Gate Time box
M0 A Linux arm64 VM (Lima or QEMU HVF) running a stock Wayland compositor (sway or cage) with one Electron app and one Tauri app launched natively. Needs downloads: a distro image of a few hundred MB and the apps. both apps run as real windows, typing and scrolling feel normal, 30 fps or better scrolling in software rendering 2 days
M1 kosmos-shell v0: a Smithay compositor with xdg-shell, layer-shell menubar and dock placeholders, our server-side titlebars, pointer and keyboard, and the same two apps same apps, same gates, windows drag and resize, our chrome 1 week
M2 fractional-scale (retina), clipboard and drag and drop, IME, dmabuf, activation, XWayland copy and paste between apps, crisp text at 2x 1 week
M3 Portals backend (file chooser, notifications, screenshots), PipeWire audio, NetworkManager panel a Flatpak app opens files and plays sound 1 to 2 weeks
M4 Flatpak store UI, first-party Tauri apps with Kamiji (Settings, Files), launcher install and run an app from the store inside our shell 2 weeks
M5 Reproducible image build, installer, updates boots from a clean image; update works 2 weeks

Risks and decisions for the user#

  1. Target hardware and GPU: software rendering is acceptable in a VM, real hardware needs a driver story.
  2. Licence: COSMIC is GPL-3.0; Smithay and wlroots are MIT (verify). Decide before forking anything.
  3. Scope and ownership: a desktop environment is a long project; the repo rules (CLAUDE.md) and plan section 8.6 apply, and starting new phase work needs the user's go.
  4. Maintenance: a distribution base means tracking its security updates.
  5. Where this lives in the repo: a new directory (for example apps/kosmos-os/) once approved.

What we stop doing#

No more screen capture or pixel streaming into TempleOS as the app route, no shared-RAM bridge spike, no further HolyC apps beyond the reference skin. The two research reports remain as the record of why.
