KSFONT2.BIN, font file format v2 (2026-10-27)

Edited 2026-10-27docs/font-format-v2.md

Host side done, guest side is phase 2. Files: scripts/gen-font2.py (writer), scripts/font2_ref.py (reader and specimen renderer), scripts/ks-utf8.py (text to literal), tests/fonts/test_font2.py, assets/fonts/ (sources and OFL text), shots/fonts-*.png. v1 (KSFONT.BIN, gen-font.py) is untouched and stays the file the desk loads until phase 2.

File layout (little endian, every table 4-byte aligned, offsets from the start of the file)#

Part Bytes Content
Header 32 "KSF2", U16 major (2), U16 minor (0), U32 file size, U32 face count, U32 face dir offset (32), U32 face entry size (64), U32 flags (bit n set = tier n present), U32 CRC-32 of bytes 32 to the end
Face dir 64 each U8 ascent, descent, line gap, line height (= sum), px size, family (0 Inter), role (0 REG, 1 BOLD, 2 SMALL, 3 BIG), scale (1 or 2); U16 weight, U16 flags (bit0 has kerning); U32 range table offset, range count, record offset, record count, pixel blob offset, pixel blob length, kern offset, kern count, expanded bytes (2 x pixel length); char[16] name
Range table 24 each U32 first code point, count, glyph index base, pixel offset of the slice (in the face blob), slice length, tier
Glyph records 12 each U16 advance (1/16 px), U8 w, U8 h, I8 bearing x, I8 bearing y (up from the baseline), U16 flags (bit0: this character has kerning pairs as the left one), U32 pixel offset (bytes, from the face blob start)
Kern pairs 4 each U16 key = (left << 8) or right, I16 value (1/16 px), sorted by key; code points below 256 only
Pixels per face 4-bit alpha, two per byte, high nibble first, each glyph padded to a whole byte, rows back to back (exactly the v1 data)

Rules. The face index is role + (scale - 1) * 4, so the eight faces are v1's, in v1's order (Regular 13, Bold 13, Regular 11, Bold 22, then at scale 2 Regular 26, Bold 26, Regular 22, Bold 44); more faces append (a reader sizes its arrays from the count, 16 is plenty). Range 0 is U+0020 to U+007E (base 0), range 1 is U+00A0 to U+00FF (base 95), every face has the same ranges, ranges are sorted and never overlap. A code point inside a range that the font lacks has a record with advance 0 and w 0 ("absent"); a space has advance above 0 and w 0. A new minor version only adds fields at the end of an entry (read by the entry size); a new major version changes the magic number's meaning, so refuse it. Tier: 0 resident (set A), 1 Latin Extended-A, Greek, Cyrillic (set B), 2 Vietnamese (set C). Kerning comes from the GPOS kern feature of Inter (class and pair tables), scaled to the face size, kept when it moves at least half a pixel, ASCII only (--kern latin1 adds the accented capitals and lower-case letters: B grows to 677,080 bytes, 40,556 more, for pairs their base letters mostly already have). No kern in v1 means v1 text is a little wider than v2 text.

Guest read procedure for phase 2 (replaces FontLoad)#

The pixel offsets already include the range slice, so one gpx per face is enough (the lazy variant keeps one per range, see below). Read the U32 fields with MemCpy on Aiwnios (as v1 does for len) or use the aligned (b+off)(U32*)[i]; every offset is 4-aligned. Initialise len=0 (Aiwnios).

A has 258 glyph slots a face (33 ranges), B 559 (37 ranges), C 654 (41 ranges). C is measured, not estimated. Without kerning the files are 18,308 bytes smaller each (2.9 percent of B); kerning is in (407 to 784 pairs a face, 1.6 to 3.1 KB). v1 for comparison: 85,701 bytes, 159 KB expanded. Expanded totals: A 462,174, B 1,113,786, C 1,375,820. Largest face (Bold 44) pixel data: 225,582 packed bytes in B, which is why v1's U16 offsets cannot hold it.

Guest memory: the VM has 1024 MB and the prompt shows about 799 MiB free; the desk at scale 2 holds up to 5 styles of 2 wallpapers at 20.7 MB (about 207 MB). Set B expanded is 1.1 MB, 0.14 percent of the free heap, so it fits with no lazy loading. Expansion costs 3 ms for 556 KB packed on the x86 VM (the tS clock) and under 1 ms on Aiwnios. The serial copy of the file into the RAM drive (serial-send.py) took 29 s for all 636,524 bytes of set B including 7 s of fixed waits, about 29 KB/s, against about 3 s for v1: a one-off cost per image build. Tiers are in the file so a later change can keep tier 0 resident (462 KB expanded) and expand tiers 1 and 2 on first use: allocate gpx per range, point it at expanded - slice_offset * 2, so gpx + off * 2 is unchanged.

Fonts and licences#

Sources are assets/fonts/Inter-Regular.ttf and Inter-Bold.ttf (Inter 3.019, the two files gen-font.py used from the puter-ui checkout, byte identical: md5 ea587988... and ba74cc32...) with OFL-Inter.txt (SIL OFL 1.1, copyright 2020 The Inter Project Authors; copied from the Inter licence file in the cosmic-text 0.19.0 crate in the cargo registry). Inter is unmodified; the atlas is a rendering of it. Coverage: every code point of the three sets except U+2714 and U+2718 (heavy check and X), which gen-font2.py draws as strokes (VECTOR), U+0149 and U+03A2 (deprecated, unassigned; stored as absent). Inter has U+2713 and U+2717 itself. System fonts with these two glyphs on this Mac (Menlo, Arial Unicode, Zapf Dingbats) are not OFL and were not used.

UTF-8 in HolyC source (tested on TempleOS V5.03 in QEMU and on Aiwnios, same results)#

Source stays ASCII; text is UTF-8 bytes; a literal writes each byte as \xHH: "LiberOS \xCE\xB1". Tool: python3 scripts/ks-utf8.py -s 'LiberOS α' --name PRODUCT --check. | Case | Both builds | |---|---| | "\xCE\xB1" | 2 bytes CE B1, StrLen 2 | | \x length | at most two digits: "\xB1A" is B1 41, "\xCEabc" is CE 61 62 63 | | adjacent literals "\xCE\xB1" "x" | joined, 3 bytes | | \d or \x24 | the dollar sign (needed for DolDoc safety) | | octal "\316\261" and "\u03B1" | not escapes, no error: the text stays as backslash and digits (8 and 6 bytes). Never use them | | StrLen, StrCpy, MemCpy, StrNew, StrPrint %s | bytes above 0x7F survive; StrCmp is unsigned | | raw UTF-8 in source (comment or literal) | compiles and survives, but keep it out: editors and DolDoc may rewrite it | | loader: Rx over COM1 | all 256 byte values arrive intact (checked, 0 differences), so the loader does not alter bytes | A DolDoc code does not carry bytes, so it is not used. Traps: U+0000 cannot be in a string; % needs %% when the literal is a Print format (--fmt); a literal in "..." lines, not char constants ('a'); never cut a string inside a sequence (Wrap does, see below).

Decoder contract for Txt, TW, Wrap (phase 2)#

  1. Decode UTF-8 from the U8 string; ASCII (below 0x80) is one byte as today. Lead bytes C2 to DF, E0 to EF, F0 to F4 with 1, 2, 3 continuation bytes; overlong forms, surrogates (U+D800 to DFFF) and values above U+10FFFF are invalid. The reference is utf8_decode in font2_ref.py, tested against Python's errors='replace' on 4,000 random byte strings.
  2. Each invalid or truncated sequence draws one U+FFFD and resumes at the byte that broke it (it consumes the valid prefix, at least one byte).
  3. Code points below U+0020 and U+007F to U+009F draw nothing and have no advance (as v1 skips them). A code point without a glyph draws U+FFFD. Combining marks (U+0300 block) are out of scope: they have no glyph and draw U+FFFD, so text must be NFC (the host does unicodedata.normalize).
  4. Pen position in 1/16 px; TW runs the same decode and kerning as Txt, so widths match. Wrap breaks only at a space byte and must never cut inside a sequence: where it limits a line to 190 bytes, step back over bytes 0x80 to 0xBF and the lead byte. CW takes a code point. Notes keeps bytes; caret and delete step over a whole sequence (optional in phase 2).
