HolyC-native apps, including a web browser

Edited 2026-10-27docs/holyc-native-apps-plan.md

Written 2026-10-27, after choosing TempleOS as the base. This replaces the screen-capture route in the earlier research and supersedes os-foundation-plan.md for this direction. Facts marked (verify) are from memory and untested here.

What "native" means here#

An app is HolyC code that draws with our renderer (desk3/), receives our input, and gets anything the guest cannot do (network, TLS, audio, persistence, an AI model) from a small number of well-defined services. No pixels are captured from another program. The honest limit is that the guest has no network stack, no TLS, no image or font libraries and no JavaScript engine; each is either built in HolyC or provided by a host service behind a clean protocol. Anything that needs a modern JavaScript web platform (Gmail, YouTube, Slack, VS Code) is out of reach for a native browser, whatever we do. The browser targets the document web: articles, docs, wikis, blogs, search results, forums, repos, feeds.

Two ways to get bytes from the web#

  1. Host fetch service (first). The Mac fetches the page (HTTP, TLS, redirects, cookies, compression), and the guest asks for it by URL. Small, fast to build, and TLS and certificate handling stay on the host. The guest never sees credentials or TLS keys.
  2. Native network stack (long term, optional). A driver for a QEMU NIC (RTL8139 or E1000, a few hundred to a thousand lines), then ARP, IP, UDP, DHCP, DNS, TCP, and TLS 1.3 (X25519, AES-GCM or ChaCha20, SHA-256, certificate chain checks with a bundled root store). TempleOS has none of it, and its original charter rejects networking, so this is new ground; plain HTTP is the achievable first milestone, TLS is several weeks on its own (verify speed under emulation: a handshake is millions of 64-bit multiplications). It would make the OS genuinely self-contained and give every app sockets.

Recommendation: build the host fetch service first so the browser exists soon, with the browser written against an internal "fetch(url)" interface so the native stack can replace the host later without touching the engine.

The browser, in layers#

Layer What it does Notes Size
Chrome tabs, URL and search bar, back and forward, reload, bookmarks, history, find in page, downloads, reader mode toggle uses widget kit v2 M
HTML tokenizer and a simplified tree builder, entities, a decent subset of elements, forgiving of bad markup no need for the full HTML5 error-recovery tables at first M
CSS parser, selectors (type, class, id, descendant, child, attribute, common pseudo-classes), cascade and specificity, inheritance, the common properties (display, color, background, font, margin, padding, border, width, height, text-align, line-height, overflow, position basics, list-style) the most work per feature L
Layout block and inline formatting, line breaking, lists, tables, floats, simple flexbox, images, forms a faithful box model L
Paint our renderer: anti-aliased rounded borders, backgrounds, shadows, text with the glyph service, images, links with hover already largely exists M
Interaction links, scrolling, text selection and copy, find, form fields and submit needs the text field widget M
Reader mode extract the main content (Readability-like heuristics, in HolyC or on the host), render with our typography gives the best result on article pages with the least code, so build it first S to M
Other protocols Gemini, Gopher, RSS and Atom, Markdown and our own docs, TempleOS DolDoc small, native, fit the OS S each
JavaScript none at first; later a small ES5-class interpreter (port mujs-sized code, about 20k lines of C, or write one) with a minimal DOM even then, most modern sites break; decide only after the document web works L to XL

Expected coverage with no JavaScript: Wikipedia, documentation sites, blogs, news articles (often via reader mode), Hacker News, most forums' HTML versions, GitHub README pages, search engines' lightweight pages, feeds. Not covered: web apps and anything that renders client side. If broader coverage is ever required, the clean fallback is a host-side headless browser that sends a display list (positioned text runs, boxes and images) for the guest to paint natively and crisply, with events sent back. That is rendering, not screen capture, but it reintroduces a host dependency, so treat it as an optional mode.

The other apps, in the same style#

App Native part Service part
Text editor and code editor gap buffer, selection, undo, syntax colouring, run HolyC with errors, find and replace file service for saves
Terminal HolyC REPL, history, completion none
Email list, reader, compose, HTML-to-text host IMAP and SMTP service (Himalaya or similar), tokens kept on the host
Messenger conversation list, bubbles, composer, toasts host Matrix or Signal bridge
Music player library, queue, art, visualiser host playback (mpd or mpv); TempleOS cannot play real audio without a sound driver
AI IDE native editor, diff, chat and approval panels host agent with explicit approval for every write and command
Files, Notes, Calculator, Monitor, Settings, Paint, Image viewer, Docs viewer, Calendar all native file service for persistence

Rule for every service-backed app: nothing is sent, deleted or purchased without an explicit prompt in the UI.

Order of work and gates#

  1. Channel spike (2 days). Gate: at least 50 KB/s sustained from host to guest and 20 KB/s back, no corruption over 10 MB.
  2. Framework and widget kit v2 (about 2 weeks). Gate: a text field, list and tab strip used by at least two apps.
  3. Host services v0: file, fetch. (3 days). Gate: the guest saves a note and fetches a page.
  4. Browser B0: chrome plus reader mode on the fetch service. (1 week). Gate: five chosen article URLs render legibly at 2x.
  5. Browser B1: native HTML and CSS subset, images, fonts. (3 to 5 weeks). Gate: a fixed set of 20 pages (Wikipedia, MDN, a blog, HN, a GitHub README) lay out without overlap and with correct links.
  6. Editor, terminal, code editor in parallel with B1, then Files completion, Paint, image viewer, docs viewer.
  7. Email and messenger on the host services, after a review of accounts and approval flows with the user.
  8. Native network stack track (RTL8139 or E1000, IP, TCP, then TLS), only if self-containment is wanted; swap in behind fetch.

Risks#

  • HolyC speed under emulation: layout and CSS cascade on large pages can be slow; budget parse and layout per page and stream results in.
  • CSS volume: scope by a fixed conformance page set, not by the spec.
  • No JavaScript is a hard ceiling on coverage; say so in the UI (a reader-mode and "open on the host" escape).
  • The mouse, keyboard and clipboard paths are still hacks in the guest (relative-mouse workaround, no key-up, no non-ASCII); fix them in the framework step.
  • Persistence depends on the channel spike.
