ArtCraft Crafting Apps on the HolyC TempleOS desktop: feasibility study

Edited 2026-10-27docs/artcraft-apps-on-templeos.md

Date 2026-10-27, branch task/templeos-shell. Research only: nothing was cloned, downloaded or run; everything below comes from web pages, the GitHub API and raw.githubusercontent.com files read today.

Labels: [V] read or fetched today (source named). [R] measured in our repo's earlier notes (cited). [M] memory, inference or estimate, not checked. Effort sizes (S, M, L) are [M].

1. Answer#

  • Do not run the Crafting Apps as windows in the desktop as the main plan. The best fit is R3: use the headless *-cli binaries (and their stdio MCP servers) as host services behind our hub, feeding our own HolyC UIs: GridCraft for xlsx/xlsb/ods import, export and a formula oracle; PdfCraft for page render, text and page organise; WordCraft and DeckCraft for docx/odt/pptx conversion and page PNGs. Each CLI is a single local process with no network need [V].
  • The second route is R2: the WebAssembly builds in headless Chrome under appd, shown as tiles. All are egui canvases, so tiles are the only route; it works with infrastructure we already have, but is slow over serial and mostly gives us the apps' own UI rather than our native look.
  • R1 (native window streaming) is possible without Screen Recording because the apps expose ui.screenshot and input calls over a JSON channel, but it has no advantage over R2 for us. R5 (Rust staticlib inside Aiwnios) is real but later. R4 (no_std to a .BIN) is blocked by std, alloc, chrono and regex. R6 (port to HolyC) is rejected.
  • Handle with care: the projects are weeks old and move extremely fast (section 2.1). Pin a release by SHA-256, expect breakage, and make no plan depend on a single version.
  • Day-one prototype: GridCraft CLI behind the hub (needs one 11.7 MB approved download). An optional hour-long R2 tile test with the 7.7 MB GridCraft web zip.

2.2 Stack (GridCraft in detail, others from READMEs)#

  • Workspace layers (enforced by cargo xtask layers) [V] architecture.md: L0 core (cell addresses up to 1,048,576 x 16,384, values, errors, date serials), numfmt; L1 formula (tokenizer, parser, A1/R1C1), functions (513 worksheet functions listed, per the README's own caveat a parity inventory); L2 model, calc, xlsx (XLSX/CSV/TSV, XLSB and ODS import, pivot caches, DrawingML charts); pdf (small PDF 1.7 writer); L3 chart; L5 engine (Session, 313 commands through Session::execute(id, params)); L6 ui-egui, mcp; L7 gridcraft, gridcraft-cli, gridcraft-web.
  • Nothing below L6 depends on egui, eframe, winit or rfd [V]. This is the key fact for R3.
  • Dependencies of the core crates [V] Cargo.toml files: gridcraft-core = serde, thiserror, chrono (std), js-sys on wasm32; gridcraft-formula = core, serde, thiserror; gridcraft-functions = core, regex; gridcraft-calc = core, formula, functions, numfmt, model, log; gridcraft-engine = those plus serde_json, xlsx, chart, pdf, image. Workspace root also has rayon, quick-xml, zip, sha1/sha2/aes (encrypted workbooks), skrifa. unsafe_code = "forbid" workspace-wide.
  • Threads: calc is single-threaded (listed as a known gap) [V]. VectorCraft and DesignCraft render multithreaded on CPU (vello_cpu) [V].
  • UI and renderer: egui 0.37 / eframe 0.37 on wgpu (Metal, Vulkan, DX12, WebGPU), winit via a storytold fork [V]. Variations: WordCraft and DesignCraft rasterise pages with vello_cpu and use the GPU only for UI compositing [V]; PhotoCraft has a CPU reference compositor and a wgpu one [V]; FigCraft uses tiny-skia with HarfRust/skrifa [V]; PdfCraft draws pages with the third-party hayro crate while its own pdfcraft-render is built [V]; FilmCraft and LightCraft use wgpu compute with CPU fallback [V]. No Skia, no iced.
  • File formats [V]: GridCraft xlsx r/w, xlsb/ods import, csv/tsv, json/html export. WordCraft docx/odt/rtf/html/md/tex/txt r/w, .doc read, PDF export. DeckCraft pptx r/w, PDF/PNG/JPEG/GIF export. PdfCraft PDF (own COS layer, 33 crates). PhotoCraft PSD/PSB/layered TIFF/ORA r/w and many flat formats. VectorCraft SVG, PDF/AI, EPS, DXF. CADCraft DXF and DWG, SVG/PNG/PDF out. SoundCraft WAV/AIFF/FLAC r/w, MP3/Ogg/AAC in.
  • WebAssembly build [V]: apps/<app>-web, trunk build --release, eframe + wgpu (WebGPU with WebGL2 fallback), wasm-bindgen, web-sys, one <canvas>; open uses the browser file picker and save downloads a file. Shipped as a static zip: GridCraft web 7,660,730 B, PdfCraft web 15,961,263 B [V]. Uncompressed .wasm sizes reported by a third-party review: PhotoCraft 24.2 MB, PdfCraft 37.9 MB [V search result, secondary source]. No hosted URL: you self-host the zip [V search result, apps page lists none]. DesignCraft's web build has no control channel [V].
  • Windowing/threading: winit fork, one UI thread plus app-specific workers [M].

2.3 CLI, control channel and MCP#

  • CLI (GridCraft) [V] cli.md: info, convert (xlsx/csv/tsv/json/html by extension), eval, cat, check (accuracy and round trip, JSON schema gridcraft-check/1), run (repeatable --cmd 'id={json}', scripts), commands --json, functions --json, mcp, send <port> <method>. No PNG or PDF export is documented for GridCraft headless.
  • Other CLIs [V]: PdfCraft info text edit combine extract split run tools ui mcp; WordCraft convert text inspect run mcp (PNG page images via convert); DeckCraft render --all (headless slide PNGs), mcp; SoundCraft run --bounce (WAV/AIFF/FLAC with LUFS report); VectorCraft run --export; DesignCraft run --all-pages out/; FigCraft render export run; EffectCraft render --comp Main --out main.mp4; CADCraft info convert run commands mcp.
  • Control channel (desktop app only) [V] control-protocol.md: plain TCP on 127.0.0.1:<port> (--control), newline-delimited JSON {id, method, params}; mandatory 256-bit token, either from GRIDCRAFT_CONTROL_TOKEN or a 0600 file in a 0700 directory; first line must be auth within 10 s. Methods include engine.execute, engine.commands, sheet.read, cell.get, ui.click/drag/move, ui.key/text, ui.dialog*, ui.resize, ui.screenshot (PNG, base64 or to a path, 8 s timeout, 64 MiB reply cap), app.open/save/quit. PdfCraft's variant is off by default and takes a control file with the token; it refuses symlinked or shared files [V].
  • MCP [V] mcp.md: hand-written JSON-RPC over stdio; GridCraft has 22 tools (read_range, write_range, evaluate_formula, insert_chart, sort_range, execute_command, screenshot in remote mode). Headless mode uses an in-process session with no window and no documented network use. PdfCraft MCP: render_preview(page, max_side<=4096), text_extract, doc_combine, doc_split, page_extract, command_run, plus --root, --automation-read-root, --automation-write-root path confinement, symlinks resolved [V]. MCP stdio plus a roots flag is exactly the shape our hub wants.

3. Routes into TempleOS (question 2)#

Relevant measurements from our own notes [R] (web-apps.md, electron-apps.md, browser-architecture.md): host-side type-to-new-display-list p50 17 ms; screenshot 600x400 PNG 35 ms, 900x600 JPEG 28 ms; the guest has no JPEG decoder, so tiles use palette/RLE rects with 16-row strip diffs; raw 900x600 RGB565 is 1.08 MB (23 s at 47 KB/s); serial 16 to 47 KB/s (16.3 end to end measured, 47 reported); Aiwnios has native sockets; second-tab input needed Page.bringToFront (5 s to 17 ms); about 129 MB of Chrome per extra app tab; hub round trip 18 ms, a 20 KB reply 0.58 s at 34 KB/s [V weather-music-status.md].

R1. Native app on the Mac, stream its window. Mechanics without Screen Recording: start the app with --control <port>, read the token file, then loop ui.screenshot (PNG), diff in our 16-row strips (the apps send no dirty rects), and forward guest mouse/keys as ui.click, ui.drag, ui.key, ui.text in window points (so no coordinate mapping error), with ui.resize to match the guest window. Costs: a real window on the user's Mac that must stay visible (minimised windows queue captures) [V]; each frame is a full render plus GPU readback plus PNG plus base64 over JSON, which I estimate at 50 to 150 ms [M]; a visible GUI process outside appd's CDP controls; sandbox-exec around a GUI app is awkward [M]. Effort M. Verdict: works, but strictly dominated by R2 for apps that have a web build.

R2. WASM build in headless Chrome under appd, tiles. Fit: the egui canvas is pixels, so display lists cannot express it; tiles are the only route [V: egui draws one canvas; R: tiles are the labelled fallback]. Plan: appd serves the zip on loopback, kind web, render: "tiles", the existing stream.py strip diff and RLE, input via Input.dispatchMouseEvent/KeyEvent with CSS px = surface px (DSF 1), focus emulation fix from the Electron work. Unknowns [M]: whether headless Chrome 156 on this Mac gives eframe a WebGPU or WebGL2 context (both are claimed fallbacks [V], not tested); egui IME and clipboard through its hidden text input; wasm load time (PdfCraft 38 MB uncompressed). Latency estimate: host side 50 to 150 ms; over serial a full first frame may be 30 to 120 KB of RLE (about 1 to 3 s at 47 KB/s) and later deltas a few KB (about 100 to 300 ms); over an Aiwnios socket close to host cost. Good for demos and for tools whose value is the UI itself (PhotoCraft, VectorCraft, FigCraft, PdfCraft). Effort S to M, since appd and stream.py exist. Canvas apps are the only kind that have no alternative.

R3. Core as host service behind the hub. The hub already does REQ/RES/APPROVE with a 20 KB reply in 0.58 s [R]. Each service is a child process of the CLI. Two protocols are available: one-shot CLI commands with --json (GridCraft eval --json, info --json, convert), or a long-lived stdio MCP session (GridCraft 22 tools, PdfCraft render_preview) confined with --root. Separability from the UI is verified in the manifests for GridCraft, PdfCraft and the layering claims of WordCraft, SoundCraft, VectorCraft, DesignCraft, CADCraft, FigCraft, FilmCraft [V]. Cost: start-up per call for one-shots (not measured [M]), process memory, a JSON-RPC client in hostd.py (about 150 lines [M]). Effort S per service. Caveat: payloads are PNG or text, and the guest cannot decode PNG, so page images must be re-encoded on the host into our RLE/RGB565 image path (the browser already does this for IMAGE ops [S: browser-architecture.md]).

R4. Core crates as no_std x86-64 .BIN. Proven so far is only a no_std, no-alloc blob with SSE2 (engine-on-templeos.md, 25x slower than native under TCG) [R]. The candidate crates are not that: gridcraft-core pulls chrono with std; functions pulls regex with std, unicode, perf; serde, Arc copy-on-write bands, and String all need alloc; PdfCraft needs image, icu_properties, url and filesystem-free but allocation-heavy parsers. gridcraft-formula (core + serde + thiserror) is the most plausible, with alloc, if chrono is isolated behind a feature. Blockers: no allocator story in the proven spike (needs a bump allocator or MAlloc import), libm for transcendentals, regex replacement, TCG speed, upstream churn (a weekly 0.x release stream will not stay compatible with a fork). Effort L for formula only, XL for engine. Rejected for now.

R5. Rust staticlib with a C ABI, linked into Aiwnios. Wrap gridcraft-engine in a 100-line crate-type = ["staticlib"] shim (gc_open, gc_execute(json) -> json, gc_free), build with rustc 1.95 or later, register the symbols with PrsAddSymbol as aiwnios/README.md describes [S]. No serial hop, so edits answer in microseconds; Session::execute already restores state on a panic [V]. But it exists on the arm64 Aiwnios build only; the x86 TempleOS guest cannot load it, which breaks the single-source rule of desk3/0*.HC [S]. Effort M. Rank it after R3, as an optimisation of the same service API if hub latency proves too high for interactive recalculation.

R6. Port to HolyC. Rejected. GridCraft alone is 8.1 MB of Rust source with 313 commands and 513 listed functions [V]; our spreadsheets plan scopes a calculator-grade P0/P1/P2 of about 60 functions in HolyC [S: spreadsheets.md]. HolyC has no generics, no iterators, no JSON, a stack-ABI and x87 float; the upstream changes weekly; XL and permanent.

Ranking: R3 > R2 > R5 > R1 > R4 > R6. R1 and R5 swap places if the user wants the apps' own UI (R1) versus speed (R5): for the stated aim (spreadsheet, slides, docs, PDF, image, music, design tools) the services in R3 give more value for less cost.

5. Reuse as spec, code, or build ourselves (question 4)#

Reuse as spec (zero risk, high value). gridcraft-cli functions --json and commands --json give a machine-readable list of 513 functions and 313 commands; docs/function-parity.md (17.8 KB), file-format-parity.md (31.3 KB) and parity-checklist.md exist in the repo and can be read by the spreadsheet plan's P0/P1/P2 lists. PdfCraft's pdf-spec-parity.md, WordCraft's 422-command catalog and DeckCraft's 200+ commands play the same role for PDF viewer, Docs and Slides.

Reuse as code (host side only). - Replace IronCalc as the first-choice oracle and host converter in docs/apps/spreadsheets.md section 8 with GridCraft: it reads xlsx, xlsb and ods, writes xlsx/csv/tsv/json/html, and has a check accuracy runner. Keep IronCalc and calamine as a second opinion; HyperFormula stays blocked (GPLv3) [S]. - In docs/apps/slides.md, python-pptx and pptxgenjs can drop to fallback status once DeckCraft's pptx round trip is checked; its render --all gives slide PNGs the plan did not have. - For Docs, WordCraft's convert covers docx/odt/rtf/md/tex import and PDF export that nothing in the current plan does. - LibreOffice stays the outside-reference oracle; the plans call it "never linked" [S].

Build ourselves. The HolyC grid editing, native recalculation for sub-30 ms edits (the spreadsheet plan's budget), our window chrome, and the approvals UI. Interactive latency over the hub is unmeasured (one-shot CLI start-up times are not known [M]), so the native engine stays the P0 plan; the hub engine becomes import/export and oracle.

What we can drop. The converter choice among SheetJS, openpyxl, calamine (if GridCraft's reader passes our corpus), a custom pptx text-run importer, and any plan to port a PDF reader. We keep sound playback (host afplay, already built).

6. Security and privacy (question 5)#

  • What the apps send where. The READMEs of PdfCraft and PhotoCraft claim no AI features, no telemetry and no network at runtime for documents: PdfCraft "no account, no telemetry, no cloud" [V]. FigCraft contacts no server until a user shares; sharing uploads to collab.craftapps.dev by default, unencrypted at rest [V]. GridCraft's page makes no privacy claim; its only AI claim is agent-driven automation through MCP/CLI/JSON [V]. The AI layer lives in craft-ai-integrations ("first draft", 111 stars): OpenAI-compatible APIs, Black Forest Labs, Vertex Gemini, BytePlus Seedance, "ArtCraft Omni API-key route", local ComfyUI and SAM; keys in the OS keychain, an encrypted file or env vars; the README does not say what data goes to each provider and does not mention telemetry; its own test coverage is local mock servers only [V]. The ArtCraft studio itself is a separate AI product with a 62-model catalog [V]. Self-update: craft-update is a dependency of GridCraft and PdfCraft [V]; what it contacts at runtime I did not read [M]. The launcher checks GitHub releases [V].
  • Our approval rules. The hub keeps tokens and keys on the host and grants live in approvals.json [S]. Rules for these services: no network for any ArtCraft child process (macOS sandbox-exec profile with (deny network*), read access limited to the user-approved folder, write access limited to a scratch directory) [M: profile text is mine, untested]; the MCP --root/--automation-*-root flags as the second fence [V]; no craft-ai-* feature ever enabled without its own PROMPT naming the provider and the data; the control channel is never used for services (it is for R1 only), and if used, the token stays on the host.
  • Running untrusted alpha binaries. We never run a downloaded binary without approval. The install flow apps-host/install.py already requires an explicit --sha256, safe extraction, codesign checks and a registry [S]. It handles .app bundles with Electron; a Mach-O CLI kind needs a small addition. The guest dialog must show: name, version tag, source URL, exact file name and size, the SHA-256 from the release's SHA256SUMS.txt and the one we computed, the codesign/notarisation result, the folder it may read, the statement "no network", and Yes/No. On Yes: host downloads, hashes, extracts, runs codesign -dv --verbose=2 and spctl --assess (a notarised DMG is claimed signed and notarised by the launcher README [V]; whether the CLI zip is signed is unverified), stores it under apps/artcraft/<version>/, and records the grant. A SHA-256 taken from the same release proves integrity, not authorship: say so in the dialog. Do not use craft-launcher: it installs into /Applications, may prompt for admin rights, and self-updates [V]. Pin one release, and let updates be a new approval each.
  • Source build instead of binaries. Building runs their build.rs and downloads git dependencies from storytold forks of egui and winit [V]. It needs a clone, which is also approval-gated, and is no safer than a binary. Not recommended.
  • Prompt injection. MCP returns document text; hub rows and tool output are data, never instructions, and an MCP session must not receive guest-supplied instructions as commands [S: hub policy].
