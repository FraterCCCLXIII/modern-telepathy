Slides for the TempleOS desktop (HolyC)

Edited 2026-10-27docs/apps/slides.md

Plan only, no code. Written 2026-10-27 on task/templeos-shell. Companion: spreadsheets.md, which owns the shared infrastructure (section 10 here summarises it). Basis: holyc-native-apps-plan.md, holyc-improvement-analysis.md, aiwnios/README.md, desk3/01-core.HC, 02-ui.HC, and the Kosmos OS sources in section 5. Labels: (V) read or fetched today, (M) from memory, not checked.

1. Purpose and users#

A presentation tool for the desktop: build a short talk from text, shapes, images and tables, present it full screen with speaker notes, and export it. Users: the desktop's author making talks and demos for the TempleOS showcase; people who receive a .pptx from the host and want to view and present it; later, the agent, which writes decks as JSON through a host service.

Out of scope: animation timelines beyond simple builds, master editing in version one, real-time collaboration, embedded video and audio (no audio driver in the guest, per the native-apps plan), and any Unicode text beyond the ASCII fonts.

2. Feature inventory#

Sources: Apple Keynote (support.apple.com/keynote, V for presenter notes and controls in a separate window on Mac, during a video-call presentation; transitions, Magic Move, builds and PowerPoint import are M: that page did not list them). PowerPoint, Google Slides and LibreOffice Impress feature sets are M, not fetched. reveal.js (revealjs.com/speaker-view, V): pressing S opens notes in a second window with the next slide, an elapsed timer and an optional pacing timer. Marp (github.com/marp-team/marp, V): Markdown slides with --- separators, exported to HTML, PDF and PPTX.

3. Architecture decision#

Options for the slide canvas and the document:

  • A. Native. The deck is parsed in HolyC; each slide is painted with the renderer; text is laid out with Wrap; transitions run in HolyC over Copy32 and LerpRow.
  • B. Host-rendered display list. The host lays out the deck and sends positioned runs, boxes and images for the guest to paint (the option the native-apps plan keeps for browsers). It gives exact text but needs a host round trip per slide change and a display-list protocol.
  • C. Host-rendered frames. The host renders each slide to pixels and streams them. Rejected: a full 1920 by 1080 frame is about 8 MB of 32-bit data, far above the serial budget.

Recommendation: A for editing and presenting; B only as an optional later path for complex PowerPoint text. A keeps the same code on the guest and on Aiwnios and needs no network.

Runs natively (HolyC) Runs on the host
Slide paint, shapes via RRFill, Disk, Line, text via Txt and Wrap PNG and JPEG decoding into 32-bit tiles, until a HolyC decoder exists

Presenter mode on one display: the guest has one screen and no second window. Version one shows the presenter layout (current slide, next slide, notes, timer) as a toggled split of the same window. A real second window needs the Aiwnios build and a framework change to its SDL windowing, so it is P2 (L).

4. Data model and file format#

Reuse. Kosmos OS already defines the deck in packages/doc-interop/src/types.ts (V): DeckDoc { version, title, width: 960, height: 540, slides: [{ id, boxes, notes }] }, where a SlideBox has kind (text, image, shape), a box x, y, w, h, content (TipTap JSON for text, a URL or data URL for images), fill, stroke, strokeWidth, color, textAlign, shape (rect, ellipse, triangle, line, diamond) and groupId. The web app (apps/slides/src/App.tsx, V) already has groups, resize handles, slide notes, a slide rail and present mode, so the interaction model is proven.

Gaps for the guest: no tables, charts, layouts or masters; no transitions; text content is a rich tree that is costly to parse in HolyC.

Proposal (additive, version 2).

  • Box kind gains table and chart; a group lists child ids.
  • Integer geometry in canvas units (960 by 540), so layout needs no F64.
  • Text as a flat list of paragraphs, each a list of runs {text, bold, italic, size: 1 or 2, color slot}. The TipTap tree is kept as an import and export form.
  • Slide gains layout (name), transition {kind, ms}, advance (seconds or none), and notes (already present).
  • A theme on the deck: a style index (0 to 4) that selects one of the five desk3 styles' palette, radius and weight.

Guest file. .KSD, one record per line, ASCII only, generated by the host from the JSON:

Interop, realistic subset. The Kosmos OS matrix (packages/doc-interop/FIDELITY.md, V) lists text boxes, shapes and images as supported and tables and charts as partial. Two findings from the code (V):

  • pptx.ts exports with pptxgenjs, which works for the subset, and embeds arco-deck.json in the zip so the Kosmos OS re-import is lossless.
  • The PPTX importer reads only text runs (<a:t>), and places each one at a fixed position (x: 48, y: 48 + i * 64, w: 800). Real positions, shapes and layouts need parsing of ppt/slides/*.xml and the layout parts. This is the L item in section 2, and the host converter (python-pptx, MIT, 1.0.2 uploaded 2024-08-07 (V); its notes and chart support is M) is the cleaner place for it.

ODP follows the same route through the Kosmos OS converter. Realistic in version one: text, shapes, images, notes, slide order, and PPTX import of text and positions. Not realistic: exact master and theme fidelity, animations, morph, and embedded fonts.

6. Security and privacy#

  • No macros, scripts or embedded code. Hyperlinks are shown and never followed on open or during presenting; a link opens only on an explicit click that asks first.
  • Embedded objects, linked media and OLE data are skipped with a placeholder box. Media in PPTX is not extracted.
  • Import caps: input size, slide count, zip entry count and uncompressed size (zip-bomb guard), and text length per box.
  • The converter reads and writes only the guest's B: directory and a host folder the user picks, with validated arguments and no shell interpolation, and no network access.
  • Export to a path, share, or send each need an explicit prompt. Speaker notes are exported only when the user chooses to include them, because the notes are private to the presenter.
  • Images are decoded with size limits (pixel count and bytes) before allocation.

7. UI specification#

Layout follows desk3: a rounded window, a toolbar strip, the slide canvas in the middle, a slide sorter rail on the left, and an inspector on the right.

Presenter layout (Present, then P for the presenter split):

Behaviour: the sorter rail selects slides; drag reorders. Double-click a text box to edit (the text field in section 8). Present mode fills the screen with the current slide scaled to 960 by 540, with no chrome. Transitions run only in present mode and only when the frame budget allows, otherwise they are skipped with no error.

8. Framework needs and gaps#

Present (V): the window, layer and dirty-rectangle system; hit regions; the Button, Toggle, Radio, Slider and Check widgets; Txt, Wrap, TW and LHt; RRFill, Rect, Disk, Line; Copy32, LerpRow, Fill32, BlendSpan; and the Frame and Menubar chrome. The Calculator and Notes apps show the single-buffer text path.

Missing:

  1. A rich text field: caret, selection, bold and size toggles, paragraph breaks, a word-wrapped layout that updates while typing. Shared with the sheets formula bar and cell editor.
  2. Box selection, multi-select, drag and resize with handles, snapping. Only window dragging exists.
  3. A slide sorter: a virtualised vertical list of thumbnails, each a cached paint of a slide.
  4. A full-screen mode and a mode-specific key map that does not fight the desktop's keys (the desktop uses Esc).
  5. An undo stack shared with sheets.
  6. Key-up and modifiers, for Shift-click and held-arrow presenting; see the spreadsheets plan.
  7. A thumbnail cache with invalidation on edit.
  8. Unicode: none in the guest. Smart quotes and dashes must be written as ASCII on import.

9. Shared infrastructure#

Built once and used by spreadsheets.md:

  • Charts: one module for line, bar, pie and scatter, fed by data arrays. Slides store a chart object with a copied data block, not a link.
  • Tables: the same cell model as the grid.
  • Text: the rich text field, Wrap and a width cache.
  • Undo: a bounded command queue.
  • File and converter: one KsExec protocol for import, export and PDF.
  • Palette and styles: the five desk3 styles' 16-slot palettes, used as themes.
  • Image cache: 32-bit tiles decoded on the host.

S7 PDF and HTML export through the host PDF page count and text match the deck; prompts tested

Test plan.

  • Deck render goldens: 20 decks (text sizes, shapes, images, notes, tables) rendered with golden.HC at 1440 by 900 and compared with pxdiff.py, on both targets. Known F64 differences are listed, not failed.
  • Round trips: JSON, .KSD, PPTX (python-pptx read-back of text and positions), Markdown corpus of 20 files.
  • Input: scripted runs of drive.HC for edits, page keys and present mode.
  • Timing: transitions and sorter scroll measured with the improvement analysis benchmark set.

11. Risks#

  • PPTX fidelity: the current Kosmos OS importer is text-only (V). Realistic for version one: text and positions. Mitigation: the host converter with real XML parsing (S4).
  • Transition cost under QEMU: a full-slide crossfade touches about 2 million pixels at 1920 by 1080. Mitigation: transitions at half resolution in the guest, and a measured budget before any promise.
  • Presenter on one screen: the second window is Aiwnios-only at first; a user on the guest gets a split layout.
  • ASCII only: most real talks use non-ASCII text. Accept for version one.
  • Scope: animations and masters are where tools spend their effort. Mitigation: they are P2 and out of the first release.

12. Effort#

Estimate, not measured: S0 to S2 about 4 to 6 weeks of focused HolyC work, dependent on the shared text field and undo from the sheets plan; S3 to S7 about 6 to 8 weeks. Total about 3 to 4 months for one developer. The shared work (text field, undo, charts, converter) is counted in the sheets plan, so the slides increment is smaller if the sheets milestones land first.
