Applications folder: plan

Status: plan, not code. Branch task/templeos-shell. Written 2026-10-27. Read with docs/holyc-native-apps-plan.md (framework step), docs/core-apps-plan.md (Tier 0 launcher and app framework), docs/apps/00-kosmos-os-primitives.md (section 6, the shared model) and docs/apps/music.md and docs/apps/fonts.md (the first two apps this registry must hold).

1. Purpose#

One registry for every app on the desk: the 11 built-in apps, HolyC apps installed from folders, TempleOS programs, and Kosmos OS apps that run on the Mac. One manifest shape, one permission vocabulary, one folder UI. The folder replaces the fixed arrays in desk3, which hard-code the apps today.

2. Features and references#

Feature Reference
Grid of app icons, folders made by dragging one icon onto another, paged Launchpad: grid, folders by drag, Command-Left and Right to move between pages [R] (support.apple.com/guide/mac-pro/apd2d2a58738/2024/mac/15). Launchpad is gone in recent macOS, replaced by a Spotlight apps mode [R, secondary] (macmost.com/how-to-launch-apps-now-that-launchpad-is-gone.html)

3. The current desk (what changes)#

Verified in desk3/:

  • App count: NA 11 [V: 01-core.HC line 26].
  • Per-app arrays: ks_an, ks_acol, ks_aico, ks_aw, ks_ah, ks_fx, ks_fy, ks_dord [V: 02-ui.HC lines 4 to 11]. ks_dord is the dock order.
  • Dispatch by number: AppBody (03-apps.HC, about lines 740 to 754) is an if-chain on a. BodyOf special-cases the browser (06-run.HC lines 9 to 14). AppClick (04-main.HC line 203) is another chain. OpenApp and CloseApp special-case app 9 (04-main.HC lines 58 to 72). Keys: app 4 at lines 408 and 214.
  • Window ids: AID(a) = ID_APP + a*500 [V: 02-ui.HC line 189]. Hit regions per window MAXWH 400, arrays sized NA*MAXWH [V: 02-ui.HC line 195].
  • Icons: L_* enum 0 to 20 in 01-core.HC (lines 1129 to 1149). gen-icons.py has 21 names [V]; the Aiwnios README says 20 [V: aiwnios/README.md]. Count to confirm.
  • Dock: DockLayout, Dock and DockHit in 02-ui.HC (lines 426 to 530), built from ks_dord.
  • Files app: Runnable() accepts .HC, .HC.Z and .CPP [V: 03-apps.HC lines 245 to 252]. RunApp runs a program in its own task with XTalk #include, then opens app 9 [V: 04-main.HC lines 153 to 167].
  • A generator already exists: scripts/gen-projects.py writes ProjectsData.HC [V]. Use the same pattern for the app table.

4. Manifest#

One file per app, apps/<folder>/manifest.json, the Kosmos shape [V: shared/manifest.ts, server/platform/manifestSchema.ts]:

  • id (dot-namespaced: core.music, core.fonts, user.<name>), name, version (semver), description, icon (Lucide kebab name), tier, entry, implements, permissions, tools, events, chrome.
  • Shell features are notify, windows, clipboard, agent [V: manifestSchema.ts]. A desk has no agent feature yet.

HolyC additions. These need the owner's decision, because they change a shared schema (primitives section 6 says the same):

  • entry gains { "kind": "holyc", "file": "music.HC", "window": { "w": 880, "h": 560, "resizable": true } }. The window defaults move here from ks_aw and ks_ah.
  • entry gains { "kind": "templeos", "path": "::/Demo/Games/..." } for TempleOS programs, and { "kind": "host", "launch": "url" | "app", "value": "..." } for Kosmos OS apps (section 8).
  • category (optional string): the folder groups (Music, Utilities, System, Kosmos, TempleOS).
  • fileTypes (optional list): for "open with". Music claims .mp3, .flac, .m4a, .ogg, .wav.
  • services (optional list): music-host, font-host, fetch, file. The desk refuses to launch an app whose service is missing, with a message.

A desk-only build step reads the manifests and writes AppTable.HC. Nothing parses JSON in the guest, which has no JSON parser.

5. Registry and loading#

  • Build time: scripts/gen-apps.py reads apps/*/manifest.json (and the built-in table), validates each against the rules in section 4, and writes desk3/AppTable.HC: arrays for id, name, icon, category, default size, dock order, permissions and file name. The generator fails on duplicate ids, unknown kinds, or a missing .HC file.
  • Run time: the table is a list of records. AppDef holds draw, click, key and close as function pointers, or as a small dispatch by an id enum, to avoid the function-pointer dialect risk on Aiwnios (check in the framework spike; not verified).
  • Load on first launch: a holyc app is compiled when first opened, with #include in a child task as RunApp already does [V]. Its functions stay in the heap afterwards. TempleOS does not unload compiled code [M]. So "unload" means: free the app's data, close its windows, and keep the code until the desk restarts. A desk restart frees all of it.
  • Boot cost: no holyc file is compiled at boot. Only the table is built in. The KS-READY target of 0.5 to 0.7 s [V: aiwnios/README.md] holds because nothing extra is loaded.

6. The folder UI#

List view: columns for name, category, version, last used, source (built-in, folder, host) and permission count. The [Info] panel shows the id, version, description, permissions in plain words (describePermissionKey wording from Kosmos: "Read contract data", "Show notifications" [V: shared/manifest.ts]), file types and services. Running apps show a dot.

Search matches name, id and category, and ranks recent apps first. Keyboard: arrows, Return to open, Delete on a non-built-in app to uninstall (with a PROMPT).

Dock: dragging an icon onto the dock pins it; dragging it off unpins it. Pins are a host-stored list with a limit of 10 visible, matching Kosmos OS, and "All apps" opens this folder.

7. Permissions#

  • The keys are Kosmos's keys: intent:<id>, contract:<id>:<read|write>, storage:own, shell:<feature> [V: permissionKeys()]. A desk app that stores data uses storage:own and gets a folder under the host store.
  • Install grants: the install dialog lists every requested key in plain words. Default state ask for anything beyond shell:notify and storage:own; those default to granted for built-in apps only.
  • First use: a key in state ask opens a dialog with "Allow once", "Allow", "Deny". The answer is stored on the host.
  • Revocation: a per-app panel in Settings lists the keys, with a toggle each. Revoking a key that is in use stops the feature and writes a line to the host audit log.
  • The guest cannot grant itself anything. Grants live on the host, and the guest asks for each check. This mirrors the Kosmos rule "the app cannot claim its own identity" [V: primitives 1.3, token flow].

8. Installing, packaging, updates, signing#

  • Install from a host folder: the user picks a folder in a host dialog. The host validates the manifest and every file's hash, shows the install dialog (name, version, permissions, services), and on "Install" copies the .HC file into the guest's RAM disk B: over the channel. The host keeps the copy, so it is back after a reboot.
  • Store: none in v1. Later, a list of URLs or a Kosmos OS catalogue (Kosmos's install-by-URL path, Path B in the publishing plan [V: docs/app-publishing-plan.md]).
  • Signing: a detached Ed25519 signature over the manifest and the SHA-256 of every file, checked on the host against a trust list in the host store. Unsigned apps install only after a PROMPT that says "not signed". The guest checks only the file hash it was sent.
  • Updates: the host compares semver. If the new version asks for keys that were not granted, the install dialog runs again for those keys only.
  • Uninstall: a PROMPT. It removes the app's files from B: and the host copy. It keeps the app's data, as the Kosmos Docs manifest states ("your documents stay") [V: apps/docs/manifest.json]. A second PROMPT offers to delete the data.
  • TempleOS programs: the TempleOS app (built-in, app 9) and any .HC file the Files app can run appear as templeos entries. The Run action is "Run file" inside this folder, so the Files app stops having its own launch path.

9. Kosmos OS apps on the Mac#

A Kosmos app (a web app or Tauri app) cannot run inside TempleOS. It appears as a host entry that the desk launches on the Mac:

  • Kind url: the host opens the URL in the default browser, or in the Kosmos frame if one is running.
  • Kind app: the host runs the named application, for example a Tauri build, with open -a.

Each launch is a PROMPT, because it runs a program on the user's Mac: "Open Kosmos Calendar on the Mac? Yes / No". Every bridge call stays on the Kosmos side with its own token. The desk never receives a Kosmos token. Kosmos apps are not copied into the guest, and their code and data stay where they are.

10. Migration: the refactor sequence#

Each step keeps the x86 and Aiwnios builds working. Gate for every step: golden.py on both builds gives the same 13 scene results as now (the Aiwnios README table [V]); kslint.py clean; boot-vm smoke run; build-image.sh run once after the step that changes an asset.

  1. Add the table, keep the arrays. Write scripts/gen-apps.py and generate AppTable.HC for the 11 current apps. Fill the old arrays (ks_an, ks_aw, and the rest) from the table in the existing init path. Gate: golden identical.
  2. Replace the AppBody chain (03-apps.HC lines 740 to 754) with a lookup through the table. Keep app 9 on its existing path, using RunApp [V]. Gate: golden identical.
  3. Fold BodyOf (06-run.HC lines 9 to 14) into the same lookup, removing the browser special case. Gate: the Browser window draws the same on both builds.
  4. Replace AppClick (04-main.HC line 203) with a per-app click hook, and move the app 4 key cases (lines 408 and 214) into the Settings entry. Gate: click and key scripts from drive.HC give identical state hashes.
  5. Open and close hooks: replace the app 9 cases in OpenApp and CloseApp (04-main.HC lines 58 to 72) with the entry's open and close hooks.
  6. Dock from the table: replace ks_dord (02-ui.HC line 11, used at lines 552 and 04-main.HC 384) with the table's dock order, then with the host-stored pin list. Keep the Quit entry. Gate: dock sweep and hover unchanged in the golden scenes.
  7. Window ids and sizes: NA becomes MAXAPP (32). Size ks_whx0-family arrays for MAXAPP*MAXWH and check memory. AID keeps its formula. Gate: golden identical; memory logged.
  8. Icon names: map manifest icons to L_*. Add new names to gen-icons.py and the enum, regenerate KSICONS.BIN, and update scripts/image-path.sh if needed (it already stamps KSICONS.BIN). Gate: all 21 icons identical in the golden icon scene.
  9. Move one app out of 03-apps.HC: the Calculator, the smallest, becomes apps/calculator/calculator.HC with a manifest. Gate: Calculator scene identical and its load-on-first-launch works.
  10. Applications folder: a new app, generated from the table, in the same way as the others. Gate: it lists all apps and opens each one.
  11. Install from host folder: the bridge copy and the install dialog (depends on the channel spike).
  12. Permissions: grant store on the host, first-use dialog, revocation panel. Gate: a denied key blocks the feature and writes an audit line.

Steps 1 to 10 need no channel. Steps 11 and 12 wait for the channel spike and the framework work in holyc-native-apps-plan.md.

12. Risks#

  1. Schema change in a shared format. The HolyC kind and the new fields change Kosmos's manifest. Mitigation: an owner decision before step 1 touches the schema; the desk uses its own generated table until then.
  2. Heap growth. Loaded code is never unloaded. Mitigation: a per-session load budget; a desk restart frees everything; measure after step 9.
  3. Function-pointer dialect differences on Aiwnios. Mitigation: use the id-dispatch fallback; check in step 2.
  4. Golden drift from the migration. Mitigation: each step is one commit with its own golden gate.
  5. Permission confusion. Users may not understand "music library (read)". Mitigation: plain-language text from describePermissionKey, reviewed with the owner.
  6. Unsigned or hostile apps. Mitigation: unsigned install needs a PROMPT; the guest runs only files whose hashes the host sent.
  7. Kosmos licence. The Kosmos OS repo has no licence [V: primitives 5]. Copy field names and rules only, not code.
