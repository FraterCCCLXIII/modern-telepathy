1. What Kosmos OS is, and how an app is defined#

Kosmos OS is a browser-based desktop shell (Vite + React on the client, a Hono/Node server with SQLite) where an agent can build apps. It has a window manager, dock, menu bar, command palette, a chat agent, generated OpenUI apps, system services and a bridge that all app calls pass through. [V] README.md, src/os/Desktop.tsx, src/os/Dock.tsx, src/os/MenuBar.tsx, src/os/WindowFrame.tsx.

1.1 The platform rules (from docs/app-platform-plan.md)#

  1. Contracts over implementations: apps implement versioned contracts (os.calendar@1); callers never bind to an app. [V]
  2. One choke point: every privileged call goes through dispatchAppBridge with a caller identity. [V] server/platform/bridge.ts
  3. Tier decides the container, not the surface. Same manifest, identity, grants and bus for every app. [V] (plan)
  4. The OS owns PIM and file data; apps are clients. [V] (plan, shared/capabilities/files.ts)
  5. No private shell APIs: core apps use the same SDK and manifest as third-party apps. [V] (plan)
  6. Typed intents on the wire, not natural language, between components. [V] (plan)
  7. Brand-free platform boundary: os.* contracts, core.* app ids, x-app-token, /app-sdk.js, --os-* theme tokens. [V]

1.2 Manifest#

Type: AppManifest in shared/manifest.ts; validated by Zod in server/platform/manifestSchema.ts. [V]

Field Shape Notes
id reverse-dns, ^[a-z0-9]+(\.[a-z0-9-]+)+$ core apps use core.*
name, version, description strings, semver
icon Lucide kebab name, e.g. calendar-days, file-text
tier declarative or code all bundled apps are code [V]
entry url / bundle (path under apps/) / openui (StoredApp id) bundle paths are validated as lowercase segments
implements contract ids, e.g. ["os.docs@1"]
permissions intent, contract (read or write), storage: own, shell (notify, windows, clipboard, agent) grant keys like contract:os.files@1:write
tools up to 20 agent tools; binding is intent or storage-query (SELECT only) JSON Schema parameters

chrome { toolbar: false } hides the version strip

Example (apps/docs/manifest.json, [V]): core.docs, tier: code, entry: { kind: bundle, path: docs/dist }, implements: [os.docs@1], permissions for os.files@1 and os.docs@1 read and write, events.subscribes: [files.changed].

1.3 Lifecycle#

  • Seeds: ensureSeeds() reads apps/*/manifest.json on boot and installs them as source: seed; they are served at /apps/<folder>/. [V] (server/platform/installedAppStore.ts, docs/office-suite-plan.md)
  • Install paths: seed folder, URL, raw JSON (all through parseManifest). [V] shared/manifest.ts AppSource
  • Grants: granted | denied | ask, keyed per permission (grantStore.ts). Install grants every requested key by default. [V]
  • Launch: the shell mints a 24-byte per-window token (POST /api/installed-apps/:id/token, 12 h TTL) and the AppHost attaches it. The app cannot claim its own identity. [V] bridge.ts
  • Window: { type: "installed", appId } in windowStore; installed apps sit in the Dock, not the NavRail. [V] (office-suite plan)

1.4 SDK and bridge#

  • SDK: packages/app-sdk/sdk.js (324 lines, zero dependencies, served at /app-sdk.js); types in index.d.ts. [V]
  • createAppClient() exposes intents.invoke(intent, params), storage.query/execute (own SQLite namespace, needs storage:own), shell.notify, shell.askAgent, shell.setWindowGeometry (aspect lock), shell.toolbar.set/onInput, events.on(topic), theme.current/onChange. [V]
  • Wire: window.parent.postMessage({ appBridge: true, type: "request", id, method, params }); host replies with ui.result; ready is type: "ready". [V]
  • Also handles host ui.command messages, so the agent cursor can click inside the app (data-arco-cid ids). [V]
  • Bridge methods (dispatchAppBridge): intent.invoke (grant check, audit, then invokeIntent), storage.query, storage.execute, events.emit. Unknown method is an error. Every call writes appendAudit. [V]
  • HTTP: POST /api/bridge (server/index.ts), audit read at the audit route. [V]

1.5 Contracts (the intent vocabulary)#

Registry: shared/capabilities/index.ts CONTRACTS map, routed by server/capabilities/registry.ts (invokeIntent). [V]

os.files@1 list, get, search, content.read (r); create, rename, move, star, trash, restore, delete, content.write (w) SQLite files + blobs in data/files/ Drive, docs, sheets, slides

No contract exists for mail, contacts, maps, weather, fonts or a code editor (see section 7).

Intent schemas are JSON Schema 2020-12 objects and are reusable as tool definitions. [V]

1.6 Data stores#

  • System stores are owned by the server: filesService (data/db/system-files.sqlite plus data/files/<id> blobs), calendar, tasks, calculator, music library, mail (server/mail/mailStore.ts, secret-safe JSON via secureFs, not SQLite). [V]
  • Per-app private namespace: app_<appId> via storageNamespace(), gated by storage:own. [V]
  • Client-only stubs: contacts vault (localStorage key arco-contacts-vault, zustand persist); timer history (localStorage). [V]

1.7 Agent tools#

  • System tools live in server/agent/tools.ts (agentTools[], e.g. tasks_list, tasks_create, sheets_query, docs_export). [V] (README, docs/office-format-interop.md)
  • App tools compile from manifests: server/platform/appTools.ts (74 lines) turns tools[] into LLM tool defs, namespaced app__<id>__<name>. [V] (shared/manifest.ts comment)
  • Dispatch is deterministic code; the app's grant sheet is enforced on every call. [V]
  • Per-tool agent policy auto | confirm | deny is planned (Phase 3), not confirmed built. [I]

1.8 Intents, events and confirmation#

  • files.changed, calendar.changed, calculator.changed are the subscribed topics; server/bus.ts republishes app events as app-event:<topic>. [V]
  • Confirmation: confirm_required SSE flow is reused for first-use prompts (plan). [V] (plan)

2. Design tokens, icons, chrome and components#

2.1 Shell tokens (src/styles/tokens.css, src/os/themeTokens.ts) [V]#

Light and dark palettes on html[data-theme]. Every value is a CSS custom property. Apps get them as --os-* through the AppHost.

  • Colour (dark / light): desktop bg #0d0d0f / #dfe4ec; surface rgba(26,26,28,.92) / rgba(252,253,255,.92); solid surface #1a1a1c / #fcfdff; elevated rgba(40,40,44,.95) / white 98%; hover 6% / 5%; active 10% / 9%; chrome rgba(18,18,20,.78) / rgba(248,250,253,.8). Text primary #ececee / #171b23; secondary #a8a8ae / #4e5665; tertiary #717178 / #8a92a3. Accent #7c9dff / #3b64e0 (strong #5b82ff / #2b51c7); success #58c98b / #23985e; warning #e5b567 / #b57f24; danger #e5737d / #cc4450. Border rgba(255,255,255,.09) / rgba(15,20,30,.1).
  • Accent presets: blue, violet, green, amber, rose, cyan, monochrome (themeTokens.ts). Font presets: system, inter, ibm-plex, source-serif, space-grotesk.
  • Type scale: xs 11, sm 12.5, md 14, lg 16, xl 20 px. UI font stack: -apple-system, BlinkMacSystemFont, Segoe UI, Roboto, .... Mono: SF Mono / Menlo.
  • Spacing: 2, 4, 8, 12, 16, 24, 32 px (2xs to 2xl).
  • Radii: s 6, m 10, l 14, window 12 px.
  • Shadows: --arco-shadow-window (0 24/64 px, two layers) and --arco-shadow-chrome (0 8/32 px). Backdrop saturate(160%) blur(22px).
  • Motion: ease cubic-bezier(0.32, 0.72, 0, 1); fast 140 ms; med 240 ms; full-screen crossfade 600 ms.
  • Z layers: windows 10, chrome 1000, overlay 2000, modal 2100.
  • Wallpapers: aurora, dusk, graphite, forest gradients (tokens.css).

2.2 Five styles in apps/os-styles [V]#

apps/os-styles/styles.css (generated by scripts/gen-styles.py, WCAG AAA 7:1 text) defines nine data-style values: longformer-light, longformer-dark, temple, kosmica, platinum, paper, macos, windows, brutalist. Each sets --lf-* tokens (accent, surfaces 1 to 3, text, border, focus ring, radii, font family, durations) and --s-* shell tokens (desk, bar, shadow, lift, title style). Targets: 44 px hit area, 16 px body, 1.6 line height. [V]

Our desk3 implements five (desk3/01-core.HC lines 40 to 48, README): Longformer light, Longformer dark, macOS, Windows 11, Kosmica glass. The temple, platinum, paper and brutalist styles are not in desk3 [V]. The user brief said "five styles"; this matches.

2.4 Icons [V]#

2.7 Layout patterns [V]#

  • Sidebar plus main plus optional right panel (Drive, Tasks, Sheets, Mail): FilesWorkspace, TaskDrawer, EmailSidebar/EmailThreadList.
  • Toolbar on top with search (--arco-search-* tokens); status line; empty states via EmptyState.
  • Adaptive: ResizeObserver plus data-arco-size and CSS container queries (os-styles uses @container); mobile shell below a width threshold. [V]

6. App model for the Applications folder#

Goal: a HolyC app and a Kosmos app share one manifest shape, one permission vocabulary and one call API, so the same app id and grants work in both.

Proposed (for discussion; no code changed):

  1. Folder: apps/templeos-holyc/apps/<name>/manifest.json plus the HolyC source (<name>.HC). The desk3 ks_an, ks_aw, ks_ah, ks_fx, ks_fy and ks_dord arrays become a scanned list, which matches the framework step in holyc-native-apps-plan.md.
  2. Manifest: the AppManifest fields from section 1.2, unchanged. Add one entry kind, { kind: "holyc", path: "<name>.HC" }, to both shared/manifest.ts and manifestSchema.ts. This is a schema change on the Kosmos side; decide with the owner first. [I]
  3. Icon: manifest icon is a Lucide name; the desk3 loader maps it to an L_* icon or a vector path (section 2.4).
  4. Permissions: the same grant keys (contract:os.files@1:write, shell:notify). The Settings Apps panel reads one grants file shared by both shells.
  5. One call gate: a single HolyC function (KsCall(appId, method, params)) that checks grants, writes an audit line, then calls either a local HolyC service or a host service over the channel. Nothing calls a service directly. Mirrors dispatchAppBridge.
  6. Contracts: HolyC apps implement and consume the same os.*@1 ids. The HolyC Tasks app reads os.tasks@1 the same way the Kosmos Tasks app does.
  7. Tools: tools[] in the manifest stays data-only; the agent calls it through the same gate.
  8. Store: the file contract (os.files@1) is the shared document store. A HolyC Applications folder lists installed manifests. Documents keep their mime types so HolyC editors can open Kosmos documents and the reverse.

Open decisions for the owner: whether the HolyC app ids are core.* (preinstalled) or holyc.*; whether the HolyC channel is a new entry kind or reuses url; whether an app that needs the network must always go through the host fetch service.
