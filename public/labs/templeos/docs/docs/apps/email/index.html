Email client for the Kosmos HolyC desktop: plan

Edited 2026-10-27docs/apps/email.md

Status: plan only, no code. Branch task/templeos-shell. Written 2026-10-27. Read with docs/holyc-native-apps-plan.md (rule: nothing sent, deleted or purchased without a UI prompt), docs/browser-architecture.md sections a, b and e (host services over a channel, security) and aiwnios/README.md (also runs natively on Apple Silicon). Companion: docs/apps/contacts.md.

Tags: [verified] = checked in this pass (GitHub API, LICENSE file, RFC index or vendor page); [memory] = not re-checked.

1. Purpose and users#

A native mail reader and composer on the desktop. The guest draws everything; the Mac host does all network I/O, TLS and credential handling. Users: people with a personal mailbox (Fastmail, Gmail over IMAP, a self-hosted server) who want to read and answer mail from the retro desktop, and keyboard-first users. Out of scope: Exchange, calendars, rich HTML composition, server-side rules.

2. Feature inventory#

Reference clients: Apple Mail (support.apple.com/mail), Gmail (support.google.com/mail), Thunderbird (support.mozilla.org), Fastmail (fastmail.com/help, [verified] setup and comparison pages found), Hey (hey.com). Gmail's exact undo window (5 to 30 s) came from third-party guides [verified as a search result, not on Google's page]; confirm before a gate uses it.

3. Architecture#

Guest: layout, list paging, reader and compose painting, keyboard, prompts, disk cache of recent bodies. It never opens a socket.

Host: every network byte, TLS, credentials, IMAP state, MIME parsing, sanitising, search, sync and the outbox. No password, token or certificate key crosses the channel.

Protocol. A mail message family on the same frame (sync 0xA5, CRC-32, 16-byte overhead). Each request carries a request id and account id; each reply echoes them.

Message Dir Payload
MAIL_ACCOUNTS H to G account id, name, state (ok, auth needed, offline)
MAIL_FOLDERS H to G account id; folders with role and unread count
MAIL_LIST G to H folder, sort, offset, count; reply: compact binary header records
MAIL_GET G to H message id; reply: text blocks, attachment metadata, phishing flags
MAIL_ACTION G to H op (read, flag, move, delete), ids; runs only with a token
MAIL_COMPOSE G to H draft id, recipients, subject, body, reply refs; stored in outbox
MAIL_SEND G to H draft id and the token from the Send prompt
MAIL_SEARCH G to H account, folder, terms, offset
MAIL_SYNC H to G folder, new count, changed flags, removed ids (pushed)
MAIL_PROMPT / MAIL_PROMPT_ANS both prompt id, kind, text; answer carries the token
MAIL_ERR H to G request id, class (auth, network, server, quota), scrubbed text

Tokens. For each prompt the host creates a random nonce. An action or send runs only when the answer repeats that nonce, so a replayed or forged message does nothing. Prompt timeout means No.

Caching and offline. Headers cached per folder with UIDVALIDITY and HIGHESTMODSEQ (CONDSTORE, RFC 7162 [memory]); a UIDVALIDITY change drops that folder. The host caches rendered text, not raw HTML, for 500 messages per account. The guest caches 100 bodies under T:/Mail/cache. Offline: lists and reader work from cache, compose and actions queue as "pending", and queued sends retry with backoff.

4. Data formats and protocols#

Start with IMAP and SMTP: every target provider speaks them, Python's stdlib clients are mature, and the wire is plain text that is easy to log in tests.

Format or protocol Use First?
IMAP4rev2, RFC 9051 [verified: rfc-editor.org/rfc/rfc9051.html, Proposed Standard, Aug 2021] folders, headers, bodies, flags, search yes, with IMAP4rev1 fallback
SMTP submission, RFC 6409 and RFC 5321 [memory] sending yes
Implicit TLS ports, RFC 8314 [memory] 993, 465 yes
MIME, RFC 2045 to 2049, and RFC 5322 [memory] bodies, attachments yes
OAuth 2.0, RFC 6749 [memory]; SASL XOAUTH2 [memory] Gmail-style sign-in M6
mbox, maildir, EML import and export P2
JMAP mail, RFC 8621 [memory] Fastmail-native later (M8 candidate)

Fastmail offers IMAP, SMTP, CardDAV and JMAP [verified: Fastmail help pages]. Gmail offers IMAP and SMTP with OAuth 2 [memory].

OAuth 2 (host only). The host opens the system browser to the provider's authorise endpoint with PKCE, receives the redirect on a loopback address (127.0.0.1, random port), exchanges the code, and stores the refresh token in the macOS keychain. The guest sees "account connected" and an account id. For a self-hosted server, the password is typed once into a host sheet and stored in the keychain.

MIME to text. Python's stdlib email package on the host, producing text blocks (paragraph, quote level, link, preformatted), attachment metadata and placeholders for inline images. No raw HTML leaves the host.

6. Security and privacy#

Prompts (no default-yes; timeout is No). Send (shows recipients and count), delete and bulk move (count and folder), mark as spam (may train the provider), import and export (file, count), sync-back of local changes after reconnect, attachment save to the guest disk (name, size, warning for executables and archives), add account (host sheet).

HTML mail. Shown as text or as a sanitised display list. The host strips script, forms, objects and styles, shows real link targets, and fetches no remote content (images, fonts, tracking pixels) unless the user allows that sender in a prompt. Remote fetches, when allowed, run on the host and are logged. No JavaScript runs anywhere.

Attachments never run. The guest lists name, type and size. Save goes to a host staging folder; a prompt then copies to the guest disk. Nothing is opened automatically.

Phishing indicators. The host shows: display name and domain mismatch, Reply-To differing from From, link text domain differing from href, and SPF, DKIM and DMARC results from Authentication-Results (RFC 8601 [memory]). Shown as a line in the reader, never as a silent block.

Tokens. macOS keychain, one item per account (service kosmos-mail). Logs redact AUTHENTICATE, LOGIN and Authorization. Guest error text is scrubbed.

Storage. Host store under ~/Library/Application Support/KosmosMail/, mode 0600. Guest cache under T:/Mail/ is unencrypted (a local disk image); stated to the user.

Test data. No real account in CI or in gates. Fixtures are synthetic.

8. What the guest needs from the framework#

Present in desk3/02-ui.HC [verified]: Button, Toggle, Radio, Slider, Check, Icon, Frame, Menubar, KMenu, Dock, hit regions, damage tracking.

Missing (blocking marked): - Single-line text field, with caret, selection, paste and key repeat. Blocking for M2; the browser omnibox needs it too. - Multi-line editor with wrap, selection and undo. Blocking for M3. - List view, virtualised, keyboard focus, multi-select. Blocking for M2. - Split view with a draggable splitter. M2. - Menus and context menus on rows. KMenu exists; row menus do not. M2. - Dialogs for prompts, modal focus. M3. - Toasts for new mail. P1. - Drag and drop. P2; menus cover v1. - Unicode. The guest font is ASCII-only Inter bitmaps. Mail names and bodies are often non-ASCII. Plan: transliterate on the host for display, keep full UTF-8 in the host cache, mark lossy spots. Real fix: the glyph service in the browser plan.

9. Shared data with Contacts#

  • Completion. Compose To, Cc and Bcc call the contacts search with the typed prefix (limit 8). Only name and address come back.
  • Sender card. "Show contact" in the reader fetches the card for the exact normalised address. "Add to contacts" is a prompt that opens the editor pre-filled.
  • Contracts. The Kosmos OS repo puts OS-owned PIM data behind typed intents (docs/app-platform-plan.md, principle 4), with os.contacts@1 first and os.mail@1 after (Phase 4). Mail calls the contact contract, never the store. The HolyC build uses the same message shapes over the channel until an intent bus exists.
  • Only shared key: the lower-cased, trimmed email address.

10. Optional AI features (host, separate)#

Thread summaries and draft replies, off by default, in a separate host process. A draft is inserted into compose only and never sent. The model sees only the text the user selects. Nothing is logged. Milestone M9, optional.

11. Milestones and gates#

Test setup, no real account: aiosmtpd (Apache-2.0) on 127.0.0.1:1025 recording messages, and GreenMail (Apache-2.0, needs Java) or a small Python IMAP fixture on 127.0.0.1:1143. Fixture mailbox: 2,000 synthetic messages with UTF-8 names, attachments, HTML-only bodies, quoted replies, a tracking pixel, a phishing mismatch and a 10 MB attachment.

12. Risks#

  • HolyC speed. Long folders under emulation. Mitigation: pages of 50, frame budget, measured at M2.
  • Non-ASCII. Transliteration loses names. Mitigation: host keeps full text; glyph service is the real fix.
  • Provider drift (OAuth and IMAP behaviour changes). Mitigation: M6 re-run before release; pinned libraries.
  • Channel rate for header listings. Mitigation: compact binary records.
  • Scope creep into HTML mail. Mitigation: section 6 rules; no HTML rendering.
  • Licences of mail-parser and mblaze unconfirmed. Mitigation: not used until checked.

13. Effort#

M0 to M5 about 6 to 8 engineer-weeks, after the framework work (text field, list view, split view, dialogs) lands; M6 1 to 2 weeks with the user; M7 one week; M8 and M9 about a week together. The framework prerequisites dominate the schedule.
