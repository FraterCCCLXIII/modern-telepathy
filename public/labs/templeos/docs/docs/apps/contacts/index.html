Contacts app for the Kosmos HolyC desktop: plan

Edited 2026-10-27docs/apps/contacts.md

Status: plan only, no code. Branch task/templeos-shell. Written 2026-10-27. Read with docs/holyc-native-apps-plan.md (rule: nothing sent, deleted or purchased without a UI prompt), docs/browser-architecture.md sections a, b and e, and aiwnios/README.md. Companion: docs/apps/email.md, which uses this app for completion and sender cards.

Tags: [verified] = checked in this pass (GitHub API, LICENSE file, Apple or vendor page, IETF listing); [memory] = not re-checked.

1. Purpose and users#

A native address book: people with cards (names, emails, phones, addresses, organisation, birthday, notes), groups, search, and vCard import and export. The guest draws everything; the Mac host holds the stores, syncs remote books (CardDAV first) and does macOS Contacts access. Users: people whose contacts live on a Mac, iCloud, Fastmail or Nextcloud who want a keyboard-friendly list on the desktop, and mail users who need completion. Out of scope: LDAP write, social profile sync, bulk photo management.

3. Architecture#

Guest: layout, letter index, list paging, card and editor painting, keyboard, prompts, small cache. No sockets.

Host: all stores, vCard parse and write, search, sync, conflicts, duplicates, the macOS permission request, and keychain access for CardDAV credentials.

Protocol (same frame; request id and account id on each message).

Message Dir Payload
CON_ACCOUNTS H to G account id, name, kind (local, carddav, macos), state
CON_GROUPS H to G account id; groups with counts
CON_LIST G to H group or all, sort key, offset, count; reply: id, display name, first email, first phone, letter
CON_GET G to H contact id; reply: typed fields (name parts, emails, phones, addresses, org, title, note, birthday, photo ref)
CON_SEARCH G to H text, limit, field filter; reply: id and display row (mail uses this)
CON_SAVE G to H contact id or new, fields; a change to a remote card needs a prompt first
CON_DELETE G to H ids; runs only with the prompt's token
CON_IMPORT G to H file chosen in a host sheet; reply: preview
CON_IMPORT_ANS G to H preview id; import all new, skip duplicates, keep duplicates, or cancel
CON_EXPORT G to H scope, format (3.0 or 4.0); host writes after prompt
CON_PROMPT / CON_PROMPT_ANS both prompt id, kind, text; answer carries the token
CON_ERR H to G request id, class, scrubbed text

Tokens work as in the mail plan: a random nonce per prompt, and a write runs only when the answer repeats it. Timeout is No.

Caching and offline. The local book needs no network. Remote books keep a local copy with an ETag per card and a sync-token (WebDAV sync-collection, RFC 6578 [memory]). Offline edits queue as "pending" and push after a conflict check. The guest caches 300 list rows and 50 cards under T:/Contacts/cache.

Host data model (sqlite3). contact (uid, account, etag, updated, raw vCard, normalised name), field (contact, kind, label, value, normalised value), grp and grp_member, sync_state, prompt_log. The raw vCard is kept so unknown properties survive a round trip.

4. Data formats and protocols#

Format or protocol Use First?
vCard 3.0, RFC 2426 [memory] import and export; common export from Apple, Google, Thunderbird yes
vCard 4.0, RFC 6350 [memory] import and export; KIND:group, PREF, TEL URIs yes
CardDAV, RFC 6352 [memory] over HTTPS iCloud, Fastmail, Nextcloud sync M5
WebDAV sync-collection, RFC 6578 [memory] incremental sync M5
macOS Contacts framework (CNContactStore) [verified: developer.apple.com/documentation/contacts] local Mac contacts with user permission M7
Google People API with OAuth 2 [memory] Google Contacts later
JMAP contacts (IETF draft-ietf-jmap-contacts) [verified: draft-10 listed on the IETF site] Fastmail-native not planned

Start with vCard and CardDAV. vCard is the portable format and the import path for every source. CardDAV covers iCloud, Fastmail and Nextcloud with one protocol; Fastmail's CardDAV endpoint is documented [verified via Fastmail help].

macOS Contacts and TCC. Apple's guidance [verified: developer.apple.com accessing-the-contact-store and CNContactStore pages]: check CNContactStore.authorizationStatus(for: .contacts), then call requestAccess(for:). The system remembers the answer, so repeat calls do not prompt. Since June 2024 the system can also grant limited access [verified: developer.apple.com/documentation/updates/contactsui]. Two constraints: the requesting process needs an NSContactsUsageDescription string, so the macOS bridge must be a small signed helper app, not a bare Python script; and reading or writing note needs the com.apple.developer.contacts.notes entitlement, which Apple approves for distribution [verified only from a third-party skill guide; confirm with Apple]. Plan: ship the helper at M7 without notes access until the entitlement is granted.

vCard parsing rules. Unfold continuation lines; decode quoted-printable and base64 PHOTO; keep unknown and X- properties raw; accept 3.0 and 4.0; write 4.0 by default. The parser is in-house (about 400 lines of Python), tested on RFC examples, because the available libraries are GPL or unclear (section 5).

6. Security and privacy#

Prompts (timeout is No). Delete (names and count); a save that changes a remote card (changed fields); merge; import (file, count, duplicate policy); export (destination, count); sync conflict (both versions); add CardDAV account (host sheet for URL and password); first macOS Contacts read (the system prompt also appears).

Exposure. Contact data goes only to a guest that asks for it and to a remote account the user connected, for a write the user confirmed. Completion returns name and address only. Search returns the minimum fields; the full card needs CON_GET.

Photos and notes. Photos are scaled to 64 px on the host. A PHOTO URI is shown as a placeholder and never fetched, so an address book cannot trigger tracking requests. Notes are plain text, never HTML.

Tokens. CardDAV passwords and OAuth tokens in the macOS keychain, service kosmos-contacts. No secret fields in the guest protocol. Logs redact Authorization and URL userinfo.

Storage. Host store under ~/Library/Application Support/KosmosContacts/, mode 0600. Guest cache under T:/Contacts/ is unencrypted (a local disk image); stated to the user.

Import caps. 5 MB per file, 5,000 cards per import, 1 MB per card. URLs stored as text and never opened. Photo bytes are re-encoded on the host.

Duplicates are never silent. A name match with a different email is flagged, not merged.

Present in desk3/02-ui.HC [verified]: Button, Toggle, Radio, Slider, Check, Icon, Frame, Menubar, KMenu, Dock, hit regions, damage tracking.

Missing (shared with mail): - Single-line text field: search and every card field. Blocking for C2. - Multi-line text field: notes and the editor. Blocking for C3. - List view with letter headers, virtualisation, keyboard focus, multi-select. Blocking for C2. - Split view with a draggable splitter. C2. - Form layout helper (label, field, add and remove rows). C3. - Dialogs with modal focus, for prompts and import preview. C3. - Row menus and context menus. C2. - Unicode. Names are the most visible non-ASCII text (accents, Cyrillic, CJK), and the guest font is ASCII only. Plan: show a transliterated name, keep the original UTF-8 on the host, and show a marker when the font cannot draw it. The real fix is the glyph service. - Drag and drop. P2.

9. Shared data with Mail#

  • Completion. CON_SEARCH with limit 8 and field filter name and email, from the mail compose field.
  • Sender card. CON_GET on the exact normalised address. Adding a sender is a prompt that opens the editor pre-filled.
  • Contracts. The Kosmos OS repo says OS-owned PIM data is reached through typed intents and never direct store access (docs/app-platform-plan.md, principle 4). It lists os.contacts@1 first and os.mail@1 after it in Phase 4. Contacts exposes os.contacts@1 (search, get, save with prompt, groups); Mail calls the contract. Until an intent bus exists in the HolyC desktop, the same message shapes run over the channel, so adopting the contract later does not change the guest.
  • Only shared key: the lower-cased, trimmed email address.

10. Optional features (host)#

Duplicate suggestions and sender-to-contact matching are host heuristics, off by default. No external people-search or lookup service. No model-generated contact summaries.

11. Milestones and gates#

Test setup, no real account: Radicale as a local CardDAV server on 127.0.0.1, seeded with 2,000 synthetic cards (accents, CJK names, duplicates, groups, a PHOTO URI, one malformed card); RFC example vectors plus synthetic 3.0 and 4.0 files modelled on the Apple, Google and Thunderbird exporters (no personal data).

12. Risks#

  • Font and Unicode. Names are the first casualty of ASCII fonts. Mitigation: transliteration now, glyph service later.
  • Sync correctness. Two-way CardDAV can lose edits. Mitigation: ETags, conflict prompt, no silent overwrite; C5 uses fault injection.
  • macOS entitlements. Notes need Apple approval. Mitigation: ship without notes until granted.
  • vCard variety. Real exports break parsers. Mitigation: raw kept; corpus from three exporters.
  • Licences. vdirsyncer's licence is unclear on GitHub; khard and Radicale are GPL-3.0. Mitigation: no code reuse; test-only use.
  • HolyC scale. 2,000 cards on an emulated CPU. Mitigation: index on host; guest asks for pages.

13. Effort#

C0 to C4 about 4 to 5 engineer-weeks after the framework text field, list view and split view land (shared with mail); C5 about 3 weeks; C6 one week; C7 1 to 2 weeks including signing; C8 three days. C5 is the largest risk.
