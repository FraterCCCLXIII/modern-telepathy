Kosmos Browser: architecture and specification

Edited 2026-10-27docs/browser-architecture.md

Status: specification, not code. Branch task/templeos-shell. Written 2026-10-27. Read with browser-features.md (what each feature is, priority, provider) and browser-test-sites.md (what we test on). It replaces the v0 design in browser-plan.md where they differ; v0 stays as the reader-mode fallback.

Every number here is one of three kinds, and the text says which: [measured] (taken from this repo or the local Mac, with the command or file named), [reported] (taken from a source or from the project notes, not reproduced here), or [estimate] (our arithmetic; the M1 or M2 gate must confirm it). Anything marked (memory) is an API or flag name from memory, to be checked against the Chrome 156 protocol JSON at M1.

0. Summary of decisions#

  1. The host runs a real engine. Google Chrome 156 (local, found at /Applications/Google Chrome.app) driven over CDP. We do not write HTML, CSS or JavaScript engines in the guest.
  2. Transport to Chrome is --remote-debugging-pipe, not a port. No listening socket, no WebSocket client needed, no other program can attach. Requires a non-default --user-data-dir (Chrome 136+ rule, verified fact 2 in browser-features.md).
  3. The guest receives a display list (positioned text runs, boxes, images, clip and scroll regions, link and control hit areas), cut into 256-px bands that the guest caches and asks for on demand. Input and navigation go back as binary messages. Pages are never rendered as pixels except in a fallback tile for canvas, video and WebGL.
  4. Extensions run in our own extension host on the host, because Chrome 137+ branded builds ignore --load-extension (verified fact 3). We implement a chrome.* shim for the MV3 subset in browser-features.md section 11.
  5. One throwaway profile per run, never the user's real Chrome profile. History, bookmarks and settings live in our SQLite store. Cookies live only in the throwaway profile and the host never sends them to the guest.

a. Components#

Component responsibilities:

  • Channel server. Owns the byte link to the guest. Frames, checksums, sequence numbers, flow control, input coalescing (section b).
  • Session and tab manager. One record per tab: browser context id, page target id, session id, navigation history, last display-list version per band, dirty flags. Routes guest input to the right tab and turns Chrome events into guest messages.
  • Engine adapter. The only code that knows CDP. Everything else calls engine.navigate(tab, url), engine.input(tab, event), engine.snapshot(tab) -> snapshot, engine.screenshot(tab, clip, scale). This is the portability seam for the Aiwnios build (the guest-side transport is in section b1).
  • DLIST builder. Turns DOMSnapshot output into ops (section c). Pure Python, no Chrome calls, so it can be tested on saved snapshots.
  • Extension host. Section g.
  • Profile store. SQLite via sqlite3. Schema in section i (stream 6).
  • Guest protocol client and painter. Section b and d.

Host language and dependencies#

  • Python 3 standard library only: subprocess (with pass_fds), json, sqlite3, base64, zlib (host side only), struct, hashlib, http.server (extension and helper pages on 127.0.0.1), threading, select.
  • Not needed: a WebSocket client (the pipe transport avoids one), Node, Playwright or Puppeteer. Playwright is a fine reference for CDP usage but adds a Node dependency; we do not need it.
  • Engine check at start-up: GOOGLE_CHROME=/Applications/Google Chrome.app/Contents/MacOS/Google Chrome, version from --version. Refuse to run below a version we tested (start at 156).
  • Not bundled. We do not ship Chrome. The user installs Chrome (or a Chrome for Testing build) and the bridge finds it. See section k2 for the licence reasoning.

Why CDP over the pipe, and not Chrome's own headless server#

  • --remote-debugging-pipe gives a bidirectional channel on file descriptors 3 and 4 with no TCP port. A port would let any local process attach to the engine, including other user processes, which is the same risk Chrome's own Chrome 136 change was made to reduce (verified fact 2).
  • --headless (new mode, unified with headful in Chrome 132+; verified fact 5) gives the full rendering path, including fonts, images and Canvas, which we need for fidelity. The old headless shell is not enough for fonts.

b. Wire protocol: guest and host#

b1. Transport and framing#

Transport: COM1 at the QEMU server socket (the v0 path, KS_SERIAL_PORT, default 4555), or a Unix socket on Aiwnios (the native build). The framing is the same on both.

Frame layout (all integers little endian):

Offset Size Field Meaning
0 1 sync 0xA5
1 1 type message type (table b2)
2 1 flags bit 0 more-fragments, bit 1 compressed (reserved, always 0 in v1), bit 2 urgent (input, navigation)
3 1 tab tab id (0 = global, 1..255)
4 4 seq sender sequence number, increments per frame
8 4 len payload length, 0 to 1 MB
12 len payload
12+len 4 crc32 CRC-32 (IEEE 802.3, the zlib polynomial) over bytes 0 to 11+len

Overhead is 16 bytes per frame. Receivers scan for sync, then check length and CRC; a bad frame is dropped and the receiver sends a NAK (type 0x7F) with the expected seq. Frames are limited to 64 KB on serial (fragment with more-fragments) and 1 MB on sockets.

Why CRC-32: the serial link is emulated, so errors are unlikely, but a corrupt display list shows as garbage text on screen and is hard to diagnose. CRC-32 table in HolyC is 1 KB and costs one table lookup per byte; measure (M1) before choosing a cheaper one (Fletcher-32 is the fallback).

Encoding: binary throughout. ASCII (the v0 KDoc form) is kept only for the debug dump (--dump), not for the wire, because hex or decimal text doubles the bytes. v0's OK <n> <c> header is replaced by framed messages; v0 and v1 are not wire-compatible, and that is fine because the guest and host ship together.

b3. Flow control#

Two modes, chosen at HELLO by the channel's caps flags:

  • Lockstep chunks (serial, v1). The sender transmits at most c bytes, waits for one acknowledgement byte (0x06, as in v0), then transmits the next chunk. The guest reads its FIFO fully on every acknowledgement. M1 measures c in {32, 128, 512} on the emulated link as v0 did; the default follows the best result that passes a 20 KB checksum test.
  • Sliding window (socket, Aiwnios; and serial if the M1 test shows the FIFO holds). Window of W bytes unacknowledged (initial 16 KB), the guest sends ACK with its free buffer, the sender stops at zero window. NAK retransmits from the expected seq.

Caution (memory, to confirm in M1): QEMU's emulated 16550 holds a small FIFO, and the guest must drain it on each poll or bytes are lost. This is why the serial mode stays lockstep until M1 shows otherwise. The sliding window is not enabled on serial by default.

b4. Throughput budget#

  • Serial figure. The v0 note reports about 47 KB/s over the QEMU serial socket [reported]. The native-apps plan records the older lockstep loader at 1.4 to 2.7 KB/s [reported] and sets a channel gate of 50 KB/s sustained [reported]. The 47 KB/s number is not in the repo's measured results that this pass read; M1 must reproduce it with the bench:N URL (browser-plan.md M1 gate) before any budget depends on it.
  • Real hardware. A physical UART at 115200 baud carries about 11.5 KB/s (10 bits per byte) [estimate]. We target QEMU and Aiwnios, not a real PC serial port, so this only matters if the guest is ever run on hardware.
  • Consequence for pages [estimate at 47 KB/s].
Payload Time over serial
20 KB display list (a small article's first band set) 0.4 s
120 KB first-paint budget (bands 0 to 2 plus a few images) 2.6 s
400 KB (Wikipedia article with a long display list) 8.5 s
one 400 x 300 photo, RGB565 uncompressed (240 KB) 5.1 s
one 120 x 80 thumbnail, RGB565 (19 KB) 0.4 s

Rules that follow: first paint is capped at 120 KB of data; images are sent only when visible and downscaled (section d); the rest of the page streams in the background at low priority, cancelled by any new request.

b5. Delta updates and caching#

  • Bands. The page is split into horizontal bands of 256 CSS px. A band's ops are positioned relative to the page origin in its own range. The host keeps a hash of each band's op bytes and a version number (band version increments only when the hash changes).
  • Delta. When the page changes (SPA update, input, timer), the host re-snapshots, rebuilds bands, and sends only bands whose hash changed. A band the guest does not hold is sent in full. There is no op-level diff in v1; band granularity is simple and the cost is at most one band (256 px) extra per change.
  • Images. Keyed by a 64-bit hash of the downscaled bytes (FNV-1a 64 in HolyC; SHA-256 truncated on the host is also fine; the hash is over what is sent, so the key matches the bytes). The guest keeps an LRU of images within a memory budget (section d). HAVE lets the host skip resends after a reconnect.
  • Fonts. Built-in bitmap faces are referenced by id and never sent (section h). Non-built-in text is sent as RUNIMG with a hash of (font, size, string, colour).
  • Strings. Each DLIST has a string table; ops refer to strings by index. Repeated link URLs and class labels cost one entry each.

b6. Input coalescing (guest side, host side)#

Input Rule
mouse-move keep the latest position; send at most one per 16 ms; send immediately when a button is down (drag selection)
wheel sum deltas for one frame; one SCROLL per frame
mouse-down, mouse-up never coalesced; each sent with urgent flag
key-down, key-up, char never coalesced, in order; a burst of char events may be packed into one frame of up to 64 bytes
resize last value wins, 100 ms debounce
zoom keys sent as NAV op, not as key events, so the host handles them once

The host coalesces Page.scrollBy (or Input.dispatchMouseEvent wheel) the same way: summed per 16 ms.

c. Display list format#

c1. What the host produces#

The host takes a DOMSnapshot per navigation or dirty tick and emits, in paint order, a sequence of ops. Coordinates are CSS px in units of 1/16 px (i32), so 800 px is 12800. The guest multiplies by the scale (1 or 2) when it paints.

Opcodes (proposed; the M1 spike may reorder them):

Op Name Fields Bytes [estimate]
0x01 BOX x, y, w, h (i32 each), fill (colour token, u8), border (token u8), border width (u8), radius (u8 in px), flags (u8) 21
0x02 TEXT x, y (i32), string index (u16), face (u8: built-in face id, see h), colour token (u8), decoration (u8: underline, strike, selected), flags (u8) 14
0x03 IMAGE x, y, w, h (i32), image id (u64), fit (u8: fill, contain, cover, none), flags 26
0x04 CLIP push: x, y, w, h (i32) 17 (push), 1 (pop, op 0x05)
0x05 CLIP-POP none 1
0x06 LINK hit x, y, w, h, link string index (u16) 18
0x07 CONTROL kind (u8: text, password (drawn as dots, no value sent), checkbox, radio, button, select, textarea, file, range), id (u16), x, y, w, h, value string index (u16), label string index (u16), state (u8: disabled, checked, focused) 26
0x08 SCROLL-BEGIN container id (u16), clip x, y, w, h, content h (i32), offset y (i32), overflow (u8) 23
0x09 SCROLL-END none 1
0x0A RUN-IMG run hash (u64), x, y, w, h 26
0x0B TILE tile id (u32), x, y, w, h 21
0x0C FIXED marks the next op as viewport-fixed (drawn at a fixed offset from the viewport) 1
0x0D STICKY the next op's y is clamped to [min, max] as scroll changes, with top inset; fields min, max, top (i32) 13
0x0E XFORM 2 x 3 matrix, i16 fixed 1/1000 (guest honours translate and uniform scale only) 13
0x0F DECOR x, y, w, h, kind (u8: hr, underline, strike, focus-ring, selection-rect) 18
0x10 STR string index (u16), length (u16), UTF-8 bytes (ASCII in v1; non-ASCII as RUNIMG) 5 + n

Token values (colour and face) are indices into the guest's palette, not RGB: C_INK, C_PAGE and so on from desk3/01-core.HC. Page colours that are not in the palette map to the nearest token in the host (or go to a RUN-IMG if the difference is large, decided at M2 by eye and by the golden tests). This keeps the wire small and the guest palette consistent with the desktop; page colours that matter for legibility (text on a background) are preserved by the nearest-token mapping in the M2 gate.

c4. Honest fidelity limits (for the user)#

  • Layout is Chrome's, so line breaks, wrapping, tables and flex and grid are exact. This is the main gain over any custom engine.
  • Glyphs are not Chrome's. Latin text is drawn with our bitmap faces (section h), so letter shapes differ from the page's own font, and widths can differ by a pixel or two per run. The positions come from Chrome, so lines do not drift. For non-Latin text, RUN-IMG uses Chrome's own rasteriser and the shapes are exact.
  • Gradients, shadows and blend modes are approximate or drawn as tiles.
  • Anything in a tile is not text: no selection, no find match, no accessible text.
  • Latency of interactions is one channel round trip plus one Chrome frame. Scroll of the root is local and instant; clicks and typing are not.
  • Video and audio are not played in the guest (section 15 of the features doc).

d. Rendering budget#

d1. What the guest draws per frame#

  • Only ops in the visible bands and only inside the dirty rectangle. Visible bands are found by a binary search on the band index (bands are sorted by y).
  • Text: one blit per glyph from a bitmap atlas. A glyph at scale 2 is about 18 x 30 device px [estimate]; a run of 40 glyphs is about 22 000 px of copying.
  • Boxes: fill rectangles, border as four rectangles, radius as a small corner table (the desk already has shadow and corner tiles, NTK cache, see 01-core.HC).
  • Images: blit of a cached bitmap, scaled only when the fit mode says so (scaling is done on the host, so the guest blits 1:1 wherever possible).

d2. Budgets (targets, to be measured at M2)#

Situation Target on Aiwnios (arm64) Target on QEMU x86 (TCG)

Full redraw of the page area, 2880 x 1800 device px under 8 ms under 300 ms

Reference points, from aiwnios/README.md [measured]: the desk's full redraw is 3.9 ms (4.2 worst) on Aiwnios at 2880 x 1800, and the desktop with ten windows runs at 35 frames a second under the scripted drive. No measurement of the browser exists yet; these are targets, not facts.

d3. Tile cache and band cache#

  • Band cache. The guest keeps parsed ops per band (array of op records). Budget 4 MB of ops per tab, LRU by band. A 1 MB op budget is about 4000 BOX and TEXT ops [estimate] which is a long article's first screen-fulls.
  • Page bitmap cache (optional, M4). Rendered 256-px bands at device scale kept as bitmaps (2880 x 512 px at 4 bytes per px is about 5.9 MB per band, too large to keep many); so the default is no bitmap cache, and the optional one is only for the 3 bands around the viewport. Measure first; the desk's own shadow tiles (NTK) are the reference for what TempleOS can hold.
  • Image cache. LRU, 8 MB budget in the guest (RGB565 bitmaps: about 1 MB per 1000 x 500 px image [estimate]).

d4. Image downscaling on the host to exact paint size#

  1. The host knows each IMAGE's paint rectangle in device px (box size times scale, from the layout snapshot).
  2. A helper page (about:blank in a hidden target, a canvas) draws the decoded image at exactly that size with imageSmoothingQuality = "high", then reads the pixels back with getImageData (memory: canvas API; verify the read-back size limit at M2). Chrome does the decode, so AVIF, WebP and SVG work with no code of ours.
  3. The result is quantised to RGB565, run-length encoded per row, and hashed. Transparent images use an alpha plane (RLE) with the colour.
  4. Images are sent when their band is requested, not with the page. Images above a 300 KB per-page budget are sent in priority order (visible first) and the rest are placeholders with the alt text until requested.
  5. Paint size changes (zoom, resize) re-request the image at the new size; the old hash stays in the cache.

Cost check [estimate]: a 400 x 300 px photo is 120 000 px, 240 KB as RGB565 raw; RLE does not help photos, so photos are the expensive case. Mitigations: the 300 KB budget, the size cap, and a later option of an 8-bit palette for flat graphics (M6).

e. Security model#

e1. Isolation on the host#

  • Per-tab browser context. Each tab is a Target.createBrowserContext (memory; the method exists in the Target domain) with disposeOnDetach. Tabs do not share cookies, storage or cache unless the user opens a link in the same context (the default for ordinary tabs is a context per window, so tabs in one window share cookies as in Chrome).
  • Incognito. A separate context with no store writes, cookies discarded when the window closes.
  • Throwaway profile. --user-data-dir points at ~/Library/Caches/KosmosBrowser/run-<pid> (created at start, removed at exit). It is never ~/Library/Application Support/Google/Chrome. Verified fact 2 explains why the non-default directory is also required by Chrome for the debugging pipe.
  • No port. --remote-debugging-pipe only. The bridge must refuse to start if a --remote-debugging-port argument is ever added (a test in stream 9).
  • Launch flags (to verify on 156). --no-first-run, --no-default-browser-check, --disable-sync, --disable-background-networking, --disable-component-update, --password-store=basic, --use-mock-keychain (memory: the mock keychain flag exists in Chromium builds; check it still applies to Google Chrome 156), --disable-extensions (we run our own host), --disable-features=... only for a named, tested need.
  • Preferences written into the throwaway profile before start: password manager and autofill off, default search as configured, third-party cookie setting, download directory set to the staging folder (section e4).

e2. The guest never receives secrets#

  • No cookies, no Set-Cookie, no Authorization headers, no tokens, no password values, no form autofill, no certificate private data. The host sends the page's own DOM values for visible controls (what the user sees), except password fields, which are drawn as dots with no value.
  • The Network DevTools panel shows headers, with Cookie, Set-Cookie and Authorization redacted by default. Revealing one needs a per-request prompt (P2).
  • Passwords and payment data are out of scope (features doc, section 8); the host does no keychain access unless the user approves each use.

e3. Outward actions and prompts#

Every action that sends data out or changes state outside the page needs an explicit prompt in the guest. The guest is the only UI; the page cannot answer a prompt, and a prompt has no default-yes.

Action Prompt Default if the timer runs out
Form submission by POST (the destination host is shown) "Send form data to host X?" No (the form is not sent)
Downloads (name, size, source host) "Download name (size) from host?" No
Dangerous file types (executables, disk images, scripts, archives with executables) second prompt, plus a warning No; nothing is run anywhere
Permission requests (camera, microphone, location, notifications, clipboard read, MIDI, USB, Bluetooth) "Site X asks for Y?" Deny
Extension install and each added permission the manifest's permissions list No; an installed extension is disabled until a new permission is accepted (the Chrome rule, verified fact 7)
Print to PDF, save page, save to the host Downloads folder file name and folder No
External protocols (mailto:, tel:, custom app schemes) "Open in another app?" (on the host, only after yes) No
Certificate error interstitial the host's own page, "Continue anyway" needs a prompt No; the page does not load
Page-initiated purchases and sign-ins none by us (a click on a page button is the user's own click) the status line shows the destination host so the user can see it
Popups blocked, with an indicator to open once Blocked

Note the last row. We cannot tell a purchase from a click on a page button; the browser does not classify page actions, and the user is the one clicking. We mitigate with no autofill, no stored card data, and a visible destination host. The user may want a stricter rule (for example, a prompt on any navigation to a new host after a form has been filled); that is an open question in the features doc.

e5. Extension permission model#

  • An extension has declared permissions and host permissions in its manifest. Each is shown at install (the warning list), and a new one disables the extension until accepted.
  • Content scripts run only on URLs matched by their matches, in an isolated world. The extension's background cannot read a page's JavaScript objects except through its own content scripts.
  • An extension cannot read another extension's storage. Storage is per-extension in the store (stream 8).
  • The host never gives an extension cookies unless the cookies permission was accepted, and then only for the matched hosts.

The DevTools UI is a guest app. It talks to the host over DEVT messages (type 0x0F). The host adapts each panel to CDP domains:

g. Extension system design#

g1. Manifest subset#

Supported keys (MV3): manifest_version (must be 3), name, version, description, icons, permissions, host_permissions, optional_permissions (requested at run time through the permissions API), content_scripts (matches, exclude_matches, js, css, run_at document_start, document_end, document_idle, all_frames, world ISOLATED only), action (default_title, default_popup, default_icon), background (service_worker as a file name; type module is accepted), web_accessible_resources (matches only), options_page (P2), commands (P2), minimum_chrome_version (ignored, reported).

Not supported: externally_connectable, content_security_policy overrides (we apply our own strict CSP to extension pages), oauth2, key, update_url (no auto-update in v1), incognito split (incognito mode off for extensions in v1), sandbox, MV2 keys.

g2. Where extensions live and how they run#

  • Folders: ~/Library/Application Support/KosmosBrowser/extensions/<id>/, with <id> the SHA-256-based ID (32 characters, a–p alphabet, as Chrome does (memory)). Each folder is a copy of the unpacked source; the originals are never modified.
  • Pages: extension pages are served by the bridge's local HTTP server on 127.0.0.1 at http://127.0.0.1:<port>/ext/<id>/... with a strict CSP. (A single port and a path prefix avoids a fake chrome-extension:// scheme. The origin is different from any web origin.)
  • Background: a page target (not a Chrome service worker) loads background.html (generated by us from the service_worker file if it is not already a page) in its own browser context. This is not MV3 service-worker semantics: no DOM is a difference we accept (the background can use DOM APIs that an MV3 worker could not), and the background does not stop when idle (memory cost; a P2 timer can unload it). Alarms keep it alive when needed.
  • Shim: before any extension script runs, Page.addScriptToEvaluateOnNewDocument installs chrome.* (the shim, host/ext_shim.js). The shim calls the host through Runtime.addBinding (a binding named __kosmosExt) with JSON messages; the host answers through Runtime.evaluate on the target (memory: the binding API exists in the Runtime domain).
  • Content scripts: Page.createIsolatedWorld gives each extension its own world on each frame; the content script is evaluated there (Runtime.evaluate with the world's context id). The page's own JavaScript cannot see the isolated world's objects.
  • Popup: default_popup is a page target at http://127.0.0.1:<port>/ext/<id>/popup.html, painted by the guest in a popup area (the same painter as pages, section c). Its size comes from the popup's content size, capped at 800 x 600 CSS px.

g4. Install flow#

  1. The user chooses "Load unpacked" in the Extensions page (guest) and picks a folder. The guest sends EXT "install-request" with the folder name, and the host opens a host-side folder chooser (Finder, through osascript; memory: a standard approach, verify in the stream) so the user picks the folder on the Mac.
  2. The host reads manifest.json, validates it (the subset above), computes the ID and the permission list, and sends a PROMPT with the warnings from browser-features.md section 11.
  3. The user answers Yes or No in the guest. On Yes the host copies the folder into the extensions directory and registers it. On No nothing is copied.
  4. Updating an extension shows a diff of new permissions and disables the extension until the user accepts them.
  5. Chrome Web Store installs and .crx files are not supported in v1 (features doc, section 11; untrusted download path). A .crx is not unpacked or run without the user's explicit folder choice.

g5. Testing extensions#

  • A sample extension lives in tests/browser/extensions/sample-title/ (content script that changes document.title and a popup with a button). Gate in M5.
  • Each extension's background console goes to the DevTools Console for that extension (a separate target id).

h6. Non-Latin text, in more detail#

  • The host knows, from the layout snapshot, the font family and the glyph coverage of each text run. A run that needs a font outside stage A and B is sent as RUN-IMG.
  • The helper page draws the run with fillText in the same font family and size at device scale, then reads the pixels back with getImageData (memory). Right-to-left and mixed-direction runs are drawn as one string, so shaping and bidi are Chrome's.
  • A RUN-IMG has an alpha mask and the colour token; selection colour is applied in the guest.
  • Hash key: (font family, weight, size, scale, string, colour token). Cached in the guest's image cache, with the same budget as images.
  • Cost [estimate]: a 20-character CJK run at 16 px at scale 2 is about 640 x 40 px; an alpha mask at 8 bits is 25 KB raw and compresses about 3 to 1 with row RLE, so about 8 KB per run. A page with 200 such runs costs 1.6 MB, which is too large for serial; the first-paint budget will hold only the first screen's runs, and the rest stream in. This is the main reason non-Latin pages are slow on the serial link (section k, risk 4).

j. Milestones and gates#

M1: Engine spike (host only)#

  • Scope. Launch Chrome 156 with the pipe and the throwaway profile. Navigate the 25 test sites in browser-test-sites.md. Produce a DLIST dump per site. k. Risks, licences and legal#

k1. Risks (ranked)#

  1. JS-heavy sites. Chrome runs them, so they work, but every interaction costs a round trip, and tiles hide text. Mitigation: the M4 gate with two SPAs; the tile fallback measured at M4.
  2. Video. No decode in the guest; tile streaming at 2 to 5 frames a second is far from smooth, and audio plays only on the host with approval. Mitigation: poster frames and short clips only in v1; say so in the UI.
  3. WebGL and canvas. Tiles only. Interaction works through the host, but the view is an image, so it does not look sharp at zoom. Mitigation: tile at device scale, re-render on zoom.
  4. Fonts and non-Latin text. Stage A covers Latin only. Non-Latin pages depend on RUN-IMG, which is large (about 8 KB a run at 16 px). Mitigation: lazy and budgeted sending; a stage D (HolyC rasteriser) decision at M6 if the measured cost is too high.
  5. Latency. Serial is a bottleneck (47 KB/s reported, to be reproduced). Every click and key is a round trip. Mitigation: coalescing (b6), bands, local scroll, budgets (j).
  6. Memory. The guest has a fixed heap; the desk's own heap use is unmeasured for a browser. Each tab holds bands and images. Mitigation: LRU caches with explicit budgets (d3), discard of background tabs (features section 1), and a per-tab memory counter in STATS.
  7. HolyC speed. Under TCG the painter may be too slow (d2 targets for QEMU are guesses). Mitigation: measure at M2 before any further design; if the guest is the bottleneck, move work to the host (for example, pre-sorted bands).
  8. Chrome changes. Chrome ships every four weeks; flags and protocol details move. Mitigation: pin the tested version (156), run the M1 spike on each update, and keep the engine adapter as the only CDP code.
  9. Extensions diverge from Chrome. Our background is a page, not a service worker; the chrome.* subset is small. Mitigation: explicit error for missing APIs; sample extension tests.
  10. Security of the bridge itself. A bug in the bridge could expose the Mac. Mitigation: no listening port for Chrome, the bridge listens only on the serial or socket channel, prompts for every outward action (e3).

  • Readability.js (Apache-2.0, memory) if used; check the licence file at the time.
  • Site terms. Automated browsing of sites is subject to each site's terms. The test list (browser-test-sites.md) uses public pages and no logins; the harness must not crawl beyond the list, must respect rate limits (one request per site per run), and must not send form data to sites other than the local test server.
  • Downloads and files. Downloads are never run. Dangerous types are refused by default (features section 6).
  • Privacy. The throwaway profile and the store are on the user's Mac, not sent anywhere. The bridge sends no telemetry. The browser's own "About" page says so.
