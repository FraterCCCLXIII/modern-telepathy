Browser v0 for the HolyC desktop

Edited 2026-10-27docs/browser-plan.md

Status: Stage 0 (plan). Branch task/templeos-shell. Scope: a first browser app in the guest, with the host doing all network work.

Architecture#

Three parts. Nothing in the guest touches the network, TLS, or JavaScript.

  1. Host bridge apps/templeos-holyc/scripts/browser-bridge.py (Python standard library only). It connects to the VM's COM1 serial port (TCP, QEMU server socket), waits for GET <url> lines from the guest, fetches the page with urllib (redirects followed, 10 s timeout, 1 MB limit, gzip handled), converts it to KDoc (below), and sends it back. Also a --convert URL mode that prints KDoc to the terminal for testing, and a bench:N URL that returns N bytes of test data for channel measurement.
  2. Document format KDoc: one block per line, ASCII only, produced by the host's reader-mode simplifier.
  3. Guest browser app (desk3/03b-browser.HC, window app id 10, "Browser"). It sends requests and reads replies with a non-blocking state machine polled once per frame, parses KDoc into laid-out runs once per page, and draws only the visible lines.

Wire protocol (over COM1, 8 bits, no flow control)#

Guest to host: - GET <url>\n. The URL is ASCII with no spaces (the guest percent-encodes).

Host to guest: - W\n heartbeat, sent about once a second while a fetch is slow. The guest ignores it and resets its silence timer. - ERR <message>\n on failure (the guest shows the message on an error page). - OK <n> <c>\n then n bytes of KDoc. c is the chunk size: the host sends c bytes, waits for one acknowledgement byte, and repeats (the last chunk may be shorter). Acknowledgement byte: 0x06, written by the guest after every chunk, so the guest is never overrun.

Guest timings: each byte poll is non-blocking. Silence for 3 s during a request is an error ("no answer from the host bridge"). Total time for one request is capped at 30 s. The chunk size and throughput are measured, see the milestones.

Host-to-guest bytes never contain a line the guest could mistake for a request, because the guest only parses lines while it is waiting for a header.

Document format (KDoc v1)#

Plain ASCII lines, LF ends each line. Lines the guest does not know are ignored.

  • URL <final url>: the address after redirects (first line).
  • TITLE <text>: page title (optional).
  • H1 text, H2 text, H3 text: headings.
  • P text: paragraph.
  • LI text: list item (bullet drawn by the guest).
  • Q text: block quote.
  • CODE text: preformatted line (drawn in the small font).
  • HR: horizontal rule.
  • IMG alt text: placeholder box with the alt text (no image decoding in v0).
  • Links inside any text: [[url|link text]]. The URL is absolute, | and ]] never appear in it (percent-encoded), and the link text never contains [ or ].

Reader mode on the host: score candidate containers (Readability-like: each paragraph adds its length times one minus its link density to its parent and grandparent, with a class and id bonus or penalty), choose the best, skip script, style, nav, header, footer, aside, form, button, svg, iframe, noscript, template, and navigation-like classes (navbox, toc, reference, sidebar, ad, comment, share). Entities decoded, whitespace collapsed, curly quotes, dashes and other non-ASCII mapped to ASCII (NFKD, then drop), text capped at about 60 KB.

Guest app#

  • Window 760 by 560 logical, icon: Lucide globe. Toolbar: Back, Forward, Reload buttons, then the URL bar. Page area with a thin scrollbar. Status line at the bottom: the URL being loaded, or the error, plus the time the load took.
  • URL bar: click to focus, ASCII typed in, Backspace, Enter loads (adds https:// when there is a dot and no scheme; text without a dot becomes a DuckDuckGo html search), Escape unfocuses (only while focused, so Escape still quits the desktop otherwise).
  • Links: accent colour with an underline; one hit region per link run; clicking pushes history and navigates.
  • Scrolling: mouse wheel, Up, Down, PageUp, PageDown, Home, End while the browser is in front.
  • History: back and forward (a list of URLs with an index).
  • Layout is cached per page and per scale; drawing walks only the visible lines (binary search on line y).

Milestones and gates#

  • M0 plan: this file committed. Gate: file reviewed in the commit.
  • M1 channel: the guest sends GET and receives a test payload with bench:N at chunk sizes 32, 128 and 512. Gate: a 20 KB payload arrives intact (checksum over the bytes at both ends matches) for each chunk size; throughput in bytes per second is reported for each chunk size. Pass if at least one size reaches 2 KB/s; fail and report otherwise.
  • M2 converter: browser-bridge.py --convert URL prints a sensible KDoc for the five test URLs. Gate: each gives at least 500 bytes of body text (except example.com, which is short), no HTML tags, no non-ASCII, links absolute.
  • M3 app: the Browser window opens from the dock, loads a page from the bridge, shows links, scrolls, goes back and forward, and shows the Loading state while the bridge is slow. Gate: screenshots of the first four test URLs render legibly and clicking one link navigates.
  • M4 polish and verification: the five URLs end to end in the VM, errors (bad URL, no bridge, timeout, unreachable host) show an error page, long pages do not freeze the desktop (the frame time while loading stays under 50 ms), screenshots in apps/templeos-holyc/shots/browser-*.png.

Out of scope for v0#

JavaScript (none, ever in the guest), forms and submitting, cookies and sessions, login, images (placeholders only), CSS (the host's reader mode decides the look), tables as tables (rows become lines), fonts other than the Inter set, text selection, find in page, tabs, bookmarks, persistence, HTTPS certificate checks beyond urllib's defaults (the host does TLS).
