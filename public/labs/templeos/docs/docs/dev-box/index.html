Dev Box: complete software development from the HolyC desktop

Edited 2026-10-27docs/dev-box.md

Status: study, no code. Branch task/templeos-shell. Written 2026-10-27. Read with docs/os-foundation-plan.md, docs/apps/ai-ide.md (2.4 workspace and sandbox), docs/apps/fonts.md, docs/browser-architecture.md (b4 throughput, h5a fonts), apps-host/hub/hostd.py.

Tags: [V] verified on this Mac or in this repo this session. [W] from a web page fetched this session (URL given). [M] from memory or estimate, to verify. Section 11 lists them.

1. The idea in one paragraph#

TempleOS cannot run containers: no Linux kernel, no network stack, no libc. So the desktop is the front end and the work runs in a Linux environment next to it. The guest talks to the host hub (hostd.py), the hub talks to a Linux box, and the box holds the compiler, the language servers, Docker and the repo. The desktop shows a terminal, a file tree, an editor, a containers panel and a preview. The same shape is what VS Code Remote, Zed remote and Codespaces use: the UI is local, the server, the language servers and the terminals are remote [W: code.visualstudio.com/docs/remote/remote-overview; zed.dev/docs/remote-development]. Our "remote" is a VM on the same Mac.

Two facts shape everything. Disk is tight: a Docker Desktop install already holds 24 GB, so a second container runtime must share, not duplicate, its images. And the TempleOS guest is x86_64 under TCG on this arm Mac, so the guest CPU is software-emulated, while a Linux box on the same Mac can be arm64 with hardware acceleration (HVF) at near native speed. That asymmetry is the reason to put the work in the box and keep the guest thin.

Notes on the choices:

  • Apple container (Apache-2.0, "supported on macOS 26", Apple silicon, each container its own lightweight VM [W: github.com/apple/container]) fits this Mac's OS but is not installed and is a v0.x tool [W]. It gives the strongest per-container isolation and no daemon. Treat it as a later backend behind the same docker service interface, not the first.
  • Lima supports mount types reverse-sshfs, 9p and virtiofs; from Lima 1.0 the default is 9p for QEMU and virtiofs for the VZ driver; virtiofs needs macOS 13+ and a guest kernel with CONFIG_VIRTIO_FS [W: lima-vm.io/docs/config/mount]. This Lima's default.yaml ships mounts: [] [V], so a fresh instance exposes no host folder until we list one. That is the right default for us.
  • Colima is Lima with a Docker front; its own default mounts $HOME writable [V colima.yaml comment]. If we use R2 through Colima we must write an explicit mounts: list (workspace only), otherwise a container can read and write the whole home directory including secrets.
  • Podman machine is a Lima-like VM on Apple's hypervisor [M], not installed. Skip.
  • Not rated for the first prototype: a QEMU HVF VM with a hand-built image. It is more controllable but costs a day of image work; Lima gives the same QEMU or VZ with cloud-init for free.

4. Terminal (question 1)#

4.1 Spec from Kosmos OS#

/Users/paulbloch/kosmos-os-frame/src/apps/terminal/TerminalApp.tsx (108 lines [V]) is explicitly "one-shot commands, not a pty": it POSTs a command to /api/exec and lists stdout, stderr and exit code, with arrow-key history. That is the floor for us (a run-a-command panel) and proves the workspace exec path exists. It is not enough for vim, htop or ssh, so the Dev Box needs a real pty.

4.2 Hub service term#

The hub is request/reply, not streaming: one REQ record, one RES record set, the reply chunked at 256 bytes with a one-byte ack per chunk, and a PENDING frame once a second while a slow call runs [V hostd.py docstring]. Records are TAB separated, and esc() drops \r and escapes \t \n \\ [V recs.py], so raw terminal bytes cannot ride in a record. Two consequences:

  1. Output is polled with a long poll: term read id max_bytes wait_ms returns what the pty produced (immediately, or after at most wait_ms), or an empty reply. The hub already sends PENDING for slow calls, so a 200 ms wait costs nothing extra. The guest keeps one read outstanding while a terminal window is focused.
  2. Binary data must be encoded: hex doubles it, base64 adds 33 percent [M]. Section 4.3 avoids the problem.

Ops:

Host side is stdlib Python: pty.fork() or os.openpty() plus subprocess.Popen(..., start_new_session=True), a reader thread feeding a bounded ring buffer (flow control: stop reading the master when the ring holds 64 KB, so the child blocks in write, which is exactly what a real terminal does), fcntl.ioctl(fd, termios.TIOCSWINSZ, struct.pack("HHHH", rows, cols, 0, 0)) for resize, TERM=xterm-256color. Smoke test run here with /bin/echo and /bin/ls in a throwaway directory [V, scratchpad devbox/pty_smoke.py]: echo returned b'hello devbox\r\n', ls -la returned four lines with \r\n line ends (the pty's tty layer adds the CR), and the winsize ioctl succeeded.

The command that open runs is the target: limactl shell devbox (R1), ssh -tt box (R3), docker exec -it c sh (R2), or /bin/echo in the smoke test. One service serves all routes. The hub, not the guest, owns credentials and the allowed target list.

4.3 Where the VT emulation lives#

A. Emulator in HolyC (parse bytes in the guest) B. Emulator in the host (hub keeps the screen model)
Guest code a VT parser plus a cell grid plus a renderer a cell renderer only
Link traffic raw pty bytes (any program, any volume) dirty rows only: text plus attribute runs
Full-screen app (top, vim) every escape sequence crosses the link only the changed rows cross
Aiwnios native pty natural fit not needed
Risk a hostile or noisy program can flood the guest host Python parser must be right; pyte (MIT [M]) exists, but stdlib-only would be about 400 lines [M]

Recommendation: B first, A later. The hub runs a small VT100/xterm model and sends, per poll, a list of changed rows: ROW y text plus ATTR y x0 x1 fg bg flags runs, plus CUR x y visible, plus ALT 0/1. The HolyC side is then a grid renderer that never parses an escape. Scrollback also lives on the host (the guest asks term scroll id offset count). Keys go the other way as bytes: arrows ESC [ A..D (application mode ESC O A when the host model says DECCKM is set), ctrl-letter as 1..26, F1..F4 as ESC O P..S, F5.. as ESC [ 15 ~ etc., bracketed paste as ESC [ 200 ~ ... ESC [ 201 ~ when the program enabled mode 2004. The host model also answers queries (cursor position ESC [ 6 n, device attributes) so vim and htop do not hang waiting for a reply.

Sequences needed for bash, vim, htop, git, ssh [M, to confirm with a recorded session]: C0 controls (BS, HT, LF, CR, BEL), CSI cursor moves (A B C D H f G d), erase (J K), insert/delete lines and chars (L M @ P), scroll region (r), SGR (0 1 3 4 7 22 27 30..37 38;5;n 38;2;r;g;b 39 40..47 48;5;n 49 90..97 100..107), save/restore cursor (7 8), modes (?1 application cursor, ?7 autowrap, ?25 cursor visible, ?1049 alternate screen, ?2004 bracketed paste, ?1000/1006 mouse optional), ESC c reset, titles (OSC 0, ignored), UTF-8 box drawing (needs glyphs, see 4.4). Acceptance is a recorded corpus: record vim, top, htop, git log --graph, ssh sessions with script, replay into the model, compare the final grid with a known-good emulator such as tmux's capture-pane [M].

4.4 Monospace face and rendering cost#

Our faces are Inter ASCII, proportional, at four sizes [V fonts.md]; browser plan h5a stage A+ already names a monospace bitmap face for pre and code (candidates Iosevka or JetBrains Mono, OFL, to check [V browser-architecture.md line 555]). The terminal needs the same asset plus box-drawing and block characters (U+2500..257F, 2580..259F, about 128 glyphs [M]); those can be drawn as lines and rectangles in code, not stored. Use one face at 8x16 and a 2x variant. Cell size 8x16 makes 120x40 equal to 960x640 pixels. Fonts are a host job (fonts.md rule 1), so the face is produced by gen-font.py style tooling and ships as a bitmap atlas; the font manager plan covers licences.

Rendering estimates [M, to measure at gate G4]:

  • Full grid: 4,800 cells x 128 pixels = 614,000 pixels per full repaint. At 60 Hz that is 37 million pixel writes per second. In HolyC under QEMU TCG (x86 emulated on arm, roughly 5 to 20 times slower than native [M]) a full 60 Hz repaint is not realistic.
  • Dirty rows only: a typical keystroke or a top refresh changes 1 to 40 rows. At 40 rows it is the same 614k pixels once per refresh, 1 to 2 per second for top; under 10 repaints per second is fine. Draw only the cells in rows the hub reports; keep the previous frame in the window buffer.
  • Therefore: the terminal is event driven, not 60 Hz. The target is under 50 ms from reply to pixels for a one-row change.
  • Aiwnios (native arm, per the build in aiwnios/) removes the emulation penalty; full repaint at 60 Hz of 614k pixels is a normal blit there [M]. It can also call a registered native function for a pty (KsExec exists [V README]) and skip the hub for the terminal entirely; that is the better Aiwnios path, with the same approval prompt.

4.5 Bandwidth#

Link: about 17 KB/s measured end to end on QEMU serial (20,000-byte bench, 1,167 ms at chunk 128 and 1,236 ms at chunk 512, checksum ok [V browser-painter-status.md line 11]). The earlier 47 KB/s figure was not reproduced [V browser-architecture.md b4]. Use 16 KB/s.

Traffic Bytes Time at 16 KB/s
One typed key and its echo (B) request about 60 bytes with framing and CRC [M], reply about 60 about 8 ms plus host latency [M]
ls of 40 lines, 80 bytes each about 3.2 KB 0.2 s
top refresh, 40 rows of text, 4,800 bytes plus attributes about 1 KB about 6 KB 0.4 s every 3 s: 12 percent of the link
vim scroll one page (full 120x40 redraw) about 6 KB 0.4 s
cat of a 1 MB file raw 1 MB 65 s (B drops what scrolls past; keep a cap)
docker build log flood MB cap the stream: send the last screen only, keep the log host-side, fetch on demand

Conclusion: interactive typing and full-screen programs fit comfortably; bulk output must be throttled in the hub (coalesce to at most 10 screen updates per second, drop intermediate frames). The channel is the limit only for output floods, not for editing.

5. Files, workspace and git (question 2)#

  • Workspace model. One host folder, e.g. ~/devbox/work/<project>, is the single shared directory. Lima mounts it into the box as /work over virtiofs (VZ) or 9p (QEMU); nothing else is mounted [W lima mount doc; V default mounts: []]. This is the ai-ide.md 2.4 rule ("the bridge mounts it as the only writable root") with a VM boundary added.
  • File tree and search. Services files list/stat/read/write run on the host against the shared folder (fast, no VM round trip) with the ai-ide.md rule that paths resolving outside the root are refused; grep runs inside the box (rg) so it sees the same view the compiler sees.
  • Git. Status and diff run on the host (git -C) for speed; commits and anything that needs hooks or the toolchain run in the box. Push is never done by the desktop (ai-ide.md policy). Credentials stay on the host (section 9).
  • File watching. The hub watches with polling on the host side (os.scandir mtimes every second [M]) or fswatch if installed; virtiofs does not propagate inotify from host edits to the guest on all kernels [M], so tools that watch inside the box (webpack, cargo-watch) may need polling mode; flag it in templates.
  • AI IDE reuse. The agent's tools in ai-ide.md (read, edit, grep, shell, tests) map to files, git, term/exec. The agent shell runs in the box, never on the Mac, unless the user approves; this implements the "Docker or Lima sandbox" setting already in the plan and makes it the default instead of an option.

6. Containers panel (question 3)#

Source of truth is the Docker Engine API on the box's socket, not parsing docker ps text. Inside Lima/Colima the socket is forwarded to the host (Colima writes ~/.colima/<profile>/docker.sock [M]); the hub speaks HTTP over a unix socket with http.client (stdlib). Read-only endpoints: GET /containers/json?all=1, /images/json, /volumes, /containers/{id}/logs?tail=200, /networks, /containers/{id}/stats?stream=false.

Action Approval
list containers, images, volumes, ports, logs, stats none (read-only default)
start, stop, restart a container the Dev Box created one approval per session per scope docker:control
exec shell (term open with docker exec -it) scope term:shell
compose up/down in the workspace scope docker:compose:<project>; shows the compose file's images, ports and volumes in the prompt
image pull, build with network each pull: prompt names the image, tag and digest if pinned; pulls are the supply-chain gate (section 9)
run with --privileged, host network, docker.sock mount, or bind mount outside /work denied, no override in v1
rm, prune, volume delete per-action prompt with the object name

The hub must not hand the guest a raw socket: the Engine API is root in the box. The docker service exposes only the whitelisted operations above and validates the JSON body for creates (reject HostConfig.Binds outside /work, Privileged, NetworkMode: host, CapAdd, Devices).

The panel is a HolyC table (Name, Image, State, Ports, CPU/Mem) refreshed by docker list every 3 s while visible, plus a log tail view reusing the terminal grid renderer in read-only mode.

7. Ports and preview (question 4)#

  • Publish with -p 127.0.0.1:HOST:CONT in the box and let Lima forward guest loopback ports to host loopback (Lima forwards listening ports automatically [M]); never bind 0.0.0.0, so nothing is reachable from the LAN. The hub's ports service lists forwards (from docker ps ports and ss -ltn in the box) and only the user-approved ones are opened in the Browser app.
  • The Browser app already renders a host Chromium route (browser-architecture); a http://localhost:PORT URL is allowed only for ports in the Dev Box's forward list, and the browser's usual rule (no localhost from arbitrary pages) stays. A page loaded from a dev server must not be able to reach other local services: use a separate browser profile with the loopback allow-list.
  • HMR / WebSocket. Vite, webpack and Next dev servers use a WebSocket back to the page's origin. Chromium on the host handles it natively since the dev server is on the same loopback; the guest only sees painted bands. The costly part is repainting over a 16 KB/s link, so preview is a screenshot/band stream, not a live pixel mirror: a hot reload that changes a region sends only that region.
  • Security. Loopback only; dev servers often disable auth and expose source maps, so the origin must never carry a cookie or token of the user's real sessions (separate profile); Host header checks in dev servers (Vite's allowed hosts [M]) mean we use localhost, not an IP.

8. Language tooling (question 5)#

  • LSP is JSON-RPC over stdio with Content-Length framing [M]; DAP has the same base framing, with single-session (stdio) and multi-session (port) modes, and requests initialize, launch/attach, setBreakpoints, continue/next/stepIn/stepOut, threads, stackTrace, scopes, variables [W: microsoft.github.io/debug-adapter-protocol/overview]. Both servers run in the box (rust-analyzer, gopls, pyright, typescript-language-server, lldb-dap or debugpy, delve).
  • Our editor is the client. The host service lsp starts a server in the box through term-like exec (no pty, plain pipes), owns the JSON framing, and gives the guest a reduced set: didOpen/didChange (full text or ranges), diagnostics (publishDiagnostics flattened to DIAG file line col sev msg), hover text, completion list (top 20), go-to-definition (file and position), symbols. Semantic tokens and code actions come later. That keeps JSON parsing out of HolyC.
  • DAP is the same pattern: dap start, breakpoints set from the editor gutter, stopped events become a status line plus stack and variables lists. A terminal debugger (gdb, lldb, pdb) in the Dev Box terminal is the day-one fallback.
  • Test and build panels. exec (no pty) with line-parsed output (path:line:col: message) produces a clickable problems list; cargo test, go test, pytest, npm test all fit.
  • devcontainer.json. The spec's main properties: image or build.dockerfile, features (ids like ghcr.io/devcontainers/features/node:1), forwardPorts, postCreateCommand (string, array or object of parallel commands), mounts, and tool-specific customizations [W: containers.dev/implementors/spec]. Support a subset: image, build, features (from an allow-list of pinned ids), forwardPorts, postCreateCommand, remoteUser, containerEnv. mounts entries outside /work are rejected. Implementation is the reference CLI (@devcontainers/cli [M], Node) run in the box, not our own parser.
  • Not planned: running VS Code extensions or code-server inside our window. code-server in a host browser stays an escape hatch the user can open in the Browser app (it is a web page; not installed here [V]).

10. Developer experience (question 7)#

  • One command. tools/devbox up [template] (new shell script in apps-host/, or hostd.py --call devbox up): creates the Lima instance from a template yaml, mounts the workspace, waits for ssh, installs nothing beyond the template, prints the status. devbox down, reset, shell, ps, snapshot name.
  • Templates (each a Lima yaml plus a provision script, all versions pinned): rust (rustup stable, rust-analyzer, lldb-dap), node (node LTS, pnpm, typescript-language-server), python (uv, pyright, debugpy), go (go, gopls, delve), holyc (a box that holds the HolyC cross-compile and the Aiwnios arm build tools plus our own regression scripts, so the desktop's own source builds from inside the Dev Box), and docker (the Lima docker.yaml template [V present]).
  • Persistence. Instance disk persists across devbox down; /work is on the host and survives reset.
  • Performance numbers I can justify. I did not run a benchmark here (no VM may be started without approval). From sources: HVF and the VZ driver give near-native CPU in the guest [M]; QEMU with TCG is software emulation and is slow (the TempleOS processes above run on TCG [V]). Colima's own config says virtiofs "is the fastest of the options" for vz and 9p is recommended for qemu [V colima.yaml comments]. Lima 1.0 made 9p the QEMU default, virtiofs the VZ default [W]. The ratio virtiofs versus 9p versus sshfs is therefore to be measured: gate G7 runs git status and npm install on a fixed repo under each mount type and records seconds. Do not quote a multiplier until then.
  • Cost on this Mac. RAM: default 6 GiB reserved while running, none when stopped (16 percent of 36 GiB). Disk: base Debian image about 0.3 to 0.5 GB plus tools 1 to 3 GB [M]; with 24 GiB free, a 16 GiB cap is the sane limit. Docker Desktop's 24 GB already held would be freed only if the user removes it, which is the user's choice.

11. What HolyC land would still lack (question 8)#

  • GUI debugging and visual tools: a Linux GUI app inside the box cannot be shown (no X/Wayland path to the 16 KB/s link) beyond screenshots; browser devtools for a web app run in the host Chromium, not in the desktop (browser plan DevTools mapping).
  • Mobile emulators: the Android emulator and iOS Simulator are macOS-host programs with their own windows; not in a HolyC window. Command-line control (xcrun simctl) is possible through exec with approval; display is not.
  • GPU work (CUDA, Metal, WebGPU): the VM sees at most a virtio GPU in software [V os-foundation-plan.md line 71 says the QEMU build has no GL]; run GPU jobs on the host.
  • Rich editor features (refactors, extension marketplace, notebooks) need work in HolyC or are out of scope.
  • Large-output tools (full docker build logs, huge test runs) are bound by 16 KB/s unless summarised on the host.
  • Latency: every keystroke is a hub round trip; fine for typing, felt in vim at 20 ms [M].

12. Linux as the base OS instead (question 9)#

os-foundation-plan.md weighs a Linux base for the whole desktop (Wayland compositor, Electron and Tauri apps). If Linux were the base, containers, ptys, LSP and the GUI toolchain are all native, the serial bottleneck disappears and 16 KB/s stops mattering. The cost is the HolyC desktop's identity: TempleOS would become one app. The Dev Box gets about 80 percent of that value for the apps that matter to developers (terminal, files, git, containers, LSP) and keeps the HolyC desktop as the product. It does not give a GPU, a real browser engine in the guest, or a high-bandwidth display.

Recommendation. Take R1 as the product: a Lima arm64 VM (VZ driver, virtiofs, workspace-only mount, Docker or Podman inside), the Docker panel reading the Engine API from it. Use R2 only as a fallback backend when the user already runs Docker Desktop or OrbStack (read-only by default, explicit mounts), R3 as the same term service with an ssh target, and R4 unchanged for HolyC projects. Do not make Linux the base OS for this goal: decide that on the other merits in os-foundation-plan.md. If the Aiwnios build becomes the main path, add the native pty route (KsExec) for the terminal and keep the hub for everything else.

13. One-day prototype#

Goal: a shell of a Dev Box in a HolyC window, with a containers stub. No installs. Starting a VM or container needs the user's approval; steps that need it are marked (approval).

Pieces:

  1. apps-host/hub/svc_term.py (new, ~200 lines, stdlib): registers term; ops open/write/read/resize/close; the first open raises NeedApproval("term:shell", "Open a shell in the Dev Box: <cmd>") using the existing token flow; allowed targets come from config.json (devbox_shell: a list like ["limactl","shell","devbox"]); default for tests ["/bin/sh"] restricted to a temp dir in tests. A host-side VT model (vt.py, ~300 lines) turning bytes into dirty rows (option B).
  2. apps-host/hub/svc_docker.py (new stub): list reading GET /containers/json?all=1 over the unix socket from config.json docker_sock; read-only; returns CTR id name image state ports.
  3. desk3/12-term.HC (new): a window with an 8x16 grid, long-poll read loop, key mapping, resize on window size change; and a containers table window from docker list.

Gates (each with a command):

Gate Check Pass
G0 python3 -I apps-host/hub/tests/test_term.py (host only; the pty runs /bin/echo and /bin/ls in a temp dir, like the smoke test) echo and ls output returned; resize ioctl accepted; close kills the child
G1 hostd.py --call term open /tmp/x 120 40 /bin/echo hi, repeat with the token first call APPROVE, second TERM; no shell without token
G2 (approval) limactl create --name devbox template://docker then limactl start devbox (the user may instead choose the existing Colima default profile, colima start, after we set an explicit mounts: list) limactl shell devbox uname -m prints aarch64
G3 guest types echo hi in the window "hi" shows within 100 ms of Enter on the bench channel
G4 guest runs ls /work listing correct, scripted compare with ls on the host
G5 top -b -n 1 (batch mode) then top and vim -u NONE vim: type text, :wq, the file has the text; top rows align under an 8x16 grid; screenshots in shots/; a recorded-session replay test compares the host model to tmux capture-pane for 5 recordings
G6 resize the window from 80x24 to 120x40 stty size in the shell prints 40 120 and vim relayouts
G7 docker list against the box's socket containers panel shows the same rows as docker ps -a in the box; no write op reachable
G8 the mount list check: limactl shell devbox ls /Users/paulbloch fails: only /work is mounted

Timing: G0 and G1 two hours, VT model three, HolyC window three, gates the rest. Risk: the VT model and the key mapping, not the pty.

14. One-week MVP#

Terminal with scrollback and 256 colours, files service and tree, git status/diff, devbox up/down/reset with the rust and node templates, containers panel with start/stop/logs/exec and approvals, ports list and one forwarded preview in the Browser app, LSP for one language with diagnostics shown in the editor, egress proxy with the allow-list and prompts, resource meter (RAM, disk), the mount-type benchmark (G7 of section 10) recorded.

15. Three-month target#

All five templates; DAP for two languages; devcontainer.json subset with features allow-list; compose panel with the spec-validating create filter; snapshots in the UI; Apple container backend behind the same docker service if it is mature by then; Aiwnios native pty path; agent actions running only in the box with the audit log; a Dev Box for the HolyC project itself (build the desktop from inside the box, run its test suite there).

Disk fills (24 GiB free) high high 16 GiB cap, meter, prune prompt, do not keep two runtimes

Lima or Apple tool changes (v0.x container) medium low thin docker service interface, backend per route

virtiofs inotify gaps medium low polling watchers in templates
Keymap/escape-sequence gaps high low recorded-session corpus test

17. Verified versus memory#

Verified here: macOS 27.0 arm64, 14 CPUs, 36 GiB, 24 GiB free; Lima 2.1.4 with no instances and mounts: [] in default.yaml; Colima 0.10.3 profile stopped (vz, virtiofs, rosetta, $HOME writable comment); Docker client 29.1.5 and Docker.app with no daemon running; QEMU 11.0.2 listing hvf and tcg; absence of container, OrbStack, Podman, nerdctl, devcontainer, code-server; Docker Desktop data 24 GB; two TempleOS TCG QEMU processes; hub protocol (request/reply, 256-byte chunks with acks, PENDING, record escaping, approval tokens); Kosmos OS Terminal is one-shot exec; measured 17 KB/s serial bench in the repo; pty smoke test (echo, ls, TIOCSWINSZ).

From the web this session: Docker plan prices; OrbStack free personal and $8 Pro; Apple container requirements and Apache-2.0; Lima mount types and defaults; Colima MIT and vz options; devcontainer properties; DAP overview; VS Code Remote and Zed remote architecture.

Memory or estimate (verify before relying on it): Lima and Podman licences, Podman machine internals, Colima socket path, Lima auto port forwarding, APFS clone snapshots, pyte, escape-sequence list, TCG slowdown factor, render timings, request sizes and key latency, VM image and tool sizes, nftables egress, @devcontainers/cli, virtiofs inotify behaviour, LSP framing, font candidates, and every other figure tagged [M] above.

Not attempted: starting any VM or container, pulling images, any benchmark of mounts or HVF versus TCG. WebSearch was not used; only the fetched pages above.

18. Approvals needed from the user#

  1. Permission to create and start a Lima instance (limactl create, limactl start): downloads an arm64 image of a few hundred MB and writes up to 16 GiB under ~/.devbox.
  2. Or permission to start the existing Colima default profile after we write an explicit mounts: list (the default would expose $HOME writable).
  3. Disk: confirm a 16 GiB budget with 24 GiB free, or free space (Docker Desktop holds 24 GB).
  4. New files svc_term.py, svc_docker.py, vt.py, desk3/12-term.HC in the shared tree (other agents are editing it), and a devbox_shell entry in config.json.
  5. A monospace font licence choice (OFL candidates) for the terminal face.
  6. Go-ahead before any image pull or compose run in gates.
