Web-technology apps on the HolyC desktop: design study

Edited 2026-10-27docs/web-apps.md

Written 2026-10-27, branch task/templeos-shell. Study, not an implementation: the only code run is scratch (listed in section 13). Tags: [R] run or measured this session, [S] read in a file (named), [M] memory or inference, to be checked before it is relied on. Kosmos OS (/Users/paulbloch/kosmos-os-frame) has no licence file: its shapes are cited as spec, nothing is copied.

1. Answer#

Build one app contract and three renderers behind it.

  1. Contract (build first, shared): a kind: "web" manifest, a default-deny window.kosmos API, theme tokens, one permission store on the host. This is almost the Kosmos OS "Tier 3 code app" (sandboxed iframe, postMessage SDK, --os-* tokens) [S: app-platform-plan.md, AppHost.tsx, packages/app-sdk], so web apps written for Kosmos OS port with a thin shim.
  2. A, host Chromium (first, for compatibility): the existing browser/appd route. Any framework works. Content apps get display-list bands, creative apps and games get tiles.
  3. C, host-side JS plus declarative tree (second, for system apps): JS runs in Node or a worker on the host; the guest interprets an indented-record tree. This is the native-feeling, cheap-in-memory track, and the right target for OpenUI Lang apps.
  4. B, JS in the guest, Aiwnios only, last, and narrowed: link QuickJS to run the reconciler for C in-process. Do not build a native HTML/CSS engine. The evidence below overturns that half of B.
  5. D (compile to HolyC): rejected, except "D-lite": JSX compiled to static tree literals.

Caveat: os-foundation-plan.md [S] proposes Linux with our own compositor as the base. If that wins, A's host pieces (runner, manifest, permissions, kit) carry over and the guest-painting parts fall away.

3. The shared contract#

3.1 Manifest, kind: "web"#

It extends applications-folder.md section 4 (a new entry.kind next to holyc/templeos/host) and manifest.py (electron). Nothing in the guest parses JSON; gen-apps.py writes the table.

Field Kosmos OS manifest [S: shared/manifest.ts] PWA manifest [M] Tauri [M]
id, name, version, icon same; Lucide icon name name, short_name, icons[] identifier, productName, version
entry url / bundle / openui start_url, scope build.frontendDist, devUrl
window not in manifest (setWindowGeometry aspect only) display app.windows[] {title,width,height,resizable}
permissions intent, contract, storage own, shell notify/windows/clipboard/agent none (browser prompts) capabilities/*.json with core:*, fs:allow-read
theme --os-* tokens pushed by the host theme_color, background_color none

Rule for importing: a PWA manifest becomes entry.start/window/icon; a Tauri tauri.conf.json becomes window and a proposed permission list that the user must still approve. Permissions are never inferred silently.

3.2 window.kosmos#

Shape mirrors the Kosmos OS SDK [S: index.d.ts] so those apps run with a shim: intents.invoke, storage.query/execute, shell.notify/askAgent/setWindowGeometry/toolbar, events.on, theme.current/onChange. Additions for the desk: files.pick() (host dialog, returns a handle), clipboard.read/write, window.setTitle/close/requestAttention, agent.registerTool.

Transport: Runtime.addBinding("__ks_send") plus a script on Page.addScriptToEvaluateOnNewDocument that defines a frozen window.kosmos. The host replies by Runtime.evaluate("kosmos._done(id,ok,value)"). Identity comes from the CDP session id that carried the call, never from a field the page sets. [R] I ran this: a denied kosmos.call('fs.read') rejected with "denied: needs host:files:r", an allowed notify resolved, 51 calls were audited, in-page round trip p50 0.1 ms (Python handler, local pipe), and assigning kosmos.call = 1 did not override it.

Default deny: every method maps to one permission key (same vocabulary as applications-folder.md section 7); an ungranted key returns a rejection and writes an audit line; "ask" keys open a guest prompt (Allow once / Allow / Deny) whose answer is stored only on the host. The guest never stores a grant and never sees a token.

3.3 Theme#

The desk has five styles and 16 palette slots (ks_pal) [S: 01-porting-method.md 4.5]. Three channels, all host-driven:

  1. CSS custom properties injected at document start: --ks-bg --ks-ink --ks-accent --ks-rad --ks-pad --ks-font-scale, and <html data-ks-style="macos|win11|kosmica|longformer-light|longformer-dark">. [R] injection worked (body computed to the injected colour).
  2. Emulation.setEmulatedMedia(prefers-color-scheme) follows the desk's light/dark. [R] flipping it changed all 3 bands of the test page (checked by band hash, not by eye).
  3. kosmos-ui.css plus web components (<ks-button>, <ks-tabs>...) that read only those variables, so the same markup looks right in all five styles. The apps may ignore the kit; they then look foreign (the Kosmos OS plan accepts the same trade).

Fidelity limit [S: browser-architecture.md c4]: in the DLIST route glyphs are the desk's bitmap faces, not the app's font. The kit should therefore set font-family to a face whose metrics the host knows, or line breaks may differ by a pixel or two.

4. Architecture A: host Chromium renders, guest paints#

Fidelity: layout is Chrome's (flex, grid, tables exact); glyphs, shadows, gradients and rotation are approximate or tiles [S]. React, Svelte, Preact, web components all work because Chrome runs them.

Measured here [R] (Chrome 156, Python encoder, 900x600 viewport, loopback server, throwaway profile, M-series Mac):

Measure Vanilla todo React 19 todo (195 KB min, 61 KB gzip) React + 200-row table
Navigate to settled 0.59 s 0.60 s 0.54 s
DLIST items / ops 22 22 822 (808 TEXT)
DLIST bytes, all bands 931 B 745 B 27.3 KB (20 bands)
First-paint bytes (visible bands) 931 B 745 B 3.6 KB
Capture + encode, steady p50 0.7 + 0.5 ms 0.7 + 0.5 ms 18.6 + 21.4 ms
  • Type text and click Add, host side, to a new DLIST: p50 17 ms, p95 21.5 ms; changed bands cost p50 1.4 KB. At the reported 47 KB/s serial [S, unreproduced] that is about 30 ms more; on an Aiwnios socket it is negligible. The guest half (paint) is not measured.
  • Resize 900x600 to 600x400 to a new DLIST: 3.9 ms host-side.
  • Pixels instead: screenshot 600x400 PNG 18.9 KB (35 ms), 900x600 JPEG q60 18.8 KB (28 ms) for this near-empty page; raw RGB565 900x600 is 1.08 MB, 23 s at 47 KB/s. The guest has no JPEG decoder, so tiles use the palette/RLE encodings already in stream.py, dirty rectangles only.
  • Memory: physical footprint (macOS footprint) of the Chrome tree rose 647 MB for 5 extra app tabs, each in its own incognito context (about 129 MB each, 16 extra processes), on top of an 810 MB tree with no app open. One shared context was not measured; it should cost less but weakens isolation.
  • Trap found: the second tab I opened ignored input for about 5 s per click (p50 5069 ms) because it was not the front target. Calling Page.bringToFront and Emulation.setFocusEmulationEnabled fixed it (17 ms). The runner must front the focused app's target and emulate focus on every window focus change.

How the awkward cases behave (mechanisms from browser-architecture.md and CDP, [M] for the CDP method names unless noted):

Area Behaviour
Resize, DPI guest RESIZE (100 ms debounce) to Emulation.setDeviceMetricsOverride; stream.py uses DSF 1 so surface px equal CSS px [S]
Scrolling root scroll local; nested containers cost a round trip [S]
Text, IME key/char events to Chrome; committed IME text via Input.insertText; inline composition preview is a gap
Clipboard kosmos.clipboard with a prompt, through the channel

Audio, video, canvas no guest audio; video and canvas as tiles (video 2-5 fps, canvas on change, ~100-200 ms, estimate)

Cost: the engine is installed on the host, not bundled (licensing and size) [S]. Memory scales with Chrome, not with the guest. Idle apps should be frozen (Page.setWebLifecycleState [M]) and their processes discarded after a timeout.

5. Architecture B: JavaScript engine inside the desktop#

x86 TempleOS. Not impossible, but not worth it. engine-on-templeos.md [S] proved a freestanding Rust blob loads as a .BIN and matches host hashes, so a C engine behind a libc shim (memcpy/malloc/math, the shim listed in holyc-improvement-analysis.md) is conceivable [M]. QuickJS has no JIT, runs on TCG emulation, and is about 6x slower than V8 even natively (below); I estimate 20-100x slower than the host under TCG [M, unmeasured]. What survives on x86 is therefore: the tree interpreter (C), host-side JS, and display-list/tile rendering (A). No JS in the guest.

Aiwnios. Feasible and cheap to start. Natives are registered by PrsBindCSymbol [S]. QuickJS: MIT licence [S: brew info quickjs], version 2026-06-04 is installed here, libquickjs.a is 1.0 MB with symbols [R]. quickjs-ng, Duktape, Hermes and Boa are alternatives, also permissively licensed [M].

Speed [R], same reconciler script (render + diff, one list row changed): Node 22 0.04 / 0.55 / 2.9 ms; QuickJS 0.11 / 3.4 / 17.4 ms for 5 / 200 / 1000 rows. QuickJS is about 6x slower than V8 but is fine at 200 rows and poor at 1000. Not measured: React itself under QuickJS (needs a DOM).

Native HTML/CSS subset. What a todo app needs: DOM (createElement, appendChild, attributes, classList, events with bubbling, innerHTML), a CSS cascade (selectors, specificity, custom properties, calc), block/inline/flex layout, text wrapping, borders/radius, images, form controls, timers, fetch. Real frameworks add MutationObserver, getBoundingClientRect, requestAnimationFrame. Ideas to borrow, not code: litehtml (BSD-3 [M]; CSS 2.1 centric, flex partial [M]), Taffy (MIT [M], Rust, flexbox/grid, layout only), Yoga (MIT [M]). Estimate [M]: 3-6 person-months to run a Preact todo app acceptably, then permanent compatibility debt. Chrome gives all of it for 0 lines; the only gain is independence from the host, which hostd already forgoes (secrets and services live there).

Verdict: B-lite: QuickJS in Aiwnios running the C reconciler, so a tree app can run without the host's Node. Defer until C exists.

6. Architecture C: host JS, declarative tree#

This is Elm's loop (model, view, messages) with React Native's split (JS thread builds a shadow tree, the native side renders and sends events) [M]. It differs from Flutter, which owns every pixel; our guest renders with its own widgets, so theme and accessibility come free. The wire format already exists on paper: TREE, SET, EV, NOTIFY over the hostd frame [S: 01-porting-method.md 3.3, 4.1, 4.6].

Measured [R] (scratch reconciler, one tree vocabulary row/col/text/button/check/list):

Rows Nodes Full tree Patch: toggle one check Patch: append a row
5 38 564 B 20 B 95 B
200 1208 20.1 KB 20 B 107 B
1000 6008 102.5 KB 20 B 113 B

Compare the same todo in A: 745 B to 27 KB per first paint and about 1.4 KB per change. C wins on bytes by 10-70x for updates, and needs no Chrome process for rendering (memory per app: a Node worker, tens of MB [M]). The limits: the pool is 512 nodes, so lists need a virtual list node (host sends only the visible window); layout is the row/col/gap/pad/fill subset, no wrap, grid or absolute positioning [S].

Relation to Kosmos OS OpenUI Lang [S: src/apps/generator, appview, node_modules/@openuidev]. Generative apps are text programs of assignments (root = Card([hdr]), hdr = CardHeader("Title","Sub")) with positional component calls and actions such as @ToAssistant("Submit"). The library (react-ui genui-lib, about 40 components) includes Accordion, Button, Callout, Card, Carousel, Charts, CodeBlock, DatePicker, Form, Image, Input, Modal, Select, Slider, Stack, Steps, Table, Tabs, Tag, TextArea, TextContent. Persisted apps add $state, SQL-backed Query bindings and declared action intents (tier 1-2 in app-platform-plan.md). The packages are MIT [S]. Mapping: OpenUI is a front end that compiles to the same tree (Card to card, Stack to row/col, TextContent to text, Button to button, Form to form, Table to list/table, Charts to chart, Modal to dialog). So C has two front ends over one IR: a React-style renderer for hand-written apps and an OpenUI Lang parser for agent-made ones. Actions become EV messages, then intents through the same grant table.

kosmos-ui contents (one vocabulary, two renderers: tree node in C, web component in A): layout (row, col, card, split, scroll, tabs, sidebar, grid-lite); controls (button, toggle, check, radio, slider, select, input, textarea, date); display (text, markdown-lite, image, icon, tag, progress, metric, table, virtual list, line/bar chart, code block); overlays (dialog, menu, toast, tooltip); system (menu-bar items, toolbar, file dialog, notification).

Costs [M]: interpreter v0 M, v1 M (text field, scroll list), React-style custom renderer S-M (react-reconciler is MIT [M]; I did not try it), OpenUI front end M. Text fields and the font service (P2, P5 in the porting plan) gate real apps.

7. Architecture D: compile-time to HolyC#

Compile web components or restricted TSX to HolyC at build time. Too ambitious for general code: HolyC has no closures, no managed strings or arrays, F64 is x87 on x86 and IEEE on Aiwnios (parity differs) [S: aiwnios README], and the Aiwnios dialect has six documented traps. What is worth keeping is D-lite: JSX with static structure compiles to tree literals plus a handler table, so a purely declarative app needs no JS at runtime. That falls out of C almost free, and runs on x86 with no host JS (it still needs the host for services).

10. Security#

  • Origin and storage. One Chrome context per app, a distinct origin per app id, disposed on close. Memory cost above.
  • No ports for assets. Prefer serving the bundle through Fetch.enable/Fetch.fulfillRequest under https://<appid>.kosmos.invalid/ [M]: no listening socket, and the same hook is the network allowlist for net: permissions (everything else fails). If a loopback server is used (the day-one prototype does), bind 127.0.0.1 on an ephemeral port, serve only the bundle, check Host, reject ... The browser design already forbids --remote-debugging-port [S].
  • CSP injected by the host: default-src 'self'; script-src 'self'; connect-src limited to the manifest's net: list; no inline script unless the manifest asks and the user approves.
  • Guest holds nothing. No tokens, cookies, keys, passwords [S: browser-architecture.md e2]. Grants live in approvals.json on the host [S: perms.py]; the guest only draws prompts. A hostile guest can ask for a token and replay it; the hub says so itself [S: hostd.py], so hostd, not the prompt, is the boundary.
  • Process. appd already strips the environment, fixes profile and download dirs, and offers a sandbox-exec profile [S]. Chrome's renderer sandbox stays on (--no-sandbox never used).
  • Supply chain. kosmos-app pack takes a built dist/, refuses install scripts, records SHA-256 of every file, and signs (Ed25519, per applications-folder section 8). No remote script at runtime (CSP). Lockfile and SBOM are packaged, not trusted. Unsigned apps need an explicit prompt.
  • Agent tools bind to intents or fixed queries, never app code [S: shared/manifest.ts].

11. Packaging, distribution, developer experience#

  • Package: a folder or .ksapp zip: manifest.json, dist/, icons, optional sw.js. Offline: the bundle is local, so a service worker is only needed for the app's own data caching. Do not register service workers by default (they add a background process); allow offline: "sw" explicitly. Updates: compare semver, re-prompt only for new permission keys [S: applications-folder 8]. Remote start URL: allowed as entry.url, flagged "not packaged", needs net: for its origin.
  • CLI kosmos-app: init (template for vanilla, Preact, Svelte; kosmos-ui preinstalled), dev (runs the user's Vite on loopback and opens it in a desk window with HMR; the dev server is the only time a loopback port serves app code), check (manifest and permission lint), pack, install, run.
  • DevTools: the host already owns each app's CDP pipe. The guest DevTools app (DEVT messages, panels to CDP domains: Elements, Console, Network, Application) [S: browser-architecture.md f] attaches to the app's target, with Cookie/Authorization redacted. Developers can also use real DevTools in dev mode through a token-guarded loopback socket, off by default.
