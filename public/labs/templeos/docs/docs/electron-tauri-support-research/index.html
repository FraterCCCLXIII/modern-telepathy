Running Electron and Tauri apps inside the TempleOS desktop: research and route

Edited 2026-10-27docs/electron-tauri-support-research.md

Date 2026-10-27. Research only: nothing was built, launched, installed or committed. The only commands run were read-only queries (qemu-system-x86_64 -device help, -machine pc,help, -object ...,help, uname, sw_vers, sed, grep). Paths are relative to apps/templeos-holyc/ unless absolute. Web pages were accessed 2026-10-27.

Evidence labels used on every claim: [V] verified here (read in a local file, or a command run on this Mac), [D] reported by documentation I fetched (URL given), [S] reported by a search result snippet only, [U] unverified (from general knowledge or inference; treat as a hypothesis to test).

0. Summary#

  1. The previous plan's transport is dead on this machine. ivshmem-plain and ivshmem-doorbell do not exist in the Homebrew QEMU 11.0.2 on this Apple Silicon Mac: -device ivshmem-plain,help answers "Device 'ivshmem-plain' not found" [V]. QEMU's own page says "On Linux hosts, a shared memory device is available" and documents only Linux setups [D] (https://www.qemu.org/docs/master/system/devices/ivshmem.html). The same QEMU does ship memory-backend-file with share= and mem-path= and the pc machine accepts memory-backend= (use a file as the guest's main RAM) [V]. So the best candidate transport is guest main RAM backed by a shared file that a host process also maps ("ramshm"). Whether that works on macOS under TCG is the first thing to prove [U]; memory-backend-file has compiled on macOS since a 2018 patch [S].
  2. Source of pixels is replaceable; build the guest side once. Whatever captures the app (ScreenCaptureKit, Chromium DevTools screencast, an Xpra client in a Linux container), the guest only needs "a surface in shared RAM, a list of changed rectangles, and an event channel back". Build that guest contract first and keep capture behind a host "surface provider" interface.
  3. Recommended route: a Swift host daemon captures real macOS app windows with ScreenCaptureKit (works for Electron and Tauri/WKWebView alike, no app changes), writes BGRA surfaces plus dirty rectangles into shared RAM, and injects input back; Electron apps can later be upgraded to CDP (no focus stealing, device-metric resizing) and risky or Linux-only apps moved into a Linux ARM64 container behind Xpra. Do not compile Chromium, Node or Rust apps into TempleOS.

1. Facts about our guest that bound every design#

  • The desktop works in logical units at scale ks_s of 1 or 2 and owns the whole framebuffer; the card address comes from PCI BAR0 (desk3/05-run.HC:58-66, ks_fb=PCIReadU32(...,0x10)) [V]. Windows are fixed size, held in arrays sized by NA (#define NA 9, desk3/01-core.HC:26; arrays ks_aw/ks_ah/ks_wx/ks_open/ks_z in desk3/02-ui.HC:5-15) [V]. Apps are AppXxx(a,x,y,w,h) draw functions dispatched by an if-chain in AppBody (desk3/03-apps.HC:584-597 (AppBody at :585)) and by AppClick (desk3/04-main.HC:148) [V].
  • A frame is: for each dirty rectangle, set the clip (ks_c0x..ks_c1y), run Draw (wallpaper, every window frame with shadow, app body, menubar, dock), Cursor, then MemCpy each row to the card (desk3/05-run.HC:3-54) [V]. So a dirty rectangle inside a video-like window still repaints the wallpaper, the shadow and the card under it unless a fast path is added. SpanCopy (desk3/01-core.HC:114) and RRTexN (:178) already copy from a full-screen-sized source with a rounded mask, but assume the source has the screen stride [V]; a stride-aware variant is needed.
  • Hit regions are rebuilt every drawn frame (Hit, desk3/02-ui.HC:92, max 500 MAXH) and the hit test is a linear scan (HitAt, :101) [V].
  • Input: mouse is relative, re-centred each loop (MsSet(320,240)), cursor moved by dx*3*s (desk3/04-main.HC:364-373); only ms.lb (left button) and wheel ms.pos.z are read (:378, :367) [V]. Keys come from ScanKey(&ch,&sc) (desk3/04-main.HC:315-318), used with sc&0xFF PS/2 scancodes in NotesKey (:264-270, for example 0x4B left, 0x4D right, 0x53 delete) [V]. ScanKey returns key-down only as far as these uses show; whether key-up and modifier state are readable (kbd globals, KeyDown()) is [U].
  • Measured by earlier agents and the README: full 1280x800x4 copy to the card about 7 ms; 700k pixel redraw about 20 ms; 7 ms redraw at 1440x900 and about 25 ms at 2880x1800 for moving a window (README.md:7, :23-24) [V as documented measurements, not re-run]. 1 GB RAM (-m 1024M, scripts/boot-vm.sh:14) [V]; at 2x the desktop already holds a back buffer, a prev buffer, low-res blur buffers and 5+5 wallpapers of 20.7 MB each (about 290 MB, my arithmetic from desk3/01-core.HC:35) so remote surfaces need a RAM increase.
  • Serial: lockstep loader about 1.4 KB/s because it acks every 8 to 32 bytes (docs/kosmos-app-port-research.md:37-40) [V as reported by that file]; a streaming drain loop is unmeasured.
  • Audio: PC speaker only (task statement). Network: none.
  • The guest build is one concatenated file: cat desk3/0*.HC (scripts/send-to-vm.sh:14) [V], so a new file named desk3/03b-remote.HC sorts between 03-apps.HC and 04-main.HC automatically.

2. Q1: architectures for getting Electron and Tauri apps into a window#

Common baseline numbers (my arithmetic): a 1000x700 logical window is 2.8 MB at 1x and 11.2 MB at 2x per full frame. All approaches below end in "BGRA surface plus changed rectangles", so Q2 and Q6 apply to all.

(a) Native macOS app, ScreenCaptureKit capture, CGEvent or Accessibility input#

  • What you see: the real app window, native fonts, native GPU, macOS menus. SCContentFilter(desktopIndependentWindow:) captures one window regardless of what covers it, minimumFrameInterval up to 60 fps, frames arrive when content changes, BGRA output, optional app audio since macOS 13, Screen Recording permission required [U: the Apple page https://developer.apple.com/documentation/screencapturekit/ returned no body to my fetch; the details come from the fetch tool's general-knowledge summary. Verify with an Apple sample before relying on them.]
  • Sunshine, a GPL-3.0 streaming server, uses ScreenCaptureKit as its only macOS capture backend and requires macOS 14.2 or later [D] (https://github.com/LizardByte/Sunshine), which is evidence that SCK capture is a mainstream route in 2026. It does not say whether it captures single windows [D].
  • Latency/FPS: capture is GPU-side and cheap; readback of 2.8 MB at 30 fps is about 84 MB/s of memcpy on the host [U]. The chain click to pixel is guest poll (up to 5 ms idle sleep, desk3/05-run.HC (the idle Sleep(5) in Main)) + serial/shm event + host injection + app render + SCK frame (up to 16 ms at 60 fps) + shm write + guest blit (about 10 ms): estimate 60 to 120 ms [U].
  • Input: CGEventPostToPid for mouse and keys to a specific app, or Accessibility (AXUIElement) actions such as AXPress for robust button clicks. Needs the Accessibility permission [U]. Unicode and IME: host can set a Unicode string on a key event; the guest cannot compose non-ASCII, so a host-side "paste or type text" path is needed [U].
  • Clipboard: NSPasteboard bridged by the daemon, gated by consent (Q5). Audio: the app plays through the Mac speakers (free); per-app mute only [U]. Cursors: SCK can hide the cursor; shape needs a query (NSCursor.currentSystem) or a guess from the AX element role [U].
  • Multi-window and popups: a per-window capture excludes the app's other windows. Menus, drop-downs, tooltips, dialogs and native context menus are separate windows. Handle by listing all windows of the same pid and exposing each as a child surface at an offset, or by capturing at application level and cropping the union rectangle [U].
  • HiDPI: ask SCK for width and height = window logical size x ks_s so the guest does 1:1 copies. Resize: set the real window size via Accessibility AXSize [U].
  • Drag and drop: not feasible except through a shared folder and the app's own open dialog (captured as another window).
  • What breaks: windows must be on-screen to be captured (minimised and fully off-screen windows are a risk) [U], so the user's real desktop gets cluttered unless windows live on a virtual display (private CGVirtualDisplay API, risky [U]) or another Space; focus stealing when injecting keyboard events; the app runs in the user's own profile with the user's files (security, Q5); permission prompts that macOS re-confirms periodically [U].
  • Cost: S/M for a single-window prototype, L with popups and resize. Best compatibility: everything installed on the Mac, including Slack, Discord, Notion, 1Password, and Tauri apps (WKWebView).

(b) Linux ARM64 VM or container on the Mac, headless compositor, pull frames over a remote-display protocol#

  • Electron officially documents running under Xvfb with DISPLAY set for headless CI [D] (https://electronjs.org/docs/latest/tutorial/testing-on-headless-ci). A forum report says headless Obsidian needed --disable-gpu --no-sandbox besides Xvfb [S] (https://forum.obsidian.md/t/one-solution-to-segmentation-fault-when-launching-headless-obsidian/117276). Tauri v2 on Linux needs WebKitGTK 4.1 and the docs give an arm64 install line (libwebkit2gtk-4.1-dev:arm64) [D] (https://v2.tauri.app/distribute/debian/).
  • Software GL only (no GPU in a container on macOS) means Chromium uses SwiftShader or llvmpipe, so heavy pages burn host CPU [U].
  • Xpra is the strongest tool here: seamless per-window forwarding of individual X11 apps, built-in HTML5 client, clipboard and audio forwarding, macOS arm64 client builds, GPL-2.0+ [D] (https://github.com/Xpra-org/xpra/). Older tickets show encodings rgb (zlib or lz4), png, jpeg, webp, h264, vp8, vp9 [S]; latest release notes seen mention 6.5.3 and AV1 decoders [S] (https://github.com/Xpra-org/xpra/releases). Per-window damage regions and window move/resize/title/icon/cursor events are the protocol's native vocabulary, which map one-to-one to our "remote window" contract [U]. The cost is writing a custom client (Python, speaking Xpra's protocol) that decodes window updates and copies them to shared RAM.
  • waypipe: a Wayland proxy with lz4/zstd/video compression and DMABUF transfer [S] (man pages, e.g. https://man.archlinux.org/man/waypipe.1.en); it needs a Wayland compositor at the receiving end, which we are not (our "compositor" is HolyC). Poor fit. Its project page returned an anti-bot "Access Denied" so licence and macOS status are [U].
  • Weston RDP backend plus FreeRDP: RemoteApp-style RAIL/VAIL support was developed for WSLg; whether mainline Weston ships it is not confirmed [S] (https://www.mankier.com/1/weston). Weston and FreeRDP licences: FreeRDP is Apache-2.0 [D] (https://github.com/FreeRDP/FreeRDP); Weston is MIT [U].
  • wayvnc with sway or another wlroots compositor: WLR_BACKENDS=headless WLR_LIBINPUT_NO_DEVICES=1, one display per wayvnc instance [S]; a wlroots issue reports a grey screen with the headless backend in some versions [S] (https://gitlab.freedesktop.org/wlroots/wlroots/-/issues/3712). One container per app under cage (single-app kiosk) plus wayvnc yields a per-app stream by construction [U]; popups and dialogs live inside that one output.
  • TigerVNC (GPL-2.0, Xvnc is an X server with a virtual framebuffer, Tight encoding with libjpeg-turbo) and noVNC (MPL-2.0, Raw, CopyRect, RRE, Hextile, Tight, TightPNG, ZRLE, JPEG, Zlib, H.264) are whole-desktop [D] (https://github.com/TigerVNC/tigervnc, https://github.com/novnc/noVNC). VNC rectangles include CopyRect, which is a natural dirty-rectangle source.
  • Latency 50 to 150 ms typical on localhost [U]. Host CPU: one container with Xvfb, a window manager and a software-rendered Chromium can use one to two cores while active [U].
  • Input: X11 events through xdotool, XTest or the protocol (Xpra/VNC both carry keysyms and button masks); IME and clipboard are native to Xpra. Multi-window: native in Xpra, absent in VNC. Audio: PulseAudio over TCP to a Mac player [U].
  • What breaks: only apps with Linux ARM64 builds (Q4); app looks like a Linux app (fonts, no macOS menu bar, tray icons need a tray host); Rosetta for Linux in Apple's Virtualization framework or qemu-user could run x86_64 Electron apps, slowly [U]; keychain/biometric integrations differ.
  • Benefit: real isolation (own filesystem, own network namespace, kill switch, cgroup limits), the right answer for untrusted or noisy apps.

(c) Electron specific#

  • Offscreen rendering webPreferences.offscreen: delivers each frame through webContents.on('paint') with the dirty rect and image, windows are always frameless, setFrameRate up to 240 fps in software mode, no frames while the page is idle, GPU mode supports WebGL with a copy cost, and a useSharedTexture mode needs a native Node module [D] (https://www.electronjs.org/docs/latest/tutorial/offscreen-rendering). It must be set where the BrowserWindow is created, so it works for apps we own or can patch, not for closed apps like Slack (and ASAR integrity or OnlyLoadAppFromAsar fuses may block patching [U]). beginFrameSubscription exists in webContents with an onlyDirty flag; the fetched page was truncated so callback details are [U]; the page also lists capturePage(rect, {stayHidden, stayAwake}) and isBeingCaptured() [D] (https://www.electronjs.org/docs/latest/api/web-contents).
  • CDP Page.startScreencast over --remote-debugging-port: frames are only emitted when the browser renders something new, every frame must be acked with Page.screencastFrameAck, the method is flagged experimental [S] (search results quoting Puppeteer recorder code and Chromium page_handler.h; the protocol viewer page fetch returned only a redirect notice). Input via Input.dispatchMouseEvent / dispatchKeyEvent / insertText; resize via Emulation.setDeviceMetricsOverride without moving the real window; no native chrome, native menus, OS dialogs, <select> popup widgets or tray [U]. Wins: no Screen Recording or Accessibility permission, no focus stealing, can run hidden [U: background throttling of hidden pages may stop frames]. JPEG frames are cheap to decode on the host but we want raw BGRA so decode costs host CPU only.
  • Playwright Electron: experimental, _electron.launch(), Electron v21 or later, firstWindow(), electronApp.evaluate() runs in the main process (so Menu.getApplicationMenu() could feed our menubar), native dialogs are not intercepted and must be stubbed through evaluate(), and the EnableNodeCliInspectArguments fuse set false breaks launch [D] (https://playwright.dev/docs/api/class-electron). Apps built with that fuse off (hardened apps) cannot be driven this way; they would still accept --remote-debugging-port unless stripped [U].
  • Electron on Linux arm64 is a supported target for packagers [S] (https://www.electron.build/docs/architecture).

(d) Tauri specific#

  • wry is the webview layer: WKWebView on macOS ("WebKit is native on macOS"), WebView2 on Windows, WebKitGTK on Linux, child webviews on macOS, Windows and Linux (X11 only); dual MIT or Apache-2.0; the README says nothing about offscreen/headless rendering [D] (https://github.com/tauri-apps/wry). tao is its window crate [U].
  • No CDP: the Tauri debugging page documents Safari's inspector on macOS (private API on macOS, blocks App Store), Edge DevTools on Windows, WebKitGTK WebInspector on Linux, and mentions no remote protocol [D] (https://v2.tauri.app/develop/debug/). Production builds disable devtools unless the devtools feature or a debug build is used [D] (same page).
  • WebDriver: tauri-driver supports Windows and Linux only; there is "no WKWebView driver tool" on macOS; CrabNebula sells a cross-platform fork needing a paid key on macOS; the docs recommend WebdriverIO with @wdio/tauri-service [D] (https://v2.tauri.app/develop/tests/webdriver/). Screenshots are not mentioned there; W3C WebDriver has a standard screenshot endpoint [U] but it is a poll, not a stream.
  • WebKitGTK remote inspector: WEBKIT_INSPECTOR_SERVER=host:port with enable-developer-extras, client is another WebKitGTK browser at inspector://; WebKitWebDriver uses the same remote protocol [S] (https://trac.webkit.org/wiki/RemoteInspectorGTKandWPE, https://blogs.igalia.com/carlosgc/?p=936, dated 2017). This is WebKit's protocol, not CDP.
  • Linux aarch64 build: Tauri's docs give the arm64 dependency line [D]; whether a given third-party Tauri app publishes aarch64 Linux binaries is app-specific (many publish only x86_64 AppImages) [U]. Building from source in a container is possible for open-source Tauri apps [U].
  • Idea: Tauri frontend as a plain page in headless Chromium, Rust backend on the host. The frontend talks through window.__TAURI_INTERNALS__ and a custom IPC protocol [U]; Tauri ships mockIPC for tests and a tauri::test mock runtime [U]. In principle the backend's #[tauri::command] functions run in a process with a mock runtime and a shim forwards invoke over a WebSocket. This needs the app source (to build a headless backend) and per-app work; it also loses plugins that need a real window (dialogs, tray, window management). Feasible for a few open-source Tauri apps we choose, not a general route. Rate: a research spike, not a platform feature.
  • For closed Tauri binaries on macOS: only (a) ScreenCaptureKit works. Cost the same as for Electron.

(e) Semantic route: redraw natively from accessibility or DOM#

  • Data sources: macOS AXUIElement trees of any app [U]; for Chromium Accessibility.getFullAXTree, DOM.getDocument, DOMSnapshot.captureSnapshot (nodes with bounding boxes and computed styles) [U]; our own egui precedent in docs/kosmos-app-port-research.md:70-90 already shows the loss profile (no colours, fonts, icons, canvases, z-order) [V].
  • What is lost: everything custom drawn (VS Code editor canvas, Slack message virtualisation, images, video, fonts, shadows); web layout cannot be reproduced by walking rectangles at 15 ns per operation with a single font atlas.
  • What it is good for as an adjunct: the app's menu bar items into our menubar (desk3/02-ui.HC:238), window titles, focus and caret rectangles for IME, cursor shape by element role, robust button activation (AXPress), and an agent/reader mode that sends styled text. Verdict: not a primary route.

(f) Better ideas found#

  1. Web-first apps in one host Chromium. Slack, Discord, Notion, Element and VS Code (through vscode.dev or code-server) all have web clients, so a single headless Chromium (Playwright) with one tab per app and CDP screencast covers many "apps" with no per-app install, no ScreenCaptureKit permission and a clean cookie jar per profile. The core-apps plan already contains this as spike 2 (docs/core-apps-plan.md:117-119) [V]. Loses Electron-only features and may breach some web-client terms (Q4).
  2. Host-side overlay. Skip pixels in the guest entirely: the guest sends window rectangles over serial and a borderless host window sits over the QEMU window showing the real app. Zero guest cost and perfect speed; but z-order with guest windows, menus and shadows is wrong, screenshots of the VM miss it, and it is not "inside". Useful only as a stop-gap demo [U].
  3. Surface-provider abstraction (recommended): the host daemon exposes one contract (create surface, resize, dirty rects, title, cursor, close, child surfaces) and implements it with SCK, CDP or Xpra. The guest never learns which.

3. Q2: the transport#

Bandwidth needs (my arithmetic)#

Quantity Bytes
1440x900x4 full frame 5.18 MB
2880x1800x4 full frame 20.7 MB
1000x700 logical window, 1x / 2x 2.8 MB / 11.2 MB
Typical typing or cursor-blink update (a few percent of a window) 20 to 200 KB at 1x
30 fps of a full 1000x700 window at 1x 84 MB/s
30 fps at 2x 336 MB/s

Serial at an optimistic 100 KB/s moves one 2.8 MB window in 28 s, so serial can never carry pixels; with zlib/RLE on a mostly static UI it could carry small deltas (about 1 to 10 KB each) at a few fps [U]. LZ4 and RLE decoders are 30 to 60 lines of HolyC but cost about 10 to 30 ns per output byte under TCG so decoding a 1 MB delta costs 10 to 30 ms [U]; they only pay when the channel is the bottleneck, which shared RAM removes.

Frame budget in our guest (derived from README.md:7, :23-24 and arithmetic)#

  • Surface-in-shared-RAM to back buffer to card = two copies. Our measured raw copy is about 5.2 MB per 7 ms (about 0.75 GB/s). A 2.8 MB window costs about 4 ms per copy, so about 8 ms if both copies are needed; the back buffer copy can be skipped by a fast path that blits straight to the card when nothing overlaps the dirty rectangle.
  • Full-window redraws: 1000x700 at 1x about 8 ms, so 30 fps is plausible (the frame cap ks_fcap defaults to 60, desk3/01-core.HC:58). At 2x the same window is 11.2 MB, about 15 ms per copy and about 30 ms for both, so 20 to 30 fps with the fast path, 15 to 20 without. Typical UI use updates 5 to 20% of a window, so 30+ fps is realistic for typing, scrolling a small region and hover effects. Video-like content (a scrolling web page) is the stress case.
  • Never upscale in the guest: nearest 2x upsample of 700k source pixels in HolyC at about 15 ns per op is 30 ms or more [derived from README.md rates]. The host renders at the final physical size.
  • Overlap cost: if another window or the dock overlaps a dirty rectangle, Draw must repaint those layers clipped to that rectangle; rounded corners and shadows use RRTexN style code. Expect 2 to 4x slower in that case.

6. Q5: security and permissions design#

Principles: the guest is a display and input terminal with no network and no secrets; the host daemon is the only holder of credentials and the only place that can reach outward.

  1. Credentials stay on the host. Each app runs with its own profile directory on the host (or in its container volume). Login happens inside the remote window by the user. The guest never receives cookies, tokens, keychain items, or app files; it receives pixels and sends events.
  2. Sandboxing. macOS route: run each app under a dedicated profile (separate --user-data-dir for Electron, separate app-specific data dir) and, where practical, sandbox-exec with a deny-default profile (deprecated but present [U]) or a separate low-privilege macOS user account (but windows from another login session cannot be captured [U]). Linux route: one container per app, read-only root, a single writable volume, no host mounts except the share folder, dropped capabilities, CPU and memory limits, no network unless the manifest asks for it (allow-list by hostname through a proxy for apps that need only one service).
  3. Per-app permission manifest. Fields: network (none, allow-list), files (none, share folder only), clipboard (none, ask, allow-paste-only), notifications (off, on), camera/mic (never in v1), automation (can agents drive it: default no). The launcher shows the manifest on first run and stores the approval on the host.
  4. Outward-facing actions need a prompt in the desktop UI. Anything that sends a message, mail, post, purchase or file upload, or that is initiated by software rather than the human at the keyboard (an agent script, a clipboard paste, a scripted click) shows an approval sheet with the exact action and the target app. Human keystrokes and clicks in the focused remote window are the user acting directly and need no extra prompt. The agent API of the daemon (click, type, drag) must be a separate, opt-in, logged channel; the desktop shows an "agent is driving" banner. This matches the rule at the end of docs/core-apps-plan.md:122.
  5. Clipboard. Guest to host: only on an explicit copy gesture in the desktop with the remote window focused. Host to guest: only when the user presses a "Paste from Mac" action; the daemon shows the first 80 characters in a toast first. Clipboard contents are never logged and are cleared from the daemon after 30 seconds. Never auto-sync (password managers copy secrets).
  6. File share. One folder per app (~/KosmosShare/<app>/); guest Files app can list and drop files there through the daemon; no path outside the share is ever accepted; size and type caps; the remote app sees it through its normal open dialog.
  7. Notifications. Forward only the title and first 120 characters of apps enabled in their manifest; never forward OTP-looking text when a manifest flag says so.
  8. macOS permissions. The daemon needs Screen Recording and Accessibility; ask once, document in README, and show a banner if the OS revokes it [U]. Use the least capable path: CDP needs neither.
  9. Audit log of every cross-boundary event (clipboard, file, agent action, launch, kill) on the host, viewable from a desktop app.
  10. ToS and licences. Respect each vendor's terms before enabling agent driving; GPL components (Xpra, Sunshine, TigerVNC) stay out of any shipped binary unless the licence is accepted.

8. Q7: recommended route, phases, spike, risks#

Phases#

  • Phase 0 (spike, 4 days): prove shared RAM plus one live window. Details below.
  • Phase 1: guest contract and framework. Items 2, 7, 8, 9, 14 (minimal), 17 (basic resize), 19. Deliver: two remote windows (host test patterns), keyboard and mouse round trip, Monitor shows fps. Uses a fake provider that renders a test page so the guest work does not wait on capture work.
  • Phase 2: macOS native provider. Items 3, 4, 10, 16; run a Tauri hello-world, Obsidian, VS Code natively; child popups; clipboard and file share (11, 12).
  • Phase 3: safety and breadth. Items 15, 18, 13; the Chromium/CDP provider for Electron and web apps (5); then the Linux container provider with Xpra (6) for apps without macOS-native safety, isolation, or arm64 packaging.
  • Phase 4 (optional): virtio channel driver in HolyC to replace polling; audio routing; second-monitor and virtual display experiments.

Smallest spike (time box 4 working days)#

Goal: a live, interactive window of a real Tauri or Electron app inside a desktop window, over shared RAM, at usable speed.

  • S0 (1 day): boot QEMU with the shared RAM file (flags in item 1). A host Python script mmaps the file. Guest HolyC ShmFind allocates a 64 KB buffer, writes the magic and its address; host finds it (scan or address from serial). Gate: host reads guest-written 4 KB blocks with sequence numbers 1,000,000 times with zero mismatches, and the guest reads host-written blocks the same way; sustained throughput at least 20 MB/s each way (the gate already set in docs/core-apps-plan.md:116); round trip under 5 ms. Fail (no visibility, corruption, or SSD write storms that a RAM disk does not cure) means switch to the second-IDE-disk transport (Section 3) for one more day or stop and use the serial thumbnail plus host-overlay stop-gap.
  • S1 (1 day): host writes an 800x600 BGRA surface with a moving test pattern and dirty rectangles; guest AppRemote window blits it. Gate: at least 20 fps full-window at 1x with a Monitor-reported frame cost under 40 ms, and at least 12 fps at 2x.
  • S2 (2 days): Swift CLI captures one window of a Tauri hello-world and Obsidian (or VS Code) with ScreenCaptureKit into the surface; guest click, wheel and key events return via the event ring (or serial) and are injected with CGEvent. Gate: typing and button clicks work; median input-to-pixel latency at most 150 ms at 800x600 1x; at least 15 fps while scrolling; no more than 5% frames with visible tearing.
  • Overall pass: S0, S1 and S2 gates all met inside four days. Anything else means reporting the failure mode before building more.

Main risks (ranked)#

  1. Shared main RAM on macOS under TCG is unproven (visibility and ordering of stores between the TCG thread and a host process; write-back of a file-backed 1 GB mapping; TempleOS identity mapping assumption). Mitigation: S0 first; RAM disk or memory-backend-shm; fallback second IDE disk transport.
  2. Guest-side cost and input fidelity. Retina surfaces are 11 MB per window; overlaps force slow repaints; there is no key-up or non-ASCII input path known to work, one pointer path with a hacked relative-delta scheme, and shortcuts like Esc already reserved (desk3/04-main.HC:319). Mitigation: fast-path blit, host-side scaling, 1x default for remote windows, a text-injection field, a keyboard-release chord.
  3. Host capture permissions, focus and policy. Screen Recording and Accessibility permission, windows that must be on-screen to be captured, popups as separate windows, apps that block automation or forbid it in terms of service, secrets visible in pixels. Mitigation: CDP or container providers for sensitive or noisy apps, per-app manifests, explicit approval for outward actions.
  4. Lesser: Electron fuses blocking CDP; auto-update; memory (-m 1024M too small); sync of frame pacing between host capture rate and guest loop sleeps.

What not to attempt#

  • Compiling or porting Chromium, Node, Electron, WebKit or a Rust/Tauri runtime into TempleOS. HolyC only, ring 0, no libc, no threads, no network stack, no GPU, 15 ns per simple operation; Chromium is tens of millions of lines of C++ that need all of those. There is no path that ends in a usable browser. The guest should stay a display and input terminal.
  • Writing a NIC driver plus TCP/IP and TLS in HolyC to let the guest talk to services directly: large, and it moves secrets into the guest.
  • Rendering web pages by reimplementing a layout engine from DOM or accessibility data (Section 2e).
  • Streaming pixels over the serial port (Section 3).
  • Relying on ivshmem (not in this QEMU build) or on a Linux-only QEMU build.
  • Embedding GPL code (Xpra, Sunshine) in a product we would distribute without a licence decision.
  • Controlling 1Password or other credential managers through the remote window.
