Kosmos Temple Desktop: core apps and how to build them

Edited 2026-10-27docs/core-apps-plan.md

Status on 2026-10-27. "Built" means running in the desktop today (desk3/). Everything is HolyC inside TempleOS V5.03, drawn by our own renderer, so each app is a function that draws into a window body in logical pixels and registers hit regions. API names marked (verify) are from memory of the TempleOS source and have not been tried yet.

What the platform gives and takes away#

  • Gives: HolyC compiled at run time (so a code editor with a Run button is cheap), raw hardware access, the TempleOS file system (RedSea on the CD and RAM drive B:), FileRead and FileWrite, FilesFind, timers, PC speaker sound, multicore.
  • Takes away: no network, no writable disk on the live CD (nothing survives a reboot), about 15 ns per simple pixel operation, 25 to 30 fps at retina size, single font atlas, no clipboard or drag and drop yet, one mouse and keyboard path of our own.
  • A host bridge changes the last two points: the QEMU serial port already carries our files in, so a small Mac-side daemon can add persistence (settings, notes), a clipboard, screenshots out, and real network or kosmos-app data in. The serial loader is lockstep (about 1.4 KB/s measured, with 32 byte acknowledgements); a streaming drain loop could be much faster (unmeasured).

Effort: S about a day, M about three days, L about a week. Order is the build order.

Build order#

  1. App framework and Widget kit v2 (everything else depends on them).
  2. Host bridge with streaming-rate spike, then persistence and clipboard.
  3. Launcher, Notifications, Text field powered Notes, Terminal, Code editor (the TempleOS-native showpieces).
  4. Files completion, Image viewer, Paint, Screenshot.
  5. Calendar, Docs viewer, Activity monitor completion, Music, Games.
  6. Kosmos Editor and Viewport, after the user approves the kosmos-app bridge.

Risks#

  • Frame budget: eleven or more windows with text in each cost real time at 2880x1800. Keep the dirty-rectangle rule and give each app its own cheap invalidation (as Viewport and Scene do) rather than redrawing whole windows.
  • Text editing at scale (selection, wrapping, undo) is where HolyC speed and our proportional font hurt: cap buffer sizes, cache line layouts, and invalidate only changed lines.
  • TempleOS API details marked (verify) can differ from memory. Each tier starts with a half-day spike that proves the API in the VM.
  • Nothing persists without the bridge. Until it exists, say so in Settings and Notes.
  • Licences: Inter (OFL) and Lucide (ISC) are attributed in assets/; the vendored kamiji kit in apps/os-styles is not cleared for publishing.

Addendum: the six big apps and porting open-source software#

Wanted: text editor, web browser, music player, code editor with AI, email, text messenger. Three ways to bring open-source software in, from least to most effort per app:

  1. Host service plus native UI (recommended for most). The Mac runs the real open-source engine; our desktop draws a themed, retina UI and talks to it over the host bridge. Credentials, network and heavy code stay on the Mac.
  2. Remote app window. The Mac (or a Linux VM or container) runs the unmodified app and streams its pixels into a desktop window; input flows back. Anything open source works, at the cost of looking foreign and of bandwidth.
  3. True source port into HolyC. Only small, self-contained C code (an editor like kilo, Lua, an image or MP3 decoder). TempleOS has no libc, threads or network stack and HolyC is not C, so this is translation with a small shim (memcpy, malloc onto MAlloc, printf onto Print), done per library, not for applications.
App Approach Open-source pieces Notes
Text editor native (finish Notes) kilo (about 1000 lines of C) as a reference to translate; gap buffer or rope no bridge needed except save to host
Code editor and AI IDE native editor plus host agent host side: an agent like Claude Code over the bridge, language servers, git files live on the Mac and are edited by the guest through the bridge; the guest runs HolyC itself; chat, diff and tool-approval panels are native
Web browser host renders, guest shows headless Chromium or WebKit through the DevTools screencast, or Servo; reader mode via Readability native chrome (tabs, URL bar, bookmarks); page pixels streamed; a cheap reader mode sends styled text instead
Email host service plus native UI Himalaya (Rust, JSON output), or isync with notmuch or mblaze native list, reader and compose; HTML mail reduced to styled text; OAuth tokens never enter the guest
Text messenger host service plus native UI Matrix with matrix-nio, mautrix bridges (Signal, WhatsApp, iMessage), signal-cli, IRC conversation list, bubbles, composer, toasts; each account needs explicit user approval, and sending is always a user action
Music player host plays, guest controls mpd or mpv (or afplay), ffmpeg for metadata and art TempleOS has only a PC speaker driver, so audio cannot come from the guest without writing an HDA or AC97 driver; native UI over mpd gives library, queue, art and a spectrum

The channel decides everything#

Correction, 2026-10-27: the ivshmem idea below does not work on this Mac. Homebrew QEMU 11.0.2 has no ivshmem-plain device (checked with qemu-system-x86_64 -device help). memory-backend-file, memory-backend-shm and memory-backend-ram do exist, so the candidate is guest RAM backed by a shared file that the host also maps. Unproven under TCG on macOS. See electron-tauri-support-research.md.

The serial port is too slow for pixels (about 1.4 KB/s lockstep, unmeasured when streamed). The best candidate is shared memory: QEMU ivshmem-plain backed by a file the host also maps. The guest already reads a PCI BAR (the VGA framebuffer), so mapping another is the same code, and a ring buffer in HolyC is a few dozen lines. A 1440x900 frame is 5 MB, a full copy measured about 7 ms in the VM, so 30 fps of streamed pixels is plausible. Unverified: ivshmem on macOS QEMU, the guest page mapping of that BAR, and host capture of other apps' windows (easiest from a Linux container running Xvfb or from Playwright for the browser).

Spikes, in order (each a half day, each with a pass or fail gate)#

  1. ivshmem ring: gate 20 MB/s guest to host and host to guest.
  2. Pixel window: stream a Playwright-driven Chromium viewport into a desktop window at 15 fps or better, with click and key back.
  3. Himalaya or Matrix over the same channel: list messages or rooms in a native list.
  4. mpd: play, pause, queue and album art from a native player.
  5. Agent panel: a chat view backed by a host process with approval prompts for every file write and command.

Rule for all of them: nothing is sent, deleted or purchased on the user's behalf without an explicit prompt in the UI.
