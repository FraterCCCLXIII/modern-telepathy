Improving HolyC on all of its deficits: analysis and ranked plan

Edited 2026-10-27docs/holyc-improvement-analysis.md

Written 2026-10-27. Evidence labels: [V] verified today (file and line in the TempleOS V5.03 source mirror, a measurement in a scratch VM, or a page opened today), [D] reported by documentation or a README, [U] unverified. Source paths are relative to the TempleOS mirror (Compiler/, Kernel/, Adam/, Doc/); line numbers are from the cia-foundation/TempleOS archive branch checked out in the scratchpad. Measurements were taken in a headless scratch QEMU (TCG, Apple Silicon, -m 1024M, TempleOS V5.03 live CD, no display); the raw outputs are in /tmp/tvm-lang/E1.out to E4.out and the test programs in the scratchpad (lang-vm/files/E1.HC to E4.HC).

Verdict#

The compiler is not the 30x problem. Measured in the same VM, the blend loop costs 11 ns a pixel written the way the spike wrote it, 3 ns as a pointer walk, and 0.8 ns a pixel as two-pixels-a-pass HolyC with reg variables, against under 1 ns for the hand assembly. The TempleOS compiler already keeps locals in registers (RSI, RDI, R10 to R15, chosen by use count, Compiler/OptPass3.HC:512-560 [V]); the 30x figure came from a loop in a large function with more live locals than register slots, an index loop instead of a pointer walk, one pixel a pass instead of two, and (probably) a visible QEMU window. The real, measured deficits are elsewhere: x87 floating point under TCG is 11x slower than SSE2 (67 ns versus 6 ns per multiply-add), a call costs 9 to 12 ns, there is no continue, the precedence table differs from C, faults are uncatchable, and tooling is a single in-OS compiler.

Two things make the compiler far more fixable than expected, both verified today:

  1. The compiler rebuilds and hot-loads on the live CD in under three seconds: copy ::/Compiler and ::/Kernel to the RAM drive (157 ms), Cmp("B:/Compiler/Compiler") (2.36 s, 0 errors, 179 KB of code), Load(...) (51 ms), then re-resolve the kernel's 19 import sites with a 30-line HolyC relinker. The prompt then compiles with the patched compiler (a changed warning string proved it). No install, no ISO rebuild, no snapshot change. So family A (modify the in-OS compiler) is a daily-loop activity, not a project.
  2. The precedence table is runtime data (cmp.binary_ops, Compiler/CInit.HC:286-310, public extern CCmpGlbls cmp in Compiler/CompilerB.HH:13 [V]). Sixteen assignments switch the live compiler to C precedence, verified with a*b>>1, a&b+c, a+b<<1, a==b|1; sixteen more restore it. No rebuild.

Recommended direction: keep HolyC as the language of the desktop, fix the compiler in place for the handful of things that matter (SSE2 for F64, continue, C precedence as an option, cheaper calls, a few peepholes), move only floating-point kernels and two or three blit loops to assembly (hand-written or NASM-assembled on the Mac and embedded as bytes), and build the tooling (lint, format, test, profiler) on the host against the compiler's own tables. Do not build an LLVM front end or a transpiler for this project: the measured gain over fixed HolyC is 2 to 4x on integer loops and the cost is the loss of the in-OS edit-and-run loop that the whole workflow is built on.

1. The compiler as it is (what the source says)#

Pipeline (Compiler/Compiler.PRJ [V]): Lex to PrsExp/PrsStmt/PrsVar producing a reverse-Polish intermediate code (IC) list, then OptPass012 (constant folding, address-mode merging, the CALL,FS/GS,... patterns), OptPass3 (register-variable scoring and assignment), OptPass4, OptPass5, OptPass6, then OptPass789A which emits x86-64 bytes through BackLib/BackA/BackB/BackC (integer) and BackFA/BackFB (x87). Terry's own description: "The compiler's parser makes RISC code which it optimizes to CISC" (Doc/Charter.DD:75 [V]); the IC is "rev polish stack machine in nature" (Doc/Glossary.DD:183 [V]).

Register model (OptPass3.HC:512-525 comment, Kernel/KernelA.HH:1801-1805 [V]): RAX, RBX, RCX, RDX, R8 are clobber scratch; RAX and R8 link IC nodes; R9 is the stack-machine temporary; RBP the frame; RSI, RDI, R10, R11, R14, R15 hold register variables; R12, R13 hold non-pointer register variables only. Variables are chosen by a use-count score with the address-taken ones excluded (OptPass3.HC:535-560); reg/noreg only force or forbid (REG_ALLOC, REG_NONE, KernelA.HH:1797-1798). Eight slots total; a function with more hot locals spills the rest to [RBP]. Functions containing try get no register variables at all (PrsStmt.HC:852, "TODO: Currently no reg vars in funs with try/catch" [V]).

Options (KernelA.HH:1546-1558 [V]): the only codegen options are OPTf_NO_REG_VAR, OPTf_GLBLS_ON_DATA_HEAP, OPTf_NO_BUILTIN_CONST and the half-implemented OPTf_USE_IMM64. There is no optimisation level, no inlining, no loop pass, no CSE. PassTrace shows the IC per pass (Doc/DbgOverview.DD:35).

Floating point: all F64 goes through x87 (BackFA.HC, BackFB.HC); OpCodes.DD has FXSAVE, MOV_CR4_RAX and friends but no SSE arithmetic (plan-review already verified no MOVAPS, PADDB and so on). The kernel never sets CR4.OSFXSR (Kernel/KStart64.HC:45-47 sets OR EAX,0xB0: PAE, PSE, PGE only [V]), so SSE instructions fault with #UD until a program sets bit 9. The scheduler already does FXSAVE/FXRSTOR per task (Kernel/Sched.HC:87,119 [V]), so XMM state survives task switches once SSE is on. ZealOS turns it on at boot (BTS RAX,CR4f_OSFXSR, src/Kernel/KStart64.ZC:6-8 [V]).

Calling convention (PrsExp.HC:545-583, OptPass789A.HC:323-330,398-416,698-704, PrsStmt.HC:116-121, KernelA.HH:577-586 [V]): every argument is a 64-bit PUSH, pushed so that argument 1 is at 16[RBP] (SF_ARG1), CALL rel32 (or MOV RBX,imm64; CALL RBX for far targets), result in RAX (F64 as raw bits in RAX), callee pops with RET imm16 when Ff_RET1 is set (default for any non-variadic function with arguments; variadic functions use caller ADD RSP). The prologue is PUSH RBP; MOV RBP,RSP; SUB RSP,n; PUSH <used reg vars> and the epilogue pops them, LEAVE, RET1. Callee must preserve RBP, RSI, RDI, R10 to R15 (Doc/GuideLines.DD:117). There is no stack alignment requirement and no red zone. Measured cost: 9 to 12 ns per call under TCG (E1/E2), five instructions (PUSH; CALL; ...; LEAVE; RET1).

Linking and loading (Kernel/KLoad.HC [V]): a .BIN is a CBinFile header (jmp, module_align_bits, 'TOSB', org, patch_table_offset, file_size; KernelA.HH:384-394), code, and a patch table of records {U8 type; U32 rip; U8 name[]; ...} with types IET_REL_I32/IET_IMM_I64 imports, IET_*_EXPORT exports, IET_ABS_ADDR (add module base at each listed offset), IET_DATA_HEAP (allocate and add), IET_MAIN (call). Load() reads the file, allocates in the code heap (below 2 GB so CALL rel32 works, Doc/Glossary.DD:169), runs LoadPass1 (exports into Fs->hash_table, imports resolved by HashFind, which returns the newest entry because HashAdd inserts at the bucket head, KHashA.HC:169-189 [V]) and LoadPass2 (IET_MAIN). Unresolved imports are parked as HTT_IMPORT_SYS_SYM and fixed when a later module exports the name (SysSymImportsResolve). The kernel loads /Compiler/Compiler.BIN.Z the same way at boot (KMain.HC:208-211); Compiler.PRJ and Kernel.PRJ are built by Cmp() from BootHDIns/BootDVDIns (Adam/Opt/Boot/BootHDIns.HC:10-15).

Lexer limits (Compiler/Lex.HC [V]): character constants up to 8 bytes (:638-682, "Char const limited to 8 chars"); $ opens a DolDoc command anywhere in the token stream including comments, $$ is a literal (:1088-1112); bytes 128 to 255 are a token class of their own (:470), so non-ASCII identifiers do not lex as letters. Doc/HolyC.DD states: no continue ("Use goto"), no #define functions, no typedef, no type checking, no ?:, no F32, postfix casts.

A one-off anomaly: the first run of BlendC in E1 took 531 ms; every later run (E2, three repetitions) took 64 to 65 ms. Treat single measurements under TCG as noise until repeated.

Reading of the BlendB body (E1 disassembly): the IC-to-CISC emitter produces the pattern MOV RAX,R13; IMUL R8; MOV R8,RAX; ADD RAX,R14; MOV R8,RAX; SAR R8,8 for (x*ia+srb)>>8, that is two redundant MOV R8,RAX per subexpression and a one-operand IMUL that clobbers RDX; the mask constants are re-materialised each use (MOV R8u32,0x00FF00FF twice per pixel). A hand version needs 14 instructions; the compiler emits 27. Under TCG, instruction count is roughly the cost, so the per-instruction codegen gap is about 2x, not 30x.

Where the 30x came from (decomposition from the table): window open versus headless, about 3x [U, inferred from 31 versus 11]; 17 live locals forcing spills and an index loop, 11 to 3 (3.7x) [V]; one pixel a pass versus two with 64-bit loads, 3 to 0.8 (3.7x) [V]; residual codegen quality, about 1.0 to 1.3x on the final form [V]. Conclusion: rewrite the hot loops, do not rewrite the compiler, to get 90 percent of the gain; the last 2x in integer code and the 10x in floating point are compiler work.

3. Family A: modify the in-OS compiler#

A.1 How to build and test a patched compiler (verified today, E3)#

  1. On the running live CD: CopyTree("::/Compiler","B:/Compiler"); CopyTree("::/Kernel","B:/Kernel"); (117 files, 157 ms). The .PRJ includes /Kernel/KernelA.HH by drive-relative path, which resolves on B: after Cmp does Cd(__DIR__).
  2. Patch the source on B: (our serial loader can write any file; the test replaced a warning string in PrsStmt.HC in place and deleted the stale .HC.Z copy, which otherwise wins the include).
  3. Cmp("B:/Compiler/Compiler"): 2.36 s, "Errs:0 Warns:0 Code:2BB9F Size:2F500".
  4. Load("B:/Compiler/Compiler"): 51 ms; exports shadow the old module's.
  5. Relink the kernel: walk sys_boot_patch_table_base with mem_boot_base (both _extern in Kernel/KernelB.HH:37-39) and rewrite each IET_REL_I32/IET_IMM_* import through HashFind (the code is Relink() in E3.HC, 30 lines; LoadPass1 itself is not visible to user code). 19 sites patched in under 1 ms. The command line then used the new compiler (the #include of a file with an unused variable printed the patched text "Unused VAR").
  6. Hazard found the hard way: loading a .BIN from a build with errors and relinking to it leaves the kernel pointing into a half-built module and Cmp itself disappears; always gate the Load on Cmp()==0. Recovery is a VM reset (60 s).

This fits the existing snap.sh/send-to-vm.sh workflow: a KS_MODE=compiler branch that ships a patched Compiler/*.HC set, runs steps 1 to 5 and saves a snapshot would make a patched compiler part of the image build-image.sh already produces. For a permanent change, BootDVDIns plus DskISORedSea builds a new ISO from inside the VM (Adam/Opt/Boot/BootDVDIns.HC, Misc/DoDistro.HC), which is the long-term route, but it is not needed for development.

Time for a patched compiler to be in use: about 5 s after the source is on B:. That is cheaper than any host-side toolchain's edit loop.

Payoff order: SSE2 (largest measured gain, isolated code), peepholes (cheap, safe, visible), continue (not speed, but it is in the same file set), fastcall for callbacks, then stop. Together they close the integer gap to about 1.3x and the float gap to about 1.2x of hand assembly on the kernels we have, by the measured numbers.

First experiment (S): patch BackLib.HC ICMov to skip a MOV reg,reg whose destination is overwritten by the next IC node before being read, rebuild with A.1, diff Uf("BlendB") and re-time with E2. Expected: 27 to 24 instructions, 64 to about 56 ms.

A.3 continue and precedence inside the compiler#

  • continue: PrsStmt.HC already threads lb_break through loop parsing and case KW_BREAK is five lines (:1133-1138). Add KW_CONTINUE to the keyword list (CompilerA.HH:258 area and the keyword registration in CInit.HC), carry an lb_continue label placed before the for increment / while test, emit IC_JMP to it. S.
  • C precedence as a compiler option (OPTf_C_PREC) that swaps the table in CmpFillTables (CInit.HC:286-310); default off so TempleOS's own code still compiles. S. Note that the runtime table patch (section 5) gives the same effect today without a rebuild.

4. Family B: a host-side toolchain#

B.1 ABI facts a host compiler must match (all [V], section 1)#

Stack-passed 64-bit arguments, argument 1 at 16[RBP], callee pops (RET imm16) for fixed-arity functions, RAX result, RBP frame, callee-saved RBP/RSI/RDI/R10-R15, caller-saved RAX/RBX/RCX/RDX/R8/R9, no alignment, code below 2 GB, globals reached by RIP-relative or absolute 32-bit addressing. This is not System V, so clang/rustc output cannot be called directly; a shim is needed in one of two forms:

  1. Per-function trampolines written as HolyC asm blocks: load SF_ARGn[RBP] into RDI, RSI, RDX, RCX, R8, R9, align RSP to 16, CALL the SysV symbol, restore. About 12 instructions per entry point, generated by a script from the C prototypes. The callee must be built -ffreestanding -fno-builtin -mno-red-zone -fno-stack-protector -mcmodel=small -fPIC (or -mcmodel=kernel) with no libc, no TLS, no unwinding, no SSE unless CR4.OSFXSR is set (set it; see A.2) and no x87 state assumptions. -mno-red-zone is required because TempleOS interrupts run on the current stack (KInts.HC INT_FAULT and the timer handler save context in place).
  2. A HolyC-ABI target: patch the host compiler's calling convention. holyc-lang (section 8) emits text assembly and uses SysV; changing its backend to push-and-RET1 is a day of work in its emitter [U]. For LLVM there is no HolyC CC; adding one is XL and not worth it.

Loading a host-built blob: emit a .BIN (header plus code plus patch table) from the host: the format is 40 bytes of header, raw code, and the IET_ records; imports of TempleOS functions become IET_REL_I32 records naming MAlloc, Free, MemCpy and so on; exports become IET_REL32_EXPORT; relocations become IET_ABS_ADDR lists. Then Load("B:/KSBLOB") resolves and the functions are callable by name from HolyC after an extern declaration (or by _extern to an exported label). A Python writer for this is S. Simpler still for kernels with no relocations: send the raw bytes over serial, MAlloc from Fs->code_heap, copy, and call through a function pointer; that works today with no format at all.

B.3 First experiment for B (S)#

Assemble KsBlendRow with NASM on the Mac (nasm -f bin), send the bytes over serial, load into the code heap, compare against the asm{} version for identical output and time. Then do the same with a clang -O2 -ffreestanding -mno-red-zone -mcmodel=small build of the two-pixel blend wrapped in a 12-instruction trampoline. Gate: both match the HolyC formula on 1,000 random pixels and the clang version is within 1.3x of the NASM one.

5. Family C: dialect and tooling on the host (no OS change)#

What the host can do with the compiler's own tables:

  • Precedence lint (S): a token-level checker (lex rules from Lex.HC: identifiers, numbers, 8-char char constants, $...$ commands, strings with \ escapes) that flags any expression mixing & ^ | << >> with + - * or a comparison without parentheses. False positives are cheap to silence with parentheses, which is what we want anyway. Also run the runtime precedence switch (section 2) around our own compile so that HolyC-written code is parsed as C: CPrec; ExeFile("B:/KSDESK3.HC"); HPrec;. Caveat: the switch is global to the compiler, so it must be restored before any TempleOS program is compiled (the Files app runs them); do it in the loader, not the desktop.
  • Preprocessor (M): a Python pass that adds function-like macros, continue (rewrite to goto to a generated label before the increment, which is what the compiler would do), ?: to if, and #include <...>; keep line numbers with #line-like comments so compiler errors still point to the source (the compiler reports file,line via LexExcept). Output is plain HolyC, so nothing in the OS changes.
  • ASCII and dollar check (S): reject bytes above 127 and unescaped $ in source and comments before sending (we already have the rule in every file header; make it a check).
  • Formatter (M): clang-format cannot parse HolyC (postfix casts, switch [], char-constant statements); write a token-based indenter instead.
  • Test framework (S): this report's harness is the prototype: boot or restore the snapshot, send a test file, read TxP lines over serial (InU8(0x3FD)/OutU8(0x3F8) polling, no driver), assert on them from Python. Add KS_MODE=test to send-to-vm.sh and a tests/ directory. Goldens via screendump as plan-review suggested.
  • Profiler (M): a sampling profiler in the guest: IntEntrySet(0x20+n,...) or better a HolyC task that reads Fs->rip of the desktop task from a 1 kHz timer (cnts.jiffies tick hook via TimerIntHndlr? Not public; use a second core's spin loop reading desk_task->rip, which the scheduler updates on every switch only) is unreliable; the dependable form is manual GetTSC spans around phases, as the renderer pass already did. A symbolised histogram of Caller() addresses sampled from a timer IRQ is possible: install an interrupt function on an unused vector driven by the PIT or HPET at 1 kHz (Kernel/KTimer-equivalent TimersInit sets the PIT); M, and the payoff is high because every speed claim so far was from manual spans.
  • Doc generator (S): the DolDoc $LK$ syntax is machine-readable; a script that strips $...$ from Doc/*.DD (as done for this report) and our file headers produces Markdown.
  • Language server (L): holyc-lang ships hcc -lsp (BSD-2) [V, README]; it understands a superset of the language with some differences (F32, auto, range for). Using it on our sources for navigation is free; for diagnostics it will disagree with TempleOS on precedence unless its table is checked (not verified today).

6. Family D: safety#

Facts [V]: everything is ring 0 in one identity-mapped address space with 2 MB or 1 GB pages (Doc/MemOverview.DD:3, Kernel/Mem/PageTables.HC); only the lowest 2 MB is 4 KB pages (MemOverview.DD:56); page 0 is mapped, so *(0) reads BIOS memory (E4: reads F000FF53F000FF53, no fault); mem_mapped_space was 0x10100000000 with 1 GB of RAM, so addresses above it page-fault. A CPU fault goes INT_FAULT (KInts.HC:61-93) to Fault2 (KDbg.HC) which enters the debugger in the faulting task; try/catch does not see it (E4: the page fault inside try dropped to "TempleOS Debugger", Fault:0x0E Page Fault, and the task stayed there). throw is a software unwind through Fs->next_except (KExcept.HC:84-114).

Options:

Option How Cost Benefit Risk
Catchable faults for the desktop task (M, recommended) Patch the first bytes of Fault2 with a JMP to a HolyC KsFault2 (code heap is writable), or better IntEntrySet(I_PAGE_FAULT/I_GP, &KsIntFault) with a copy of the INT_FAULT stub; in the handler, if Fs is the desktop task and Fs->next_except is non-empty, SetRFlags to re-enable interrupts and throw('Fault'); otherwise fall through to the original Fault2. The desktop's frame loop wraps each app callback in try, logs the fault address and RIP, closes the window. M the common "bad pointer kills the demo" becomes a closed window and a log line a fault inside the renderer leaves the back buffer inconsistent (redraw all); a fault while holding a lock{} or inside the heap allocator corrupts state, so the policy must also mark the task for restart after N faults; interrupt state after a fault must be restored by hand

7. Family E: ecosystem#

  • libc shim (S): the functions C libraries actually need are memcpy/memset/memmove/strlen/malloc/free/realloc/abs/sqrt/pow/floor plus assert; all exist in TempleOS under other names (MemCpy, MemSet, MAlloc, Free, Sqrt, Pow, Floor). A 200-line HolyC file of _extern-style aliases plus a generated header lets ported C code (via family B trampolines) link. realloc must copy because MSize gives the rounded size.
  • Porting candidates: stb_image (PNG, JPEG; about 7,000 lines of C) and stb_truetype (5,000) compile freestanding with -DSTBI_NO_STDIO and user allocators; through clang plus trampolines they are M each, mostly ABI shim and testing under TCG for speed (JPEG decode of a 1 MB image will be seconds under TCG; measure). miniz for PNG inflate is L in HolyC by hand (plan-review's estimate) or S through clang. minimp3 is pointless without audio in the guest. lua (20,000 lines, needs setjmp/longjmp, stdio, strtod) is L and the value is an in-guest scripting language that HolyC already is; skip. mujs is L to XL and only matters for the browser's JavaScript, which the apps plan deferred. kilo is a 1,000-line editor that assumes POSIX termios; the Notes app already exists.
  • What HolyC cannot express and how to cope: C varargs (HolyC's argc/argv is different, write the shim per function), bit fields (Doc/HolyC.DD: none; use masks), float (none; decoders that use float must be built on the host), switch with sparse cases (jump table only; rewrite as if chains), string literals used as statements (HolyC prints them; never paste C into HolyC), static function-local arrays on the data heap (static vars stay on the code heap).
  • Package convention (S): one directory per package under B:/Pkg/<name>/ with <name>.HC as entry, <name>.BIN for host-built code, and a MANIFEST listing exports; the loader sends them over serial. Shrine's Pkg and PACKAGES.md format (ISO.C images, no dependency resolution) is the only prior art and is archived since 2020-11-13 [V, GitHub API].

Aiwnios in detail (answers to the questions asked; source read today, not built)#

  • Native or bytecode on macOS arm64: native JIT. The arm backend emits instructions through an assembler (c/arm64_asm.c, Xbyak-derived encodings per the README credits) into code-heap pages mapped PROT_EXEC|PROT_READ|PROT_WRITE with MAP_JIT on Apple (c/mem.c:681-683), toggles pthread_jit_write_protect_np around writes (SetWriteNP, c/mem.c:457-466) and flushes the instruction cache per compiled function (c/arm_backend.c:5309-5311). Bytecode is only the USE_BYTECODE build used for WASM [V].
  • Backend quality: reverse-Polish IR ("THIS COMPILER USES REVERSE POLISH NOTATION", README [V]); c/optpass.c has OptPassConstFold, OptPassMergeCommunitives, OptPassRemoveUselessArith, OptPassMergeAddressOffsets and OptPassRegAlloc, whose comment says "AIWNIOS will not do fancy register allocation shenanigins. We will get a score for REG_MAYBE|REG_ALLOC" (c/optpass.c:1066-1073 [V]); the developer manual's "Sexy Register Allocator: Live Variable Analysis, Graph Coloring" sections exist (DEVMAN.MD:910-920) but are headings in a WIP manual, so treat graph colouring as [U]. Temporaries are spilled depth-first (PushTmpDepthFirst, c/arm_backend.c:4757). Expect code quality in the TempleOS class, that is use-count register variables, not LLVM class. No benchmark published.
  • Inline asm on aarch64: no. KW_ASM in Src/PrsStmt.HC:1042-1056 is wrapped in #ifdef TARGET_RISCV with the comment "TODO gutted by nrootconauto in favor of his own assembler"; on aarch64 and x86-64 an asm{} block is not compiled [V]. Our asm{} routines (one block in desk3/01-core.HC with 11 _extern entry points, plus the spike files) would have to become C or HolyC. Src/AsmARM64.HC and Src/UAsmARM64.HC exist (an ARM assembler and disassembler in HolyC, 36 KB and 28 KB) and the README says "I plan on adding something lit like an arm assembler from HolyC", so the pieces exist but are not wired to asm{}.
  • Graphics, mouse, keyboard: SDL2 window created at 640x480 with a 4:3 letterboxed viewport (c/windows.c:82-116); the screen is an 8-bit paletted SDL_CreateRGBSurface(0,640,480,8,...) (:95) and UpdateScreen(px,w,h,w_internal) memcpys w bytes per row into it and presents via SDL_CreateTextureFromSurface (:170-192); GrPaletteColorSet sets the 16 colours (:195). Mouse events are scaled to 640x480 and delivered through FFI_CALL_TOS_4(ms_cb, x, y, z, state) with a relative mode available (:623-636, SDL_SetRelativeMouseMode :709). There is no 32-bit framebuffer path and no resolution other than 640x480; adding one is a change to windows.c (new surface format and size, a HolyC-visible UpdateScreen32) plus the HolyC side; M.
  • Native C functions: registered at start-up with PrsAddSymbol(name, int64_t (*)(int64_t *stk), arity) which binds a C function taking an array of 64-bit arguments (c/main.c:122-127, hundreds of uses such as PrsAddSymbol("PrintI", STK_PrintI, 2) :202), and PrsAddSymbolNaked for functions called with the native convention; the README's "Extending Aiwnios" shows the same mechanism plus how to add IR nodes. No dlopen (0 hits in c/*.c), so adding a NEON blend means editing main.c and rebuilding the runtime; S per function. The trampoline for calling HolyC from C is asm/ffi_call_tos_aarch64.s (FFI_CALL_TOS_n) [V].
  • Completeness: Src/ carries the TempleOS user land file by file (DolDoc Doc*.HC, Gr*.HC, Win.HC, WinMgr.HC, KTask.HC, Sched.HC, KExcept.HC, Menu.HC, Mouse.HC, Keyboard.HC, Sprite*.HC, God*.HC, file systems FAT/RedSea/virtual, sockets) with its own KernelA.HH (224 KB), AIWNIOS_CodeGen.HC, AIWNIOS_PrsExp.HC, a profiler (Profiler.HC) and ScrnCast.HC; there is no PCIBIOS, no port I/O, no KStart*, so anything that touches hardware (our Bochs VBE driver, OutU16, PCIReadU32) has no equivalent [V, directory listing]. try/catch, Spawn, MAlloc, Fs-> are provided (except.c, multic.c, mem.c, Src/KTask.HC).
  • Language: TempleOS precedence; no continue; reg/noreg honoured as scores; 8-char char constants (lexer is a port); F64 through NEON scalar (ARM_fmulReg in the README's example; AArch64_ops.csv 448 KB opcode table).
  • Build and benchmark: not done. The build was going to run in the scratchpad through a sub-agent; the request was refused by the session's permission classifier ("Code from External"). Dependencies per README: a C compiler, SDL2 development headers (Homebrew on macOS: "Your on your own"), cmake; then ./aiwnios -b to bootstrap HCRT2.BIN, ./aiwnios to run, --tui for a terminal mode, -c for a command. So the ns-per-pixel number for a HolyC blend loop on Aiwnios is not measured; the expectation from its allocator design is the same instruction mix as TempleOS's compiler executed natively, that is about 0.5 to 1 ns a pixel for the pointer-walk form (TCG costs roughly 5 to 10x on this loop, [U]).
  • Porting desk3 to Aiwnios: (1) a 32-bit, arbitrary-size framebuffer path in windows.c and a HolyC UpdateScreen32 binding, M; (2) replace the Bochs VBE and PCI code (desk3/01-core.HC, 04-main.HC, 05-splash.HC, 06-run.HC: 8 port-I/O sites) with the new binding, S; (3) rewrite KsBlendRow/Col/A/A2D, KsMix3, Copy32, Fill32 and the other 11 _extern asm entry points as C registered through PrsAddSymbol (NEON optional), M; (4) input: relative mouse already exists, keyboard key-up and modifiers are better than TempleOS's, S; (5) the splash, serial go-byte, savevm boot image and the TempleOS mirror window (gr.dc2) have no meaning there, rework the boot story, M; (6) timing and the Monitor app use cnts.jiffies, available; (7) persistence becomes real files, S; (8) the Files app browsing ::/ becomes the host directory, S. Total L to XL, and the result is a macOS app, not an OS, which plan-review section 3.12 already lists as "the embedding option: months; useful as the development vehicle and demo, not the goal".

Off x86 emulation for the OS itself: an ARM64 or RISC-V backend for the TempleOS compiler is XL and the kernel (KStart16/32/64, KInts, paging, PIT, PS/2, ATA, VGA) is x86 through and through; no fork has tried. KVM on an x86 host removes the TCG penalty entirely (plan-review condition 2). WebAssembly: Aiwnios's bytecode build, "slow" by its own README. Nothing here changes the recommendation to stay on QEMU for the showcase.

10. Recommended architecture for the next six months#

  • Language: HolyC, compiled by a lightly patched TempleOS compiler (continue, OPTf_C_PREC, peepholes, later SSE2), carried as a small patch series applied to ::/Compiler on the RAM drive during image build (build-image.sh step: copy, patch, Cmp, Load, relink, savevm). The desktop is compiled with C precedence; the loader restores TempleOS precedence before handing the prompt back so Demo/ and user programs keep their semantics.
  • Hot code: assembly kernels assembled on the Mac by NASM (SSE2 allowed after the one-line CR4 enable at desktop start, per core if -smp is used), embedded as DU8 byte strings with the source kept alongside; the existing hand asm{} routines stay. Rule: anything that runs per pixel or per glyph is a kernel; HolyC does per-span, per-widget and per-frame work.
  • Host-built C only for ported libraries (image decoders, TrueType), through the .BIN writer and trampolines, after the fetch channel exists.
  • Tooling on the host: kslint (precedence, ASCII, $, unused reg, functions over the register budget), ksfmt, kstest (serial harness), ksbench (section 11), a profiler in the guest reporting over serial. All Python, none touching the OS.
  • Safety: fault policy and debug allocator in the desktop; snapshot restore as the backstop; no attempt at memory protection.
  • Stop doing in HolyC: per-pixel loops with more than eight live variables; F64 arithmetic in anything that runs per frame (use fixed point or an SSE2 kernel); per-pixel function calls; goto-based continue once the keyword exists; expressions mixing &, |, ^, shifts with arithmetic without parentheses (lint).
  • First week: items 1 to 5 of the ranked list; they are all S and each is checkable with the benchmark set.

12. Risks and the conditions for leaving HolyC in an area#

  • Compiler patches diverge from upstream: TempleOS is frozen; ZealOS has not touched the compiler either. Keep patches under 500 lines total and rebuild-tested by the harness; if a patch breaks Cmp of the kernel (the Charter's own metric), revert it.
  • A patched compiler can be loaded half-built (E3 hazard): gate on Cmp()==0 and keep HolyCPrec-style restore paths; the image build must fail loudly, not snapshot a broken compiler.
  • SSE in a kernel that never used it: FXSAVE/FXRSTOR are already in the scheduler; interrupt handlers do not touch XMM; the only unknown is -smp (each core must set CR4). Test with the Monitor app running on a second core before relying on it.
  • Precedence switch is global: any TempleOS program compiled while it is on misparses; restore in the loader, add a lint that refuses to send a file compiled under the wrong table.
  • Fault catching hides bugs: log every caught fault with RIP and address over serial; a fault counter that restarts the desktop after three.
  • TCG numbers are not hardware numbers: a 2x change in instruction count can be 1.2x on KVM or metal; the only user-facing target is the frame time in QEMU on this Mac, so measure that.

Leave HolyC for an area when: (a) the kernel is floating-point heavy and the SSE2 backend is not done, use NASM; (b) the code is a port of more than 2,000 lines of C (decoders, fonts), use clang plus trampolines; (c) the loop needs more than eight live registers and the RBX audit is not done, use assembly; (d) a crash in that code would corrupt heap or lock state (allocator, scheduler hooks), keep it tiny and in assembly with no allocation. Stay in HolyC for everything else: the in-OS loop (edit, send, run, Uf, PassTrace) is the asset this project has that no host toolchain offers.

13. What could not be verified#

  • Aiwnios was not built or run; its blend speed on this Mac is an estimate.
  • The 31 ns figure's exact cause (window versus other conditions) was inferred from headless re-measurement of the same loop (11 ns), not re-measured with the window open.
  • holyc-lang's precedence table and the LSP's behaviour on our sources.
  • Whether a custom fault handler can throw out of Fault2 cleanly (interrupt flag, stack state): designed from KInts.HC and KExcept.HC, not tested.
  • -smp plus CR4.OSFXSR on every core; the single-core case was tested.
  • The compile time of the full desk3 (8,000 lines) under the patched compiler; the serial transfer dominates the measured 20 s today.
  • QEMU TCG's x87 implementation being 80-bit softfloat is the standard explanation for 48 to 67 ns per op [U]; the SSE2 number (6 ns) is measured.
