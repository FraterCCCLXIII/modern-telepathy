Can the kosmos engine run on TempleOS, and what is the best way

Edited 2026-10-27docs/engine-on-templeos.md

Feasibility study, 2026-10-27, branch task/templeos-shell. No engine crate was touched; all experiment code lives in the session scratchpad (.../scratchpad/engine-on-templeos/, not in the repo).

Tags: [R] verified by running something this session. [S] verified by reading source (path given). [M] from memory or inference, not checked.

1. Answer in one paragraph#

Yes, in a limited and well-defined form. A deterministic slice of the engine, compiled by rustc as no_std for x86-64 and wrapped as a TempleOS .BIN, was loaded into TempleOS V5.03, called from HolyC, and returned the same 64-bit values as the native aarch64 build (blake3 state hash and a 10,000-tick f32/libm physics loop) [R]. That settles the hard questions for route 1 (ABI, loader format, SSE, float determinism, task switching). What is not settled is size: the real kosmos-sim and kosmos-physics pull bevy_ecs, rapier3d, serde_json, thiserror and HashMap, which need alloc and a std-free port of our own crates; that is weeks, not days, and was not attempted. The whole engine (wgpu renderer, winit, threads, files, network, MCP) cannot and should not run inside TempleOS. Recommended: route 3 now (already how the desktop works, zero risk), route 1 as a gated spike for the sim core only, and route 4 on Aiwnios as a cheap by-product of a C-ABI build. Do not hand-port to HolyC.

2. Hard facts established (section B)#

Toolchain available [R]#

  • rustup target list --installed for the active toolchain (1.97.1): aarch64-apple-darwin, wasm32-unknown-unknown, x86_64-unknown-linux-gnu. x86_64-unknown-none is not installed. Nothing was installed.
  • nightly-2025-12-04 (rustc 1.93.0-nightly) has rust-src. rustc -Zunstable-options --print target-spec-json --target x86_64-unknown-none works without the target installed (the spec is built in), so a custom JSON can be derived from it.
  • cargo -Zbuild-std=core,compiler_builtins fails offline: build-std resolves the whole std workspace and the registry cache has no dlmalloc (and no compiler_builtins). Using it needs network access to crates.io (downloading source crates, no tool install). What the user would need to approve: either rustup target add x86_64-unknown-none (a tier-2 prebuilt core+compiler_builtins, about 30 MB, no network use at build time after that), or letting -Zbuild-std fetch std's dependencies. Either is needed for the soft-float variant with float code (see below).
  • Workaround that needed neither: build libcore by hand with the nightly rustc from rust-src (7 s) into a private sysroot for the custom target, supply a 20-line stand-in compiler_builtins (memcpy, memmove, memset, memcmp, bcmp), and point cargo at it with RUSTFLAGS=--sysroot=.... That built libm, blake3 and the test crate with plain cargo build --offline [R]. For the rest of the plan, installing the target is cleaner.

Trap found: the target JSON must be named x86_64-... [R]#

blake3's build script reads the first dash-separated component of $TARGET. A target file called ks-sse2.json gave TARGET=ks-sse2, the script concluded "not x86_64", configured no SIMD modules, and the build failed with "could not find sse2 in the crate root". Renaming to x86_64-ks-sse2.json fixed it. Any crate with an arch-sniffing build script will do the same.

Two custom targets (derived from the builtin x86_64-unknown-none)#

  • x86_64-ks-sse2: code-model small (the builtin one is kernel, which assumes addresses in the top 2 GB and is wrong for TempleOS, whose code heap is the low 2 GB), relocation-model pic, disable-redzone, panic-strategy abort, SSE and SSE2 enabled, no SSE3 and up, no x87 use for f32/f64.
  • x86_64-ks-soft: same but -mmx,-sse,-sse2 ... +soft-float and rustc-abi x86-softfloat. Float ops become compiler_builtins calls (__addsf3 and so on). Not built with float code (needs the real compiler_builtins); built and checked with integer-only code.

The test crate (ks-eng, no_std, no alloc) [R]#

Exports ks_add, ks_hash_abc (blake3 first 8 bytes, byte-identical to kosmos_core::state_hash; same locked versions blake3 1.8.7 with pure, libm 0.2.16 as Cargo.lock pins), and ks_run(seed, ticks): 16 bodies, f32 state, libm::sinf/cosf/sqrtf, a SplitMix64 kick, final state hashed. It stands in for the engine's float policy (rust-engine.md 4.2: IEEE f32, libm transcendentals, no mul_add).

Inspection with objdump -d (Apple's LLVM objdump reads x86-64 ELF) [R]:

build size xmm instructions x87 calls
sse2, with float 3,644 disassembly lines, 19 KB .BIN 1,744 lines mention xmm (expected) 0 11 calls, all internal: blake3, libm rem_pio2_large, core::panicking (loops forever), plus memcpy/memset through two GOT slots. No libc symbol.
soft, integer only 1,032 lines, 3.9 KB .BIN 0 0 1 internal call (blake3 portable compress)

Blake3 under the soft target selects only its portable path (the SSE modules are cfg-gated off), so no hidden xmm. Under the sse2 target it also links its SSE4.1 module (dispatch is a compile-time cfg!, no CPUID in no_std); harmless but dead weight.

Link step: rust-lld -flavor gnu -pie --no-dynamic-linker --gc-sections -T ks.ld, base address 0, one blob. The only relocations are 2 R_X86_64_RELATIVE (the GOT slots for mem*), which map exactly onto TempleOS IET_ABS_ADDR.

3. Route 1 in detail: the .BIN wrapper (format read from source) [S] and run [R]#

Format, from Kernel/KLoad.HC, Kernel/KernelA.HH:383-427, Compiler/CMain.HC:534-560 in the extracted ISO sources:

  • Header CBinFile is 32 bytes, not 40 as holyc-improvement-analysis.md section C says (U16 jmp, U8 module_align_bits, U8 reserved, U32 signature, then three I64: org, patch_table_offset, file_size). jmp = 0xEB | (30 << 8); signature 'TOSB' = 0x42534F54; org must be INVALID_PTR, which is I64_MAX (0x7FFF...F), not -1 (KernelA.HH:40), or Load copies to a fixed address; module_align_bits 4 gives a 16-byte aligned module_base (needed for SSE constant loads).
  • Image bytes follow at offset 32 (module_base). Exports are made visible to HolyC through the hash table.
  • Patch table at patch_table_offset, records U8 type; U32 value; NUL-terminated name, then payload: IET_REL32_EXPORT=16 (value = offset, symbol = base + offset), IET_ABS_ADDR=20 (value = count, empty name, then count U32 offsets; the loader does *(U32*)(base+off) += base, so the 64-bit slot must hold the link-time address in its low 32 bits, which works because the code heap is below 2 GB), IET_END=0 followed by 16 zero bytes. File size rounded to 16.
  • The writer is 25 lines of Python (mkbin.py: rust-objcopy -O binary, symbols from objdump -t, relative relocs from objdump --dynamic-reloc).

Calling convention: the .BIN is SysV, TempleOS is stack-based, callee-pops. One HolyC asm{} trampoline serves every export (KseSysV2(fn, a, b)): load fn from SF_ARG1[RBP], args from SF_ARG2/3 into RDI/RSI, save RBX/RSI/RDI/R10/R11 (SysV callee clobbers RSI, RDI, R10, R11 that TempleOS expects preserved; R12-R15, RBX, RBP are preserved by SysV), AND RSP,-16 because TempleOS gives no alignment and rustc spills with movaps, CALL RAX, restore, RET1 24. The exported address is fetched with HashFind("KsEngRun", Fs->hash_table, HTT_EXPORT_SYS_SYM)->val. Generating one trampoline per signature (2 to 6 integer args) is trivial; floats and structs pass through memory pointers.

What ran [R]#

TempleOS V5.03 ISO, QEMU TCG, headless, -m 1024M, KS_TVM=/tmp/tvm-eng, KS_SERIAL_PORT=4564. The .BIN and the HolyC test went in over the serial Rx receiver (serial-send.py; I booted with boot-vm.sh and defined Rx by hand instead of snap.sh, because snap.sh regenerates ProjectsData.HC inside the repo). Results are printed on COM1 and compared with the native aarch64 host build of the same source:

call TempleOS x86 (TCG, SSE2 on) host aarch64 match
add(40,2) 0x2A 42 yes
hash_abc 33514638ACB33764 33514638acb33764 yes
run(7,1) C049312FC87B5352 c049312fc87b5352 yes
run(7,64) F429E7AA152561B5 f429e7aa152561b5 yes
run(7,1000) 25C96999908C8471 25c96999908c8471 yes
run(7,10000) 8F53F2C9CCFD7243 8f53f2c9ccfd7243 yes
  • SSE was enabled by MOV_RAX_CR4; OR RAX,0x600; MOV_CR4_RAX (OSFXSR bit 9 plus OSXMMEXCPT bit 10) in a 5-instruction asm routine, run once on core 0. Nothing in TempleOS objected. The integer-only soft-float .BIN also loaded and returned the same hash_abc with SSE untouched.
  • Task switching: the main task plus two Spawned tasks each ran run(7,10000) 8 times (24 runs, Yield between), single core; 0 mismatches. The scheduler's FXSAVE/FXRSTOR per task (Kernel/Sched.HC:87,119, 512-byte CFPU per task, KTask.HC:211) preserves XMM once OSFXSR is on, as the analysis doc predicted. Not tested: a second core (-smp; each core needs its own CR4 write), a timer interrupt landing mid-call (the Yield-based test did not prove preemption), and the fault path (a #UD from SSE with OSFXSR off would drop into the TempleOS debugger; I did not trigger it because it hangs the VM).
  • Speed: run(7,10000) takes 43 ms in the guest (cnts.jiffies) against 1.72 ms native, about 25x, which is TCG's cost for SSE2 scalar float plus sinf/cosf in pure-Rust libm. On KVM or an x86 host it would be near native; on this Mac the engine inside TempleOS is TCG-bound.
  • VM stopped with KS_TVM=/tmp/tvm-eng scripts/stop-vm.sh; three other QEMU processes (not mine) kept running.

Determinism assessment#

  • Float. IEEE f32 + - * / and sqrt are bit-identical on SSE2, AArch64 and wasm, and the test confirms it across x86-under-TCG and aarch64. The risks are the ones the plan already names (4.2): no mul_add, no -C target-feature=+fma, transcendentals only from libm (done: libm 0.2.16 is the locked version and was the one linked), no fast-math. x87 must never be used for engine f32 or f64: TempleOS's own compiler uses x87 with 80-bit intermediates, and the Aiwnios README already documents the consequence for the desktop (0.36 percent of wallpaper pixels and some graph pixels differ by one level between x86 TempleOS and Aiwnios, aiwnios/README.md) [S]. HolyC has only F64 (no f32 type) [M], so route 2 cannot reproduce f32 hashes at all, and kosmos-crowd (all f64) would differ in the last bits [M, from the README evidence].
  • Hashing. blake3 pure produced the same digests as the std build with its runtime-dispatched SIMD. No platform dependence found. State serialisation uses to_le_bytes, which is fine on x86.
  • Threads. The sim is single-threaded by contract (rust-engine.md principle 1: iteration by SimId). bevy_ecs runs systems on a thread pool by default but is #![no_std] with a single-threaded executor available [S for no_std: bevy_ecs-0.20.0/src/lib.rs:16; M for executor choice]. kosmos-host, -genai, -human use std::thread/rayon and stay outside the slice.
  • libm. Only the libm crate; never f32::sin (a disallowed_methods rule already exists per the plan).

5. Engine requirements versus TempleOS (section C)#

Under -m 1024M there is roughly 1 GB total; the desktop's framebuffers already use a large share [M] Fits a small scene. Give the Rust side one arena (one MAlloc, passed at init) behind a bump or simple free-list #[global_allocator]; no per-allocation HolyC calls.

Network, MCP tungstenite, kosmos serve --port, kosmos-mcp stdio/ws no TCP stack in V5.03 (serial only) Stay on the host (route 3).

Which crates can plausibly go bare metal [S: Cargo.toml and source reads; not compiled]: - kosmos-core (220 lines): blake3, rand_pcg, serde, uses std::hash; trivial to make no_std. - kosmos-math (243 lines): glam (has a libm feature, #![cfg_attr(not(feature="std"), no_std)]) and libm. Easy. - kosmos-airship (9.8 k lines), kosmos-crowd (4.3 k, uses HashMap and serde_json, f64): pure sims, libm, need alloc, HashMap must become BTreeMap or hashbrown with a fixed hasher. Moderate; this changes iteration order, so the golden hashes must be rechecked. - kosmos-sim (6.1 k): bevy_ecs 0.20 (declares #![no_std]), postcard, serde_json, thiserror; snapshot/replay use serde_json and files in two places. Moderate to large. - kosmos-physics (1.4 k wrapper): rapier3d 0.36 declares #![no_std] (rapier3d-0.36.1/src/lib.rs:13), but pulls nalgebra, parry, and whatever float intrinsics those use [M]; the repo's own wasm hash harness (apps/kosmos-hash) already proves it runs without OS services on wasm32. Unknown until compiled. - Out: kosmos-render, -app, -host, -genai, -human, -audio, -protocol (tungstenite), -assets, -scene (jsonschema).

What the engine would give TempleOS users: deterministic physics and walking/vehicle/airship sims, crowd, seeded replays whose hash can be checked against the host, snapshot/restore, and (through the host) the agent surface. In every route except 4 the MCP/agent control stays on the host, because TempleOS has no sockets; a TempleOS user would see it as an app that talks to the host over serial. A HolyC-visible API of 6 to 10 integer-argument entry points (engine_init(arena, size), load(buf,len), step(n), hash(), pose(id, out), snapshot(out), restore(buf,len)) is enough.

6. Route notes#

Route 2, port the sim to HolyC. About 6 k lines for kosmos-sim alone plus the physics (rapier is not portable by hand), and the crowd/airship ports are 14 k lines of f64. HolyC has F64 on x87 only (analysis section on floating point), no f32, a different operator-precedence table, no continue, one compiler. The hashes would not match the engine's f32 values, which defeats the purpose of the engine's replay contract. Measured float cost today: 67 ns per multiply-add (x87 under TCG) against 6 ns for hand SSE2 (holyc-improvement-analysis.md). Rejected.

Route 3, host engine, TempleOS client. What the repo already does. kosmos serve --port speaks line-delimited JSON/WebSocket (apps/kosmos-cli/src/main.rs; rust-engine.md 4.15); TempleOS has serial only, so the same bridge as the browser spec (framed binary over COM1 with CRC, browser-architecture.md section b1) would carry step, query, hash and a state or display-list stream, with a small Python or Rust bridge on the Mac translating serial to the WebSocket. The TempleOS side draws with its own software renderer. Cost S to M; no determinism question since the engine runs once, on the host.

Route 4, Aiwnios. Aiwnios binds native C through PrsAddSymbol(name, int64_t (*)(int64_t *stk), arity) and has no dlopen [S, aiwnios/README.md and the analysis doc], so the engine would be linked into the Aiwnios runtime itself (a static library, crate-type = ["staticlib"] with a C header) and registered at start-up, then called from HolyC like any function. This is the one route where the full engine (std, threads, files, even wgpu) can sit next to HolyC, because it is a normal arm64 process. It costs a patch and rebuild of the Aiwnios runtime for each new entry, but each entry is a few lines. It does not run the x86 TempleOS build and it is not the OS showcase; it is a development vehicle. Not built or run here (the analysis doc records that the Aiwnios build was earlier blocked by the permission classifier).

Route 5. Status quo: TempleOS UI in QEMU, everything else on the host. It is route 3 without the dedicated protocol work.

7. Recommendation (section D)#

Ranked: 1. Route 3 as the product path (now). It is the only route that gives TempleOS users the whole engine, including rendering assets, physics at full speed and the MCP surface, and it adds no new risk. Build the serial protocol once; it also serves the browser. 2. Route 1 as a research spike, sim core only, because it is the only route that puts engine code inside the OS and the experiment shows it works. Value: a TempleOS-native "engine state hash" check, offline deterministic replays, and a stress test of the engine's no_std hygiene that also benefits wasm. Do not promise physics at scale under TCG (25x slower in the test). 3. Route 4 only if Aiwnios becomes the desktop's daily driver; almost free once a staticlib with a C header exists. 4. Route 2: no. Route 5: keep as fallback, it is what runs now.

Risks#

  • Hash drift: HashMap-to-BTreeMap swaps change iteration order; every hash golden would need a hash-epoch bump (core HASH_EPOCH policy). Keep std builds as source of truth and prove the bare-metal build matches them, not the reverse.
  • Toolchain coupling: bare-metal build needs nightly features (-Zbuild-std or a prebuilt target, custom JSON), while the workspace builds on stable; isolate it in one CI job and pin the nightly (2025-12-04 here).
  • TempleOS fragility: faults are uncatchable and drop to a debugger; an out-of-arena write corrupts the single address space (no MMU protection). Run the engine only in a throwaway VM snapshot during development.
  • TCG speed: 25x on float-heavy code; acceptable for hashes and small scenes only.
  • blake3 SIMD dead code and compiler_builtins float helpers in the soft-float variant are unverified; choose the SSE2 variant, which was verified.

Relation to the Linux and Wayland fallback (os-foundation-plan.md)#

That plan (Linux with our own Wayland compositor, apps run unmodified) is the real OS direction. It makes the engine a normal native Linux process, so nothing in this study is needed for it. The TempleOS-hosted engine is therefore a showcase and research track, not a dependency: a TempleOS desktop on Linux or on this Mac is route 3/5 whichever kernel is underneath. If the Linux shell lands, route 3 becomes "TempleOS-style shell talks to the same kosmos serve" with the Wayland shell as client, and route 1 remains optional.

8. What was not verified#

Real engine crates were not compiled for bare metal (only reading their manifests and sources); rapier3d and bevy_ecs on this target are untested. The soft-float variant with float code needs the real compiler_builtins (network) and was only built integer-only. No SMP, no real preemption proof, no stack-depth measurement, no fault test, no Aiwnios build. The 25x speed figure is one measurement of one loop under TCG on an Apple Silicon Mac. TempleOS behaviour for Spawn stack size and heap limits under -m 1024M is from memory.

Experiment files (scratchpad, not in the repo): engine-on-templeos/ks-eng/ (crate), host-ref/ (native reference), x86_64-ks-sse2.json, x86_64-ks-soft.json, ks.ld, mkbin.py, KSENGT.HC, KSENGT2.HC, sse2.dis, soft.dis, serial*.out.
